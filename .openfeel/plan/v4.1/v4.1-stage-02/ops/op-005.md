将 `reviewer.md` 从 86 行扩充到 90–110 行，细化快速通道三要素的获取/判定方式，标准化 REV 条目的 YAML frontmatter 格式，明确 blocking 字段的判定细则。

> 参见 kb/patterns.md #REV blocking 标记模式、#审查五维度体系 — 这些已沉淀的模式需硬化到 Reviewer prompt 中成为必遵守规则。

## 实施步骤

- [ ] 1. 读取当前 `.opencode/agents/reviewer.md` 完整内容（87 行）
- [ ] 2. 扩充 `## 快速通道` 中的三要素条件表，在「获取方式」列补充具体的操作指令：
  - 代码量：从 Executor 自测报告的 `git diff --stat` 汇总中提取 `+` 行数
  - Executor 自测：从自测报告的「自测结果」字段获取（须为 `全部通过`）
  - 测试覆盖率：从自测报告的 `coverage` 字段获取（须 ≥ 80%）
  - 代码量统计规则：仅统计新增和修改的行（`+` 和 `~`），不统计删除行（`-`）
- [ ] 3. 扩充 `## 快速通道` 的「快速通道行为」：
  - 补充：即使快速通道，仍需对产出文件做最低限度的人工审查（通读 diff）
  - 补充：若产出文件 ≥ 5 个，快速通道自动失效（恢复完整审查）
- [ ] 4. 在 `## 审查流程` 之前新增 `## REV 模板规范` 节：
  - 标准化 REV 条目格式，采用 YAML frontmatter：
    ```yaml
    status: pending | fixing | resolved | closed
    priority: high | medium | low
    author: Reviewer
    created: YYYY-MM-DD HH:MM
    blocking: true | false
    ```
  - 确保 Schemer 和工具链可程序化解析（连续 3 个 `-` 作为 YAML 分隔符）
  - 条目编号格式：`REV-{NNN}`（阶段内递增）
  - 参见 kb/patterns.md #REV blocking 标记模式
- [ ] 5. 在 `## 注意事项` 中细化 blocking 判定细则（替换当前的简单枚举为场景化判定表）：
  - **blocking=true**（无条件阻塞）：
    - 功能缺陷（实现与方案目标不符）
    - 安全事故（注入/越权/泄露/路径遍历）
    - 产出文件缺失（方案声明但未产出）
    - 破坏现有测试（引入回归）
  - **blocking=true**（需判定，默认阻塞）：
    - 编码规范严重违反（违反 AGENTS.md 核心约束）
    - 跨模块一致性问题
  - **blocking=false**（非阻塞）：
    - 命名建议（不影响功能）
    - 注释完善建议
    - 代码风格微调（不影响可读性）
    - 优化建议（非必要修复）
  - 快速通道命中时，REV 默认 `blocking=false`（安全漏洞除外）
- [ ] 6. 新增 `## blocking 与流水线行为` 小节（在 blocking 判定细则后）：
  - blocking=true → 流水线设为 `review_failed`，阻塞推进
  - blocking=false → 流水线直接推进到 `review_passed`，REV 保持 open 跟踪
  - 每个 op 至少需要 1 条阻塞性 REV closed 才能标记阶段为 review_passed（保留原有规则）
- [ ] 7. 最终检查：`wc -l` 确认行数在 90–110 范围内
