## 一、变更目标

补齐「纠正/清理」侧的首个能力（反馈二问题 1/2）：**孤儿 op**（`flow.json` 的 `stages[].ops` 键与 `ops/` 目录文件不一致）的**回收**与**检测**——新增 `plan scheme remove`、`flow repair` op↔opsDir 对账、`flow health` 孤儿 warn，使「禁止手改 flow.json」在故障恢复场景下可解。

**A2 裁定落地要点**：默认**只报告、不删任何条目**；清理须显式 `--prune-orphans`。

### N1-1（高）新增 `openfeel plan scheme remove <stage> <opId>`

- **文件:行号**：`src/commands/plan.ts:98-132`（`scheme` 组，现有 `create`/`list`）；`src/core/plan/scheme.ts:177-211`（`createScheme` 旁新增）
- **现状**：`plan scheme` 仅有 `create`/`list`，**无删除** → 多建的 op 只能永久残留或违规手改 `flow.json`（`scheme.ts` 仅 `createScheme`）。
- **改后**：
  1. **core 新增**（`src/core/plan/scheme.ts`）：
     ```ts
     /** 删除结果 */
     export interface RemoveSchemeResult {
       /** 是否已删除 flow.json 中的 op 键 */
       removed: boolean;
       /** 未删除时的原因（错误码，供命令层映射 i18n） */
       reason?: 'stage-not-found' | 'op-not-found' | 'op-done' | 'has-checkpoint';
       /** 该 op 是否本已是「键孤儿」（opsDir 无对应文件） */
       orphan?: boolean;
     }

     /**
      * 从 flow.json 注销一个 op 键（不删除 op 模板文件），并留审计日志。
      * 默认对「已 done」或「存在 checkpoint 进展」的 op 拒绝删除（--force 覆盖）。
      * @param projectPath 项目根路径
      * @param stageName 阶段 ID（简写或全称，经 normalizeStageId 归一）
      * @param opId op ID（op-001 或 完整 stage.op-001）
      * @param options.force 跳过保护校验
      * @returns 删除结果（成功/原因码/是否孤儿）
      */
     export function removeScheme(
       projectPath: string,
       stageName: string,
       opId: string,
       options?: { force?: boolean },
     ): RemoveSchemeResult
     ```
  2. **校验矩阵（默认拒绝 → 命令层 exit 1；`--force` 覆盖）**：

     | 情形 | 默认 | `--force` | 说明 |
     |------|:--:|:--:|------|
     | 阶段或 op 键不存在 | **拒绝**（错误） | 拒绝 | 无对象可删 |
     | `op.state === 'done'` | **拒绝**（`op-done`） | 允许 | 保护已完成进度 |
     | 存在该 op 的 checkpoint 进展 | **拒绝**（`has-checkpoint`） | 允许 | checkpoint 目录/快照含该 op 或阶段快照指向该 op |
     | **孤儿**（`opsDir` 无对应文件） | **允许** | 允许 | **这正是回收场景**（`orphan: true`） |
     | 正常 pending/executing op | 允许 | 允许 | 常规纠错 |

  3. **实现要点**：删除 `flowData.stages[stage].ops[opId]` 键（经 `FlowManager` 加锁 + `save()`）→ `appendLog({ action: 'scheme_remove', detail: { stage, opId, force, orphan } })`；**不删除 op 模板文件**（避免误删源码）——删键后该文件成为「文件侧孤儿」，由 `flow repair` 报告并提示（人工删除或保留）。
  4. **命令层**：`plan scheme remove <stage> <opId>` + `--force` + `--dry-run`（预览不写盘，沿用既有 dry-run 语义）。

### N1-2（高）`flow repair` 增「ops 键 ↔ opsDir 文件」对账

- **文件:行号**：`src/core/flow-manager.ts:2275-2410`（`repair(dryRun)`）+ 命令层 `src/commands/flow.ts:876-895`（`flow repair [--dry-run] [--backup]`）
- **现状**：`repair()` 只做字段级修复（`pipeline.current`/缺失字段等），**不做 op↔文件对账** → op 数虚高、幽灵条目被调度。
- **改后**：
  1. **core 新增**（`src/core/flow-manager.ts`）：
     ```ts
     /** 孤儿 op 描述 */
     export interface OrphanOp { stage: string; opId: string; }
     /**
      * 对账 flow.json 的 op 键与 ops/ 目录文件。
      * @param projectPath 项目根
      * @returns keyOrphans（有键无文件）/ fileOrphans（有文件无键）
      */
     export function findOrphanOps(projectPath: string): { keyOrphans: OrphanOp[]; fileOrphans: OrphanOp[] }
     ```
  2. `repair()` 集成：`RepairResult` 增 `orphans?: { keyOrphans; fileOrphans }` 字段；**默认只报告**（命令层打印清单）。
  3. `--prune-orphans`：**仅清理 `keyOrphans`**（删 flow.json 孤儿键 + `appendLog`）；**`fileOrphans` 永不自动删除**（仅报告并提示：保留或经 `plan scheme create` 重新注册 / 人工处理）——避免误删源码。
  4. 命令层：`flow repair` 增 `--prune-orphans`；与 `--dry-run` 组合 → **只预览不写盘**（沿用 stage-49 B1 的 dry-run 语义）。
- **行为变更**：**是（附加输出）**——`flow repair` 新增孤儿报告行；**默认不删任何条目**。

### N1-3（高）`flow health` 增孤儿 op warn

- **文件:行号**：`src/core/flow-manager.ts:2683-2752`（`healthCheck` 现有检查）+ 参照 `:2728`（`checkDanglingDeps` 范式）
- **现状**：`healthCheck` 只检查 `current` 指向的 op（`:2689` 附近「不存在的 op」），**全量孤儿不检测**。
- **改后**：新增私有 `checkOrphanOps(items)`：
  - `keyOrphans.length > 0` → `status: 'warn'`，detail 列出前 N 条（如 5 条）+ 总数（`… 等 N 个`）；
  - `fileOrphans.length > 0` → `status: 'warn'`（detail 注明可能为历史命名/已注销键，建议人工确认）；
  - **不设为 `fail`**（保持非阻塞；`health` 退出码仅由 `fail` 决定 → **不改变退出码**）。
  - quick 模式下若成本高可跳过（与既有 quick 语义一致）：**建议**在 quick 模式仍执行（纯内存 + 目录列举，成本低），但在方案中标注该取舍。

## 八、风险与回滚
