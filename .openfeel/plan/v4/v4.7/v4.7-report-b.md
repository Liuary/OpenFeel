## 1. LangGraph（LangChain 生态）

### 核心机制

LangGraph 是 LangChain 推出的有状态图编排框架，核心抽象为**有向图**：

- **节点（Node）**：Python 函数或 LangChain Runnable，表示计算步骤
- **边（Edge）**：普通边（固定流转）和条件边（运行时决定下一节点）
- **状态（State）**：共享的 TypedDict Schema，所有节点读写同一个 State 对象
- **Checkpointer**：状态持久化层，支持 Memory / SQLite / Postgres 后端

```
Agent Loop = 工具调用节点 → 条件边{工具调用? → 工具执行 → 回到 LLM | else → END}
```

### 亮点

| 维度 | 机制 |
|------|------|
| 调度模型 | **中心化状态图**，由 StateGraph 定义全流程，节点间通过 State 耦合 |
| Loop/反思 | 条件边实现工具调用循环；支持 `interrupt` 暂停等人机交互 |
| 状态管理 | Checkpointer 持久化 State，支持跨会话恢复（`get_state` / `update_state`） |
| 提示词策略 | 主要通过 LangChain ChatPromptTemplate 构建，无框架级分层 |
| 工具集成 | 通过 `ToolNode` 统一包装，支持 `@tool` 装饰器注册 |

### 与 OpenFeel 对比

| 维度 | LangGraph | OpenFeel |
|------|-----------|----------|
| 调度模型 | 图状态机（节点+边+条件） | 流水线状态机（phase 序列 + flow.json） |
| 灵活性 | 极高，任意 DAG | 固化，预定义 phase 流水线 |
| 可恢复性 | Checkpointer 持久化任意节点 | flow.json + status.md 记录阶段进度 |
| 碰撞点 | **OpenFeel 可借鉴条件边机制**，在 phase 间增加决策逻辑 | |
| 优劣势 | LangGraph 灵活但需手动搭建；OpenFeel 开箱即用但扩展性弱 | |

## 2. CrewAI

### 核心机制

CrewAI 采用**角色化团队**模型，核心抽象为 Agent → Task → Crew → Process：

- **Agent**：拥有 `role` + `goal` + `backstory`，可配备 `tools` 和 `memory`
- **Task**：描述 + 预期输出 + 指定执行 Agent，支持 `context` 任务间依赖
- **Crew**：Agents + Tasks + Process 的组合，通过 `kickoff()` 启动
- **Process**：`sequential`（串行）或 `hierarchical`（管理 Agent 委派）

```
Crew Loop = 遍历 Task 列表 → Agent 执行（tool-use loop + 最多 max_iter 次）→ 输出 → 下一 Task
```

### 亮点

| 维度 | 机制 |
|------|------|
| 调度模型 | **中心化 Crew 调度**，按 Process 模式决定执行顺序 |
| Loop/反思 | `reasoning=True` 启用前置规划；`max_iter`（默认 20）限制工具调用轮次；`max_retry_limit`（默认 2）控制重试 |
| 状态管理 | **CheckpointConfig**（v0.x 新增），支持按事件自动保存（`task_completed` 等），`Crew.from_checkpoint()` 恢复 |
| 提示词策略 | 三层模板（`system_template` / `prompt_template` / `response_template`），支持 `{role}` `{goal}` 等变量注入 |
| 工具集成 | 兼容 CrewAI Tools + LangChain Tools；JSONC 声明式配置 |
| 上下文管理 | `respect_context_window=True` 自动摘要；False 时超标报错 |
| 记忆 | 短期 + 长期 + 实体记忆（`memory=True`） |

### 与 OpenFeel 对比

| 维度 | CrewAI | OpenFeel |
|------|--------|----------|
| 调度模型 | Task 列表线性 + 可选层级 | phase 序列 + 子阶段并行 |
| 角色体系 | 完全由用户自定义 | 9 Agent 固定角色（Planner/Executor/Reviewer 等） |
| 可恢复性 | CheckpointConfig 任务级 | flow.json 阶段级 |
| 碰撞点 | **借鉴 Checkpoint 机制**增强 OpenFeel 容错；**借鉴 reasoning 模式**给 Agent 前置规划空间 | |
| 优劣势 | CrewAI 角色灵活但缺流程治理约束；OpenFeel 流程严格但角色固化 | |

## 3. AutoGen v0.4（Microsoft）

### 核心机制

AutoGen 采用**团队（Team）** 为调度单位，v0.4 大幅重构为异步消息驱动：

- **Agent（AgentChat）**：`AssistantAgent` 为核心，具备 tool calling + handoffs
- **Team**：多种预设模式 — RoundRobin / Selector / Swarm / MagenticOne
- **消息**：TextMessage / HandoffMessage / ToolCallRequestEvent 等类型化消息
- **终止条件**：TextMentionTermination / ExternalTermination / MaxMessageTermination 组合

```
Team Loop = 选择 Speaker → Agent.run() 产生消息 → 检查终止条件 → 下一 Speaker / Stop
```

### 四种 Team 模式

| 模式 | 机制 | 适用场景 |
|------|------|----------|
| **RoundRobin** | 轮流发言，共享上下文 | 反思模式（primary + critic） |
| **SelectorGroupChat** | LLM 动态选择下一发言人 | 开放协作 |
| **Swarm** | HandoffMessage 驱动交接，去中心化 | 客服路由、多专家系统 |
| **MagenticOne** | 通用多 Agent 系统，内置 Orchestrator | 跨领域开放任务 |

### 亮点

| 维度 | 机制 |
|------|------|
| 调度模型 | **中心化 Team + 去中心化 Swarm 双模式** |
| Loop/反思 | Reflection 模式（primary + critic 循环直到 APPROVE）；`max_tool_iterations` 限制工具调用 |
| 状态管理 | `save_state()` / `load_state()` 完整序列化，支持 JSON 持久化到磁盘/数据库 |
| 提示词策略 | `system_message` 单层；通过 Handoff 传递角色上下文 |
| 工具集成 | 任意 async 函数；`handoffs` 作为特殊工具；支持 parallel tool calling 控制 |
| 人机交互 | Human-in-the-Loop（通过 Handoff to "user"） |
| 控制 | CancellationToken 中止；ExternalTermination 优雅停止；`reset()` 清除状态 |

### 与 OpenFeel 对比

| 维度 | AutoGen | OpenFeel |
|------|---------|----------|
| 调度模型 | 多种 Team 模式可选 | 单一流水线模型 |
| 交接机制 | HandoffMessage 标准化 | 无内部交接，由 Feel 统一调度 |
| 终止控制 | 组合式终止条件（位或运算） | phase 状态机推进 |
| 状态 | Agent/Team 完整序列化 | flow.json + status.md 文件状态 |
| 碰撞点 | **借鉴 Swarm 的 Handoff 机制**让 Agent 间自主交接；**借鉴组合终止条件**增强 phase 转换灵活性 | |
| 优劣势 | AutoGen 团队模式丰富但学习曲线陡；OpenFeel 简单但缺运行时灵活性 | |

## 4. MetaGPT

### 核心机制

MetaGPT 提出 **`Code = SOP(Team)`** 的核心理念，将人类软件公司的**标准操作流程**编码到多 Agent 提示词中：

- **角色**：Product Manager / Architect / Project Manager / Engineer
- **SOP 编码**：每个角色按预定义流程生成结构化文档（PRD / 设计文档 / 任务列表 / 代码）
- **流水线**：需求 → 竞品分析 → 数据结构 → API 设计 → 代码生成

```
SOP Pipeline = PM 生成 PRD → Architect 生成设计 → PM 生成任务 → Engineer 逐任务编码
```

### 亮点

| 维度 | 机制 |
|------|------|
| 调度模型 | **装配线范式**（Assembly Line），固定顺序的流水线 |
| Loop/反思 | 通过结构化产物的**上下游审查**实现纠错（下一角色审阅上一角色产出） |
| 状态管理 | 基于文件系统（workspace 目录），每步产出落盘为 .md/.json/.py |
| 提示词策略 | **SOP 编码到系统提示词**，每个角色有详细的职责和工作流程描述 |
| 工具集成 | 主要是代码生成和文件操作 |
| 论文成果 | ICLR 2024 接收；后续 AFlow（ICLR 2025 Oral）自动化工作流生成 |

### 与 OpenFeel 对比

| 维度 | MetaGPT | OpenFeel |
|------|---------|----------|
| 调度模型 | 固定装配线（需求→设计→编码） | 通用流水线（plan→scheme→exec→review→test→archive） |
| 角色粒度 | 模拟软件公司真实角色 | 模拟开发流程角色 |
| SOP 方式 | 编码在角色 prompt 中 | 编码在 flow.json + AGENTS.md 约束中 |
| 碰撞点 | **借鉴 SOP 编码模式**将流程约束更结构化地注入提示词；**借鉴装配线范式**的角色间产物传递 | |
| 优劣势 | MetaGPT 流水线固定不可扩展；OpenFeel 流水线通用但缺少领域化 SOP 模板 | |

## 5. OpenAI Agents SDK

### 核心机制

OpenAI Agents SDK 定位为**轻量级生产级 Agent 框架**，仅三个核心原语：

- **Agent**：LLM + instructions + tools + handoffs + guardrails
- **Handoff**：Agent 间任务委派的标准机制
- **Guardrail**：输入/输出/工具调用的安全校验

```
Agent Loop = LLM 推理 → 工具调用 → 执行 → 回到 LLM | Handoff → 新 Agent | 完成 → 输出
```

### 两种编排模式

| 模式 | 机制 | 决策依据 |
|------|------|----------|
| **Agents as Tools** | 管理 Agent 调用 `Agent.as_tool()`，保持对话控制权 | 合并多专家输出、统一 guardrail |
| **Handoffs** | Triage Agent 将对话路由到专家 Agent，专家接管对话 | 专家直接回复、聚焦 prompt |

### 亮点

| 维度 | 机制 |
|------|------|
| 调度模型 | **LLM 自主编排 + 代码编排双模式** |
| Loop/反思 | 内建循环直到任务完成；支持 `while` 循环 + evaluator 的迭代改进模式 |
| 状态管理 | **Sessions** 持久工作内存（SQLAlchemy / SQLite / Redis / MongoDB / Dapr / Encrypted） |
| 提示词策略 | `instructions` 字符串 + `RECOMMENDED_PROMPT_PREFIX` 前缀提示 handoff 用法 |
| 工具集成 | 任意 Python 函数 → 自动 schema 生成；MCP Server 工具；**Sandbox agents** 隔离执行 |
| 权限控制 | `input_filter` 控制 handoff 时的历史可见性；Guardrails 输入输出校验 |
| 可观测性 | 内建 Tracing + Agent 可视化 |

### 与 OpenFeel 对比

| 维度 | OpenAI Agents SDK | OpenFeel |
|------|-------------------|----------|
| 调度模型 | LLM 自主决策 + 代码控制 | flow.json 状态机全量控制 |
| 交接机制 | Handoff 是核心原语（按功能设计） | 无 Agent 间交接，Feel 统一调度 |
| 状态 | Sessions 多后端持久化 | flow.json + 文件状态 |
| Sandbox | 内置 Sandbox agents 支持隔离执行 | 无 |
| 碰撞点 | **借鉴 Handoff 原语**让子 Agent 可通过标准接口自主委派；**借鉴 Sandbox 机制**实现代码执行隔离；**借鉴 Guardrail 模式**增强阶段间质量门控 | |
| 优劣势 | Agents SDK 轻量灵活但缺流程治理；OpenFeel 流程治理强但缺运行时灵活性 | |

## 6. Anthropic Claude Agent SDK / Claude Code

### 核心机制

Claude Code 是 Anthropic 的 Agent 编程工具，其 Agent SDK 能力嵌入在 Claude Code 产品中：

- **子 Agent（Sub-Agents）**：Lead Agent 协调多个子 Agent 并行工作
- **动态工作流**：通过 prompt 描述让 Claude Code 自行决定执行策略
- **CLAUDE.md**：项目级持久指令文件，每次会话自动读取
- **Skills**：可复用工作流包（如 `/review-pr`、`/deploy-staging`）

```
Session Loop = 用户指令 → Claude 自主计划 → 工具调用循环 → 产出 → 用户审查
```

### 亮点

| 维度 | 机制 |
|------|------|
| 调度模型 | **LLM 自主决策**（无显式状态机），通过 prompt 描述任务策略 |
| Loop/反思 | 内建工具调用循环；子 Agent 并行 + 结果合并 |
| 状态管理 | CLAUDE.md 持久指令；**Auto Memory** 自动跨会话学习（如构建命令、调试经验） |
| 提示词策略 | CLAUDE.md 项目指令 + 自动记忆 + Skills 三层；**Hooks** 在操作前后注入行为 |
| 工具集成 | MCP 协议标准化工具连接；bash / 文件编辑 / git 等内置工具 |
| 子 Agent | 显式 `task` 工具启动子 Agent，支持并行 + Lead Agent 协调 |

### 与 OpenFeel 对比

| 维度 | Claude Code | OpenFeel |
|------|-------------|----------|
| 调度模型 | LLM 自由决策 | 固定流水线状态机 |
| 记忆 | Auto Memory 自动化经验积累 | dev_last.md 手动维护 |
| 指令层 | CLAUDE.md + Skills + Hooks 分层 | AGENTS.md + dev_core.md + kb/ 三层 |
| 碰撞点 | **借鉴 Auto Memory 模式**自动化经验沉淀；**借鉴 Skills 封装**标准化子流程；**借鉴 Hooks 机制**在关键 phase 前后注入自动化检查 | |
| 优劣势 | Claude Code 自主性强但不可预测；OpenFeel 可预测但需人工介入较多 | |

## 7. 其他值得关注的框架

### 7.1 Camel

- **核心**：角色扮演（Role-Playing）框架，两个 Agent 分别扮演 AI 用户和 AI 助手
- **特色**：Inception Prompt 生成任务描述，通过 `task_specify` 逐步细化
- **与 OpenFeel 关联**：角色扮演思路可用于 Review 阶段的对话式审查

### 7.2 AgentVerse

- **核心**：多 Agent 任务求解框架，支持自由协作和结构化的决策流程
- **特色**：支持 Planning / Discussion / Execution 三阶段；Recruiting 机制动态选择 Agent
- **与 OpenFeel 关联**：动态 Agent 选择机制值得参考

### 7.3 AutoGen v0.2（旧版）

- **核心**：对话驱动，UserProxyAgent + AssistantAgent 通过 chat 接口交互
- **特色**：`max_consecutive_auto_reply` 控制自动对话轮次
- **与 OpenFeel 关联**：对话轮次限制模式与 OpenFeel 的 phase 迭代次数有相似之处

## 8. 调度模型总览

| 框架 | 调度模型 | 调度粒度 | 去中心化程度 |
|------|----------|----------|:--:|
| **LangGraph** | 状态图（DAG） | 节点（函数） | 低（图定义集中） |
| **CrewAI** | Task 列表 + Process | Task | 低（Crew 集中调度） |
| **AutoGen** | Team 模式 + 消息驱动 | Agent 响应 | 中（Swarm 可去中心化） |
| **MetaGPT** | SOP 装配线 | 角色阶段 | 极低（固定顺序） |
| **OpenAI Agents SDK** | LLM 自主 or 代码控制 | Agent 调用 | 高（LLM 自主决策） |
| **Claude Code** | LLM 自由决策 | 工具调用 | 极高（无预设流程） |
| **OpenFeel** | 流水线状态机 | Phase | 低（Feel 集中调度） |

## 9. Loop / 反思机制总览

| 框架 | 反思机制 | 重试/错误处理 | 终止控制 |
|------|----------|---------------|----------|
| **LangGraph** | 条件边回到 LLM | 取决于节点实现 | 条件边判断 |
| **CrewAI** | reasoning 前置规划 | max_retry_limit=2 | max_iter=20, max_execution_time |
| **AutoGen** | Reflection(primary+critic) | CancellationToken 中止 | 组合终止条件（位或） |
| **MetaGPT** | 上下游文档审查 | 无显式重试 | 流水线结束 |
| **OpenAI Agents SDK** | evaluator while循环 | error handlers | 任务完成即结束 |
| **Claude Code** | 工具调用循环 + 自纠正 | 自动重试（上限未知） | 用户中断或任务完成 |
| **OpenFeel** | review_failed → exec_running | retry 计数 | phase 状态机 |

## 10. 可借鉴清单

按优先级从高到低排列，共 10 项可以引入 OpenFeel 的具体机制：

| # | 借鉴机制 | 来源框架 | 应用场景 | 实现方式 |
|:--:|----------|----------|----------|----------|
| 1 | **Handoff 标准原语** | AutoGen Swarm / OpenAI Agents SDK | Agent 间自主委派任务 | 在 Executor/Reviewer 间增加 Handoff 消息类型，允许 Agent 主动将子任务委派给专家 Agent |
| 2 | **组合终止条件** | AutoGen（位或运算符） | Phase 推进更灵活 | 允许多个终止条件组合（如：`APPROVE \| max_iter \| external_stop`） |
| 3 | **Checkpoint 自动保存** | CrewAI（CheckpointConfig） | 增强容错和跨会话恢复 | 在每个 phase 推进时自动保存完整状态快照，支持 `resume` 恢复 |
| 4 | **Auto Memory 自动化经验沉淀** | Claude Code | 减少人工维护 kb/ 的负担 | Agent 在关键操作后自动提取经验写入 dev_last.md，下次会话提醒用户确认归档 |
| 5 | **Guardrail 质量门控** | OpenAI Agents SDK | 增强阶段间质量检查 | 在 phase 转换（如 exec→review、review→test）前注入可配置的校验规则 |
| 6 | **Reflection 反思模式** | AutoGen（primary+critic） | 增强 Executor 自检能力 | 可选启用：Executor 产出后自动启动 Critic Agent 审查，迭代直到通过 |
| 7 | **SOP 编码到提示词** | MetaGPT | 强化 Agent prompt 的流程引导 | 将 flow.json 的阶段流程描述自动注入对应 Agent 的 system prompt |
| 8 | **Input Filter 历史控制** | OpenAI Agents SDK | 减少不必要上下文传递 | Handoff 时允许配置哪些历史消息对下游 Agent 可见，避免 prompt 膨胀 |
| 9 | **Sandbox 隔离执行** | OpenAI Agents SDK | 安全执行生成的代码 | 为 Executor 的代码执行步骤提供可选的隔离沙箱（Docker/临时目录） |
| 10 | **Skills 可复用工作流** | Claude Code | 标准化常见子流程 | 将常见操作（如创建阶段、归档等）封装为可加载的 Skill 模板 |

### 优先级建议

- **高优先级（v4.8 可实施）**：#1 Handoff 原语、#2 组合终止条件、#3 Checkpoint 自动保存
- **中优先级（v4.9 规划）**：#4 Auto Memory、#5 Guardrail、#6 Reflection 模式
- **低优先级（探索中）**：#7 SOP 编码、#8 Input Filter、#9 Sandbox、#10 Skills
