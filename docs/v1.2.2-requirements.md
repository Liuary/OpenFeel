# OpenFeel CLI 需求单（由 DSH 适配器提出）

> 来源：开发 `openfeel-dsh`（OpenFeel 的 DSH 适配版本）时逐条撞到的缺口。
> 适配器原则是**不重实现领域逻辑**，因此下列需求都指向「让 CLI 输出机器可读、
> 让决策权威留在 CLI」，而不是把逻辑搬进适配器。
>
> 基线版本：OpenFeel v1.2.1 ｜ 提出方：DSH 适配器 ｜ 优先级 P0 > P1 > P2

---

## 总述

适配器当前消费 18 个 `--json` 出口，其余命令只能回显人类文本。要让适配器
（以及任何未来的 harness 适配器）稳定工作，需要三件事：

1. **读命令全面 `--json`**——消除对中文人类输出的文本解析。
2. **决策下沉**——「下一步该谁做」目前只在 `feel` agent 提示词里，适配器不得不
   镜像一份 `PHASE_AGENT_MAP`；应由 CLI 单一权威输出。
3. **机器可读错误**——拒绝原因与稳定 `code` 应以结构化形式给出。

---

## P0 — 阻塞适配器质量

### P0-1 新增 `openfeel flow next [--json]`

**问题**：适配器需要「当前活跃阶段 + 相位 → 负责 Agent → 合法下一相位 → 建议命令」。
这个决策目前**只存在于 `src/core/templates-data/*/agents/feel.md` 的自然语言里**，
适配器只能镜像 `PHASE_AGENT_MAP`（`flow-manager.ts:2550` 的 `mapPhaseToAgent`），
一旦 OpenFeel 调整 Agent 编制就会静默漂移。

**建议输出**（`--json`）：

```json
{
  "schemaVersion": 1,
  "stage": "v1.2.1-stage-94",
  "phase": "plan_pending",
  "phaseLabel": "计划待定稿",
  "responsibleAgent": "openfeel-planner",
  "workflowMode": "full",
  "reviewTier": "full",
  "legalNextPhases": ["plan_review", "plan_passed"],
  "suggestedCommand": "openfeel flow advance --stage v1.2.1-stage-94 --to plan_review",
  "guards": ["auto_advance=disabled 时推进前须询问用户"],
  "blockingReviews": []
}
```

**收益**：`feel_next` 退化为一次 CLI 调用；agent 提示词与适配器都不再持有 Agent 编制。

---

### P0-2 读命令补齐 `--json`

以下命令目前只能拿到中文人类文本，适配器只能整段回显，无法结构化：

| 命令 | 适配器用途 | 现实影响 |
|---|---|---|
| `openfeel stage status [stageId]` | 阶段 `status.md` 字段读取 | 「谁负责 / 自动推进 / 工作流模式」只能正则 |
| `openfeel flow recover` | 跨会话恢复（阻塞原因、待处理任务） | 换会话后的第一条建议无法结构化 |
| `openfeel flow checkpoint list [stage]` | 快照列表 | 无法给用户「可回退到哪些点」的选择列表 |
| `openfeel knowledge search <q>` | 知识检索 | 检索结果无法逐条呈现/排序 |
| `openfeel knowledge list` / `index` / `dedup` | 知识库概览与去重 | 同上 |
| `openfeel config get` / `effective` | 配置与生效来源 | 只能回显文本 |
| `openfeel view list` | REV 条目列表 | 无法筛出 blocking 条目做门禁提示 |
| `openfeel plan scheme list [stage]` | 方案列表 | 无法枚举 op 与填充度 |
| `openfeel flow log --last <n>` | 审计链 | 无法结构化「最近发生了什么」 |
| `openfeel project overview` | 项目结构概览 | 同上 |

**建议**：与既有 `--json` 一致地采用 `{ "schemaVersion": 1, … }` 单文档契约。

### P0-3 机器可读的错误封装

**问题**：门禁拒绝目前是**本地化的人类 stderr 一行 + 退出码 1**（无堆栈）；
内部错误则先写运行日志再抛出、带堆栈。适配器只能靠「有无堆栈」+ 文本特征区分
「预期拒绝」与「内部故障」（`lib/adapters/cli.js` 的 `errorFromResult`），
语言切换（zh-CN / en）会直接破坏这套启发式。

**建议**：`--json` 模式下，失败也输出单文档：

```json
{
  "schemaVersion": 1,
  "error": {
    "code": "PHASE_TRANSITION_ILLEGAL",
    "kind": "refusal",
    "message": "…本地化文本…",
    "detail": { "from": "done", "to": "exec_running", "stage": "v1.2.1-stage-93" }
  }
}
```

稳定 `code` + `kind`（`refusal` / `internal`）后，适配器即可精确分类，
不再依赖文本或堆栈。**保留退出码语义**（0 / 1 / 2）作为冗余信号。

## P1 — 显著提升适配质量

### P1-1 `flow status --json` 补齐每阶段调度属性

当前 `stages[]` 只给 `{id, phase, status, deps, ops}`。适配器需要为**每个阶段**
计算「该阶段的模式与合法下一相位」，但 `workflow_mode` / `requirement_id`
只在 `flow mode --json` 里按**单阶段**给出，多阶段并行时需 N 次调用。

**建议**：`stages[]` 增加 `workflowMode`（解析后的生效值）、`requirementId`、
`reviewTier`，以及 `opsSummary`（`{total, byState}`）。适配器即可一次调用完成调度视图。

### P1-2 全局 `--project <path>`

`knowledge dedup` 已有 `--project`，但其余命令没有。适配器目前只能用**进程 `cwd`**
锚定项目（CLI 用 `process.cwd()` 解析项目根）。有了全局 `--project`，适配器就能
在一个进程内服务多项目会话，而不必每次 `cwd` 切换。

### P1-3 `req list --json` 附带关联阶段

`req list --json` 只给需求字段，不给关联阶段。适配器的需求概览要显示进度，
只能对每条需求再 `req show --json`（N+1 次调用）。

**建议**：`requirements[]` 增加 `linkedStages: [{id, phase}]` 与 `progress`（done/total）。

### P1-4 `flow archive` 显式暴露判据明细

`flow archive <version>` 的判据门（全阶段 done 且无 blocking open REV）失败时只给
人类文本。适配器想在**执行前**提示用户「还差哪几个阶段 / 哪几个 REV」。

**建议**：`flow archive <version> --dry-run --json` 输出
`{ eligible: false, unfinishedStages: [...], blockingReviews: [...] }`。
（`--dry-run` 已存在且照常校验判据，只差结构化输出。）

## P2 — 体验与一致性

### P2-1 `--json` 的稳定字段顺序与类型

现有 `--json` 已是单文档，但建议在文档中冻结：`schemaVersion` 恒为首键、
数组元素字段不增删、可选字段用 `null` 而非缺省键。适配器可做更严格的断言。

### P2-2 `flow phases --json` 的 `reviewTier` 语义说明

上游审查档位 spec 明确指出：`flow phases --json.reviewTier` 是**展示值**（按模式派生），
而 `flow advance` 未显式传 `--review-tier` 时生效档位是 **`full`（零裁剪）**。
二者语义不同却同名字段，适配器容易误用。

**建议**：把这两个概念显式区分命名，例如 `displayReviewTier` 与 `effectiveReviewTier`，
或在文档中固定说明。

### P2-3 `openfeel --version --json`

适配器启动自检解析 `--version` 的纯文本。`{"schemaVersion":1,"version":"1.2.1","node":"…"}`
会更好解析，也便于做版本兼容断言。

### P2-4 `openfeel archive <stage>`（阶段摘要归档）`--json`

与 `flow archive` 的 `--json` 对齐，返回生成的摘要路径与提取的知识条目。
