## 二、接口与签名变更（跨阶段契约，REV-001 / stage-51 事前约束）

### 2.1 T1：`syncCurrentOp(stageName)` —— `current.op` 生命周期**单一 owner**

> **跨阶段强制约束（stage-51 N4）**：`pipeline.current.op` 的生命周期有且仅有 `syncCurrentOp` 一个 owner；`advanceStagePhase` 与 `recordAttempt` **共用**该方法，**严禁各自实现**（禁双实现）。stage-51 复用本方法，不得另写路径。

**签名（`src/core/flow-manager.ts`，public）**：

```ts
/**
 * 同步 pipeline.current 到指定阶段中首个 pending / executing 的 op。
 * 单一 owner：被 advanceStagePhase 与 recordAttempt 共用，禁止各自实现。
 * @param stageName 目标阶段 ID（如 'v1.1.2-stage-50'）
 * @returns 同步后的 current 快照（便于调用方复用，不写盘）
 */
syncCurrentOp(stageName: string): { stage: string; op: string }
```

**语义（必须逐条实现）**：

1. 取 `this.data.stages[stageName]`；阶段不存在时**不改动** `pipeline.current`，直接返回当前快照 `{ stage: this.data.pipeline.current.stage, op: this.data.pipeline.current.op }`（防御，不抛错）。
2. `Object.entries(stage.ops ?? {})` 中取**首个** `state === 'pending' || state === 'executing'` 的 op。
3. 命中 → `this.data.pipeline.current = { stage: stageName, op: opId }`。
4. **未命中（阶段内 ops 全 done / ops 为空）→ `this.data.pipeline.current = { stage: stageName, op: '' }`（置空，绝不保留旧 op）** ← 本条即 T1 缺陷修复点（现状 `:1105` 回退为 `this.data.pipeline.current.op`，导致跨阶段悬空）。
5. **不触碰 `pipeline.phase`**（`phase` 归 `advanceStagePhase:1108-1112` 管理），**不触碰 `pipeline.retry`**，**不做 IO/不写盘**（由调用方 `save()`）。

**职责边界**：

| 调用方 | 调用时机 | 说明 |
|--------|----------|------|
| `advanceStagePhase`（`flow-manager.ts:1099-1106`） | 阶段 phase 推进、phase 字段已更新后 | 用 `this.syncCurrentOp(stageName)` 替换现有内联 `find` + 赋值块 |
| `recordAttempt`（`flow-manager.ts:1791-1845`） | `pass`→`op.state='done'` 之后；`fail` 且 `attempts < max_attempts`→`op.state='pending'` 之后 | 调用 `this.syncCurrentOp(stageIdOf(opId))`；stageId 由 `getOp(opId)` 或 `parseOpId(opId)?.stageId` 取得 |

> `recordAttempt` 现**完全未维护** `current.op`（实测 `:1791-1845` 只改 `op.state`/`op.attempts`），故 `pass` 后 `current.op` 会滞留于已 done 的 op —— 本 op 一并收口（同属 T1 悬空族）。

### 2.2 T8：`findSimilarEntries` 的 `basePath` 参数化（stage-51 N9 事前约束 / REV-001）

> **跨阶段强制约束（REV-001）**：本形态为 stage-51 `openfeel knowledge dedup --project <path>` 子命令的**注入契约**，两侧**禁各自实现路径解析**。

**签名（`src/utils/kb-dedup.ts`）**：

```ts
/**
 * 在指定分类中查找与新内容相似的现有条目。
 * @param target - 新待归档的内容文本
 * @param category - 知识库分类名（architecture | patterns | troubleshooting | setup）
 * @param basePath - 【可选】知识库根目录（即 `.openfeel/kb` 的**绝对路径**）。
 *                   缺省时在调用时刻解析 `resolve('.openfeel/kb')`（保持现行为）。
 *                   供 stage-51 `knowledge dedup --project <path>` 注入
 *                   `resolve(projectPath, '.openfeel/kb')` 复用。
 * @returns 相似度 > 0 的条目列表，按相似度降序排列
 */
export function findSimilarEntries(
  target: string,
  category: string,
  basePath?: string,
): SimilarityResult[]
```

**形态约束（写入本方案即生效，供 stage-51 N9 依赖）**：

1. `basePath` 语义 = **知识库根目录绝对路径**（`.openfeel/kb` 本身），**不是** projectPath；调用方负责拼接（即 `resolve(projectPath, '.openfeel/kb')`）。
2. 默认值**在调用时解析**（函数体内 `const base = basePath ?? resolve('.openfeel/kb')`），**不得**保留模块加载期的 `const KB_BASE_DIR`（T8 缺陷根因：`:34` 在模块加载时固化 cwd）。
3. 返回结构 `SimilarityResult[]` **不变**；`shouldUpdate`/`mergeEntry` 不含路径，**不改签名**。
4. 路径解析仅此一处；stage-51 侧**只允许传参**，不得再写 `resolve()` 逻辑（禁各自实现）。
