## 一、变更目标

修复「`flow attempt` 后 `current.op` 滞后」（反馈二问题 4）：`recordAttempt` 在 op 状态变更后**不接力维护** `pipeline.current`，导致跨会话恢复误判进度、执行方需手写偏差说明。本 op 使 `recordAttempt` **复用** stage-50 的 `syncCurrentOp`，与 `advanceStagePhase`（T1 已改）形成同一生命周期。

### N4-1（中）`recordAttempt` 在状态变更后同步 `current.op`

- **文件:行号**：`src/core/flow-manager.ts:1791-1859`（`recordAttempt(opId, result)`）；调用点参照 `advanceStagePhase` 的既有 `syncCurrentOp` 调用
- **现状**：`recordAttempt` 仅改 `op.attempts` / `op.state`（`:1804`/`:1807`/`:1826`）+ 写日志，**不触碰 `pipeline.current`** → pass 后 `current.op` 仍指向刚 done 的 op（滞后），跨阶段/跨会话恢复误判。
- **改后**：
  1. 在 `result === 'pass'` 分支（`op.state = 'done'` 赋值**之后**）调用：
     ```ts
     // 同步 current.op（唯一 owner：syncCurrentOp；禁自建指针逻辑）
     this.syncCurrentOp(<该 op 所属 stageId>);
     ```
  2. 在 `result === 'fail'` 且 `op.attempts < op.max_attempts` 分支（`op.state = 'pending'` 赋值**之后**）调用同一函数（使 fail-retry 时 `current.op` 稳定指向该 op）。
  3. `<该 op 所属 stageId>` 的取得：`this.getOp(opId)` 返回的 op 对象含 stage 归属，或 `this.parseOpId(opId)?.stageId`；**以实测可用者为准**，不得另建解析（复用既有 `parseOpId`）。
  4. **不得**修改 `syncCurrentOp` 内部实现（owner 属 stage-50）；本 op 仅新增调用点。
- **行为变更**：**是**（`current.op` 在 attempt 后即被纠正；不再滞后）。

### N4-2（低）`flow attempt` 输出可选同步提示

- **文件:行号**：`src/commands/flow.ts:675-702`（`flow attempt` action）
- **现状**：attempt 输出仅含 retry/replan 结论，用户无法确认 `current.op` 是否已同步。
- **改后**：在 attempt 成功后，读取 `mgr` 的 `pipeline.current` 并输出一行提示：
  - `flow.attempt.currentOpTmpl`：`当前指针：{stage}.{op}`（若 `op` 为空 → `{stage}.（无待执行 op）`）；
  - 该行为**只读**，不写盘；
  - **注意**：`flow current` 命令读取同一数据，需保证任务输出一致（§六 验收 4）。
- **行为变更**：**是（附加 stdout）**。

### N4-3（中）与 T1 的边界核对（不重复实施）

- **动作**：`rg -n "syncCurrentOp" src/core/flow-manager.ts` 定位 `advanceStagePhase` 的调用点（stage-50 已替换内联实现）。
- **改后**：**仅核对，不改**：确认 `:1099-1106` 的内联 `find(...) + pipeline.current = ...` 已被替换为 `this.syncCurrentOp(stageName)`；若**发现残留双实现** → 登记 REV 并回报（**不在本 op 就地删改**，避免与 stage-50 归档产物冲突）。
