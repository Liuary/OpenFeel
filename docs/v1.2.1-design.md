# v1.2.1 设计与分析文档

> **主题**：需求为核心（发布 / 接取）· 流水线优化提速 · 提示词瘦身 · 简化通用任务 · 三模式架构
> **版本**：v1.2.1（功能主题级，Z 递增）
> **日期**：2026-10-15
> **状态**：**设计草案** —— 本批次先文档、后规划、暂不落地。待 openfeel-planner 据此拆阶段。

## 0. 一句话

把 OpenFeel 从「一切皆流水线」改造为「**以需求为核心、非流水线优先、Agent 自治调度**」：以**需求发布 / 接取**为主工作模式、**流水线与版本解绑**（仅发布时推进版本号）；**执行者 / 探索者**作为**通用工作者**可被任意 Agent 按需调度；**鼓励拆分需求并行执行**；并据此**提速、瘦身提示词、简化通用任务、新增三模式**。

| 维度 | 大头 | 值 |

| # | 盲区 | 严重度 | 说明 |
|--:|------|:------:|------|

| 2 | subagent 调度开销 | 高 | task 派发的排队/启动延迟无处记录 |
| 3 | 人工确认 / 跨会话等待 | 高 | 占墙钟 96~99% |

| 5 | `metrics.json` 缺失 | 低 | `src/core/metrics.ts` 的 `recordRun` 是**死代码**，从未被调用 |
| 6 | CLI 日志无 `duration_ms` / 项目归属 / session 标识 | 中 | 且真实命令与测试用例调用混装 |

### 1.5 Claude 会话面（9 会话 / 8182 响应 / 217 subagent）

| 维度 | 结论 |
|------|------|
| token 结构 | prompt 合计 1.10B（非缓存 input 17.67M + **cache_read 1.085B**），output 仅 **9.48M（0.9%）**；缓存命中率 **98.4%**（主会话 99.5% / subagent 98.0%） |
| subagent 主体 | 占 prompt **76.4%** / 响应 **91.2%**（7459 条）；角色最大 `openfeel-schemer`（27.5%）；最贵模型 deepseek-flash |
| 最贵 session | 634M token / 4404 响应 / 47.6h / **$561**（次贵 $393，第三 $21.6） |
| 时间构成（主会话 56h） | **人不在/跨夜 40.9% + 等用户 32.6% + 等 subagent 22.9%**；模型响应仅 2.2%、工具真实执行仅 0.9%（29.5min） |
| 机器侧大头 | subagent 推理 **10.79h**（其中 **69.4% 是 thinking**）+ 工具 3.81h，且**基本串行**（时间轴重叠仅 8.3%） |
| **根因** | **上下文膨胀**：主会话每请求 p50 **34.7 万** / max **78.6 万** token（54.5k→785k，**14.4×，全程无 compact**）；工具结果注入 31.0M 字符（Read 均 9k/次 × 2271 次） |

> Claude 侧与 opencode 侧**互相印证**：贵在缓存重放 + subagent 主体；慢在人等待 + 串行 subagent。
> **新增关键轴：上下文膨胀** —— 主会话 token 14.4 倍增长且**从不 compact**，是 token 成本与推理延迟的隐性放大器。

### 1.6 结论

- **慢** = 串行 subagent 派发（73%）+ 多道审查关（reviewer 37%）+ 人工等待（17.5%~32.6%）+ 跨会话闲置（墙钟 96%+）。
- **贵** = 缓存重放（97%+ token 体量）+ reviewer 模型档位 + 子会话膨胀（84% cost）+ **上下文膨胀（主会话 14.4×、无 compact）**。
- **无关** = CLI 执行速度。
- **缺** = 可观测性（模型推理/op 级/子 agent 调度全盲）。

## 2. 核心原则（本次改造的基石）

### 2.1 非流水线优先

- **正式流水线只在「正式计划 / 发布需求」时推进**；日常任务**不推进版本号**、不开 stage、不走全链审计。
- 现状问题：一切皆流水线 → 小改也要开 stage、跑 planner→schemer→executor→reviewer→tester→archiver 六环，治理成本远超改动本身。

### 2.2 Agent 自治调度

- **Agent 不应被流水线锁定**，按需调度即可。
- **通用工作者 = 执行者 / 探索者**；**任意 Agent 均可直接调度它们干活**（**直接派发，不经 feel 转介**）——不再只有主会话能编排。
- 冲击一条现行硬规则：

| 现行规则 | 新语义 | 实现口径 |
|----------|--------|---------|
| 「subagent 不调用 Task」 | **任意 agent 可直接调度通用工作者**（executor / explorer） | 授予子 Agent **直接调度**通用工作者的能力（嵌套 Task / 专用调度通道，待设计） |
| 「仅主会话（Feel）编排」 | 编排能力下沉，不再是主会话特权 | 与上同一机制 |

> **与需求接取制度的区别（勿混淆）**：本条说的是**通用工作者**的**直接调度**（**允许各 Agent 直接操作**）。
> **需求接取制度**（§2.4 / §3）是**另一套**——只针对**需求本身**的发布 / 认领，因只有 feel 常驻而由 feel 中介。

### 2.3 需求为核心，流水线与版本解绑

- **需求（REQ）是主要工作单位**：openfeel 以**需求发布、接取**为主要工作模式。
- **版本号仅在涉及发布时推进**；日常需求不绑定版本。
- **流水线模式是需求级属性**，不是全局阶段：流水线与版本**解绑**，一切以需求为核心。

### 2.4 需求接取制度（只针对需求，feel 中介）

> 本条的"发布 / 接取"**只针对需求本身**；通用工作者的调度是**直接**的（见 §2.2），不受此约束。

- **语义**：**需求**的调度从"指派"改为「**发布需求 / 接取需求**」——feel **发布任务**，由 Agent **接取（认领）** 后执行。
- **触发链**：**所有 Agent 完成工作、需要流转时，通知 feel** → feel **发布对应任务** → **安排** Agent **接取**并执行。
- **本质**：因只有 feel 常驻，需求级调度由常驻的 feel 中介（机制层仍是 feel 调度）。

## 3. 需求工作流（需求为核心）

### 3.1 主流程

```text
用户发布需求
   → feel 拆分需求（需求转规划），发布子需求
   → 规划 agent 接取 → 执行 / 探索者等接取（按规模选流水线）
   → 某 Agent 完成工作、需要流转 → 【通知 feel】
   → feel 发布下一步任务 → 安排对应 Agent 接取
   → 循环至 验收 → 收口
   → 〔仅发布时〕推进版本号
```

### 3.2 角色职责

| 环节 | 主体 | 动作 |
|------|------|------|
| 发布 | 用户 | 提出原始需求 |
| 拆分 | feel | 拆解为可独立执行/并行的子需求并**发布**（需求转规划） |
| 通知 | 完成工作的 Agent | 工作完成、需要流转时**通知 feel**（Handoff） |
| 发布/编排 | **feel（常驻）** | 收到通知后**发布下一步任务**并**安排**接取 |
| 接取 | 各子 Agent | **认领（claim）** 被安排的任务 |
| 执行 | 执行者 / 探索者 等 | 按需求的流水线模式执行 |
| 验收 / 收口 | 对应 Agent | 完成并闭合需求 |

### 3.3 并行执行（提速）

- **鼓励拆分需求并行执行**：粒度足够独立的需求应拆开、并行接取执行，以缩短端到端——直接针对 §1「串行 subagent 占 73%」的根因。

### 3.4 与现有 `openfeel req` 的关系

- 复用并强化 v1.2.0 已建的 `openfeel req`（`draft→scheduled→in_progress→done` + `claim`/`link`/`advance`/`board`/`next`）。
- 强化点：**版本与需求解绑**、**接取制为默认调度**、**拆分为一等动作**。

## 4. 主题一：流水线优化提速

| 项 | 现状 | 设计方向 |
|----|------|----------|
| 审查关 | 每 stage **3 道**（plan/scheme/code），占 37% | 合并/抽样：小改免审、计划审查与方案审查合并、高风险才走满 3 道 |
| subagent 派发 | 串行，单次均 331s，累计 73% | 并行化独立子任务；缩短长子会话（避免 1000+ step） |
| 人工等待 | `question` 33.9h / 17.5% | 减少提问、批量确认、非阻塞式交互 |
| 会话卫生 | 大量子会话永不回收（wall 达 1094h） | 一次性调研子会话自动 archive |
| 归档 | archiver 中位 5.9min、0 离群（固定开销） | 评估轻量化（机械归档可下沉给事务官/脚本） |

## 5. 主题二：提示词瘦身

- **问题**：`feel.md` 达 **30KB**；各 agent / skill 提示词冗长，长上下文既贵又慢。
- **核心原则（新增）**：**现代模型能力已大幅提升** → 提示词**不必细化繁琐内容**。**必要的操作流程一律转化为 skill**；agent 提示词**只列出 skill 以便快速索引**（名称 + 一行用途）即可。
- **方向**：
  - **流程 → skill**：可复用操作流程下沉为 skill，提示词仅保留 **skill 索引**。
  - **约束 → 工具化**：能由 CLI 校验的规则不写进提示词（如 phase 合法性交 `flow health`）。
  - **按需加载 / 可插拔**：规则按需载入，职责段落按角色裁剪。
- **目标**：agent 提示词瘦身为「**索引壳**」，降低首轮 input 与维护成本。
- **上下文治理（源自 §1.5）**：主会话 token 全程 14.4× 无 compact → 引入**上下文压缩/裁剪策略**（定期 compact、工具结果截断、按需加载而非全量驻留）。

## 6. 主题三：简化通用任务（执行者 / 探索者双通用工作者）

### 5.1 背景

现状：通用任务（分析/脚本/批量/调研落盘）无框架原生承接者，外溢到 Claude 内置 `general` / `Explore` → **模型不可控、无框架纪律、不落审计**。

### 5.2 执行者 agent（读-写）

- 承接**任意 agent** 的活（不只主会话）。
- 既支持流水线 op 编码，也支持**通用模式**下的任意执行任务。
- 工具：`Bash, Read, Glob, Grep, Edit, Write, TodoWrite`。

### 5.3 探索者 agent（只读，新增）

- 专职**探索/调研**：读代码、查资料、定位问题、数据探查。
- 替代对内置 `Explore` 的依赖 → 模型可控、有框架纪律、可审计。
- 工具：`Bash, Read, Glob, Grep`（只读，无副作用）。
- 当前路由表「调研/探索 → general/explore」将改为「→ 探索者 agent」。

### 5.4 二者区分与重叠

| 维度 | 探索者（只读） | 执行者（读-写） |
|------|----------------|------------------|
| 副作用 | 无 | 有（改/造） |
| 并行性 | 可并行、便宜 | 需谨慎、串行性强 |
| 典型任务 | 调研、定位、分析 | 编码、批量改、跑脚本 |
| 重叠 | 都需读代码探索 → 由探索者承担前置探索，执行者专注「改」 | |

> **原则**：**先探后执行**——需要理解现状时先派探索者，产出结论后再派执行者落地。

### 5.5 与现有 agent 的关系

- `openfeel-utility`（事务官，机械操作）保留；探索者/执行者面向「需要推理」的通用任务。
- 三者边界：事务官（无推理的机械活）｜ 探索者（只读推理）｜ 执行者（读写推理）。

## 7. 主题四：三模式架构

| 模式 | 定位 | 触发 | 流水线 | 审查 | 版本号 |
|------|------|------|:------:|:----:|:------:|
| **规划模式** | 正式计划 / 发布 | 明确立项 / 发布需求 | 完整（plan→scheme→exec→review→test→archive） | 全量 | 推进 |
| **快速模式** | 中等改动、快线 | 有源码变更但非正式发布 | 快线（plan→计划审查→exec→代码审查→archive） | 单轮必经 | 可选 |
| **通用模式** | 日常通用任务 | 分析/调研/批量/小修 | **无流水线**，按需调度探索者/执行者 | 无（按需） | **不推进** |

- **模式选择**：由**需求规模**驱动——有一定规模的需求**默认走快速流水线**；**用户要求或设置**时走完整流水线（规划模式）；通用任务走通用模式。
- **流转**：通用模式可**升级**为快速/规划模式（当任务演变为正式变更）；反之不自动降级。
- **正交性**：通用模式 = 「非流水线、按需调度」的形态，是 §2 原则的直接落地。

## 8. 可观测性改造（供后续优化验证）

> 本批次的提速举措若无埋点则无法度量，故列为前置。

1. **接线 `recordRun`** —— 现成死代码，接上即获得结构化 run 级耗时。
2. **CLI 日志补 3 字段**：`duration_ms`（done 行落盘）、`project`（项目路径）、`session_id`（区分人工/自动化）。
3. **op 级 phase 埋点** —— 让 `exec_running` 可细分到 op。
4. **活跃/闲置语义标注** —— phase 转换时显式标注是否跨会话恢复，替代 >20min 启发式。
