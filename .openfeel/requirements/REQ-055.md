# REQ-055：需求/阶段正文必须写实：空壳需求禁止流转

> 本文件为需求正文（人读副本，由 openfeel req 机械铺骨架）。**机读权威恒为 `.openfeel/flow.json` 的 `requirements` 条目**；两者不一致时以 flow.json 为准。下方状态为创建时快照，不追写实时状态。

## 状态

in_progress（创建时快照；以 flow.json 为准）

## 摘要

Agent 为了通过「没有需求不得执行」的门禁，只建一个带标题的需求、正文留空（占位骨架），然后自由发挥。本仓 54 份需求正文中 48 份是骨架占位；CulaHub 同样。上下文一旦清空，后来者只剩一个标题可用，无法恢复意图。

根因是流程只校验「需求 ID 存在」而不校验内容：`req add` 只收标题，正文骨架机械铺开，且 `.openfeel/requirements/*.md` 被 guard 列为受保护路径、CLI 又没有更新正文的命令——正文在结构上不可能被写实。

## 目标与验收

**目标**：让「需求/阶段正文有实质内容」成为可校验的结构性前提，而不是口头要求。

- A1 夹具级：`req body` 能写/追加/替换指定小节，`--json` 形态稳定；`req add --problem/--goal/--acceptance/--plan` 直接落正文。
- A2 空壳正文 `advance --to scheduled|in_progress|done` 被拒（退出码 1 + 文案含 `req body` 修复指引 + 零写盘）；写实后放行；`--force` 放行且 `body_waiver` + 审计。
- A2c `claim` 不校验正文（认领≠开工，保证 `req add --claim` 原子成功）；正文门在 `in_progress` 首拦，general 与零阶段需求同样生效。
- A3 `lint req --json` 输出 `fill.emptyBody/emptyPlan`；`lint fill` 可枚举存量空壳（当前 54 份），恒 advisory 退出码 0。
- A4 阶段 `plan_passed`/`exec_running` 门要求 overview `## 目标` 写实。
- 既有 2400+ 用例不回归，`npm test` / `npm run build` 全绿。

## 问题

1. 空壳需求使「需求=工作单元」前提失效，阶段与计划失去锚点。
2. 没有正文写入通道：`writeRequirementBodySkeleton` 后无人能改，手改被 guard 拒绝。
3. 没有写实判据：占位符、空小节、零信息量都能一路推进到 done。
4. 存量脏数据不可见：没有任何 lint 报告空壳清单。

## 初步规划

1. `src/core/plan/filled.ts`：写实判据单点（占位符、空小节、最小信息量）。
2. `src/core/req/body-file.ts` + `src/commands/req.ts`：`req body` 原语与命令，`req add` 结构化字段。
3. 门禁：claim / 状态流转前置（硬门 + `--force` + 审计）。
4. `lint fill` 与 `lint req` 扩展，存量可见不阻塞。
5. 本阶段 6 份需求正文用新命令回填，作为首个验收样本。
