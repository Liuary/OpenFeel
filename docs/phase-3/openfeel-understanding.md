# 对 OpenFeel 的理解

> 基于 2026-06-27 全 Agent 功能测试的实际操作体验。

---

## 一、OpenFeel 是什么

OpenFeel 是一套**多 Agent 协作的软件开发流水线体系**，通过明确分工的 Agent 角色，将软件开发从需求到交付的全过程自动化。其核心理念是：

> **"每个 Agent 只做一件事，做到极致；Feel 作为总统领，负责全局调度。"**

它不是简单的代码生成工具，而是一个**有状态的、可审计的、支持故障恢复的开发流程引擎**。

## 二、架构分层

```
┌─────────────────────────────────────────────────────┐
│                    Feel (Orchestrator)               │
│              主力推理模型 (deepseek-v4-pro)           │
│         全局调度 · 意图理解 · 流水线管理 · 决策权      │
└──────────────┬──────────────┬───────────────────────┘
               │              │
    ┌──────────▼──────────┐   ┌──────────▼──────────┐
    │   计划层 (Planning)  │   │   执行层 (Execution) │
    │                     │   │                     │
    │  Planner ── 分期大纲  │   │  Executor ── 编码   │
    │  Schemer ── 操作方案  │   │  Reviewer ── 审查   │
    │                     │   │  Tester   ── 测试   │
    └─────────────────────┘   │  Archiver ── 归档   │
                               └─────────────────────┘
```

### 三层计划体系

```
roadmap/v1.0.md          ← 分期大纲（宏观：版本目标与里程碑）
  └── stages/stage-01/   ← 工作阶段（中观：阶段任务与依赖）
        └── ops/op-001   ← 操作方案（微观：Executor 逐行可执行）
```

## 三、六个 Agent 的职责与边界

### 1. Planner — 计划官
- **模型**：推理模型
- **输入**：用户需求描述
- **输出**：roadmap + stages + deps.yaml + status.md
- **不做**：不写代码、不定操作方案
- **关键行为**：理解需求 → 分解为阶段 → 声明依赖

### 2. Schemer — 方案官
- **模型**：推理模型
- **输入**：单个 stage 的任务清单
- **输出**：op-xxx.md（极细粒度，含完整代码和自测清单）
- **不做**：不写实际代码
- **关键行为**：将"做什么"翻译为"怎么做"

### 3. Executor — 执行官
- **模型**：快速模型（速度优先）
- **输入**：单个 op 方案文件
- **输出**：源代码文件 + 自测报告
- **不做**：不做决策、不扩缩范围
- **关键行为**：严格按方案逐行实现，自测不通过最多重试 3 次

### 4. Reviewer — 审查官
- **模型**：异种推理模型（避免同模型盲区）
- **输入**：op 方案 + 实际代码
- **输出**：REV 条目（pending/fixing/resolved/closed）
- **不做**：不修复代码
- **关键行为**：5 维度审查（正确性/规范性/安全性/完整性/一致性）

### 5. Feel Tester — 测试官
- **模型**：推理模型
- **输入**：代码 + 测试方案
- **输出**：测试报告 + BUG 条目（open/fixing/resolved/closed）
- **不做**：不修复 Bug
- **关键行为**：运行时验证，对比预期/实际行为，根因分析

### 6. Archiver — 归档官
- **模型**：推理模型
- **输入**：阶段全部产出（ops/reviews/tests）
- **输出**：知识库条目 + 公共审查摘要 + 公共日志
- **不做**：不干预开发流程
- **关键行为**：从阶段产出中提炼可复用知识

## 四、流水线与状态机

Flow.json 是流水线的中枢神经：

```
plan_pending → plan_passed → (scheme) → (code) → (review) → (test) → (archive) → done
```

Stage 级状态机更加精细：

```
planned → ready_for_code → coding → ready_for_review
    │                                    │
    ├── review_passed → ready_for_test   │
    │       │                            │
    │       ├── testing → done           │
    │       └── bug_found → bug_fixing ──┘
    │
    └── review_failed ──────────────────┘
```

### 手动 vs 自动模式

| 模式 | execution_mode | auto_advance | 行为 |
|------|---------------|--------------|------|
| 手动 | manual | disabled | 每步需用户/Feel 显式触发 |
| 半自动 | auto | disabled | Agent 自主推进，但阶段间需确认 |
| 全自动 | auto | enabled | AutoRunner 接管完整闭环 |

## 五、工作区设计

### 公共域（纳入版本管理）
```
.openfeel/
├── dev/          # 核心规则 + 进度状态
├── plan/         # 计划文件（plan.md, deps.yaml）
├── stages/       # 工作阶段（status.md + ops/）
├── roadmap/      # 分期大纲
├── kb/           # 知识库（架构/模式/排查/环境）
├── code_review/  # 公共审查摘要
├── bugs/         # 公共 Bug 摘要
├── log/          # 公共日志（团队级重要事件）
└── tmp/          # 临时文件
```

### 私域（不纳入版本管理）
```
.openfeel/users/{username}/
├── dev_last.md   # 上次操作状态 + 经验暂存
├── note/         # 个人笔记
├── log/          # 个人日志
├── code_review/  # 详细审查记录
├── bugs/         # 详细 Bug 记录
└── tmp/          # 个人临时文件
```

### 知识自动沉淀机制

```
会话经验 → dev_last.md 经验暂存
              │
    下次会话启动 → 用户确认
              │
    写入 kb/architecture.md / patterns.md / troubleshooting.md / setup.md
              │
    标记 [x] 已归档 → 更新 kb/index.md → 记录公共日志
```

## 六、模型选择策略

| Agent | 模型类型 | 原因 |
|-------|----------|------|
| Feel | 主力推理模型 | 全局调度与决策需要深度理解 |
| Planner | 推理模型 | 架构设计需要推理能力 |
| Schemer | 推理模型 | 方案拆解需要推理能力 |
| Executor | 快速模型 | 编码执行追求速度 |
| Reviewer | 异种推理模型 | 避免与主力模型同源导致的盲区 |
| Tester | 推理模型 | 测试分析需要推理能力 |
| Archiver | 推理模型 | 知识提炼需要推理能力 |

## 七、OpenFeel 的独到之处

1. **关注点分离到极致**：每个 Agent 只做一件事——Planner 定计划不管方案，Schemer 定方案不管代码，Executor 写代码不管审查，Reviewer 审查不管修复，Tester 测试不管修 Bug，Archiver 归档不管开发。

2. **方案驱动而非意图驱动**：Executor 不是根据"实现一个 Task 模型"意图编码，而是根据 op 文件中逐行写好的代码去复制实现。这消除了模型幻觉影响代码质量的风险。

3. **异种模型审查**：Reviewer 必须使用不同的模型系列进行交叉审查，避免同一模型"既当运动员又当裁判"。

4. **可审计的全链路**：每一步操作都有文件记录——计划、方案、审查条目、Bug 条目、日志——整个开发过程完全可追溯。

5. **知识持续沉淀**：不是一次性知识管理，而是通过 `dev_last.md` 经验暂存机制，让每次会话的经验都能在下次确认后进入知识库。

6. **级联配置覆盖**：`用户指令 > status.md > config.yaml defaults`，兼顾全局统一和局部灵活。

## 八、与 Cursor/Windsurf/Devin 的本质区别

| 维度 | 传统 AI 编程工具 | OpenFeel |
|------|-----------------|----------|
| 工作方式 | 单模型对话式编程 | 多 Agent 协作流水线 |
| 质量控制 | 依赖提示词技巧 | 方案→审查→测试三重保障 |
| 模型策略 | 单一模型 | 快慢结合 + 异种审查 |
| 可审计性 | 仅对话历史 | 完整文件级操作记录 |
| 知识管理 | 无/手动 | 自动沉淀 + 分层索引 |
| 大规模项目 | 上下文窗口瓶颈 | 分阶段独立 Agent 上下文 |
