## 逐条分析

### 1. 归档命名规范 (2026-06-27)

> 规则核心：`docs/` 归档文档命名格式 `yyyy-mm-dd-NNN-{category}-{title}.md`，全局递增序号，同步更新 `index.md`。

| 维度 | 判断 | 理由 |
|------|------|------|
| **CLI 内化** | 部分可行 | `openfeel archive` 命令可校验命名格式合规性，自动分配递增序号、更新 `index.md`。但命令尚未实现。 |
| **提示词内化** | 不适合 | 过于细节（序号规则、类别枚举），写入 AGENTS.md 会造成提示词膨胀。 |
| **保留动态规则** | ✅ 推荐 | 属于项目级文档规范，不涉及代码行为。规则细节可能随项目演进调整（新增类别、调整格式），动态规则灵活性最优。 |

**建议**：保持现状，待 `openfeel archive` 命令实现后，可将格式校验内化到命令中，但规则定义仍保留在 dev_core.md。

> 规则核心：todowrite / question / task / skill 四种工具的触发条件、使用要求、优先级表格。

| 维度 | 判断 | 理由 |
|------|------|------|
| **CLI 内化** | 不可行 | 工具调用是 LLM 行为决策，CLI 无法强制 Agent "遇到模糊需求时必须调用 question"。 |
| **提示词内化** | ✅ 推荐 | 核心原则已在 AGENTS.md 第 68-88 行「跨 Agent 工具使用约束」中引用。具体触发条件和反例应写入各 Agent 的 system prompt（`.opencode/agents/*.md` 或 `instructions/core.md`），直接注入 Agent 上下文。 |

**建议**：

### 5. Feel 归档后版本控制收尾 (2026-08-07)

> 规则核心：归档阶段完成后，Feel 负责 `git add -A && git commit -m "chore: v{版本} 归档 — {简述}"`，禁止让归档产物悬空未提交。

| 维度 | 判断 | 理由 |
|------|------|------|
| **CLI 内化** | ✅ **最佳候选** | 规则描述的是机械性操作（git add + git commit），无歧义、无需人工决策。可在 `openfeel flow advance --to done` 时自动触发：读取版本号和归档简述 → 执行 git 操作 → 失败时回滚并报告。 |
| **提示词内化** | 不适合 | 机械操作，靠 Agent prompt 约束不可靠（Agent 可能遗漏）。CLI 强制执行才是正确做法。 |
| **保留动态规则** | 过渡期保留 | CLI 实现前保留为行为约束，实现后标记 `[-]`。 |

**实现思路**：
```
openfeel flow advance --to done
  ├── 1. 检查当前 phase == archiving
  ├── 2. 调用 Archiver 完成归档产物
  ├── 3. 读取 flow.json 获取版本号
  ├── 4. git add -A
  ├── 5. git commit -m "chore: v{version} 归档 — {简述}"
  └── 6. 更新 phase → done
```

**建议**：这是本次分析中**内化收益最高的规则**。实现后可将「归档后忘提交」的人为失误概率降为零。
