# REQ-017：1.5.6：需求正文命令名校验（lint req：剥 openfeel 前缀 + 真实命令树解析 + 抑制标记）

> 本文件为需求正文（人读副本，由 openfeel req 机械铺骨架）。**机读权威恒为 `.openfeel/flow.json` 的 `requirements` 条目**；两者不一致时以 flow.json 为准。下方状态为创建时快照，不追写实时状态。

## 状态

draft（创建时快照；以 flow.json 为准）

## 摘要

REQ-015 暴露的流程漏洞：写需求正文的人（含 Agent）凭意图写命令名，不与 CLI 注册面核对，导致 `stage deps` / `stage reset` / `op create` / `archive create` 这类**根本不存在**的命令进了需求，到执行期才被发现，靠人工补一张差异表兜底——下次还会犯。本需求把「命令名存在性」变成机器可校验的事实：新增 `openfeel lint req`。

## 目标与验收

**目标 1：新增 `lint req`**

- 与 `lint i18n` / `lint kb` 并列（`src/commands/lint.ts`）；`--json` 输出沿用既有形状 `{schemaVersion, target, ok, issues:[{path,message}]}`，`target='req'`。
- 扫描 `.openfeel/requirements/*.md` 全部正文，不区分需求状态。

**目标 2：判定规则（已用 16 份真实正文实测，零误报）**

1. **候选**：行内反引号 span，1–4 个 token，每 token 匹配 `^[a-z][a-z0-9-]*$`。含点 / 下划线 / 斜杠 / 空格以外字符的一律不入候选（天然排除 `flow.json`、`plan_review`、`stage-114`、`op-001`）。
2. **剥前缀**：首 token 为 `openfeel` 时剥掉再解析（`openfeel config get` 属合法写法）。
3. **解析**：从 `program.commands`（`src/cli/index.ts` 已导出 `program`）构建**真实命令树**，逐 token 贪心下降，每个 token 必须是上一级的已注册子命令。**不得维护第二份命令清单**（会与注册面漂移）。
4. **A 类（计入失败）**：首 token 是根命令，但逐词解析在某处断掉 → issue。
5. **B 类（低置信，不改变退出码）**：首 token 不是根命令，但 span ≥2 token 且**尾 token 是任一已注册命令名** → issue，message 标注「疑似未知命令组」。
6. **解析到已注册命令即通过**：`plan scheme`、`stage`、`flow review` 这类「停在父命令」的写法合法，不得因「还有更深子命令」而报错。

**目标 3：抑制机制（两档）**

- 行内：`<!-- lint-req:ignore -->` → 跳过该行全部候选。
- 区间：`<!-- lint-req:ignore-start -->` … `<!-- lint-req:ignore-end -->` → 跳过区间内全部候选。
- 用途：正文按定义需要引用「错误命令名」的场合。REQ-015 的差异表已按区间标记自举。

**目标 4：退出码**

- 有 A 类 → exit 1；仅 B 类或无 issue → exit 0（与 `lint i18n` / `lint kb` 的「发现问题非 0」口径一致）。

**目标 5：契约计数与文档**

- `--json` 注册选项 **41 → 42**；成功出口 **40 → 41**（实测当前 41 / 40）。
- `docs/commands.md` 的「43 个注册选项」口径 = 41 + `chore --end` / `--status` 两个非 json 选项 → 更新为 **44**；成功出口 40 → 41。
- `docs/json-contract.md` 新增出口 #41 小节与 §5 表项；`lint` 命令描述追加 req。
- i18n 新增 `help.lint.req` / `help.lint.req.json`（zh-CN / en **双表成对**），`lint i18n` 键数 1048 → +2。
- cli-usage SKILL 快照 + `npm run build` 双生成物（`template-loader.ts` / `update.ts`，**禁手改**）。

**实测基线（本次已跑，供测试对齐）**

- `--json` 注册数 = **41**（`lint i18n` / `lint kb` 各计 1）。
- 16 份需求正文：候选 span **34** 个；A 类 **4** 个（`archive create` / `stage deps` / `stage reset` / `stage remove`）、B 类 **7** 个（剥 `openfeel` 前缀后 5 个解析成功，余 `op create` / `op publish` 为真缺陷）——全部落在 REQ-015 的差异表，已用区间抑制覆盖。

**验收**

- `openfeel lint req` 对现有 16 份正文 exit 0；临时插入 `` `stage deps` `` → exit 1，message 含命令与断点位置。
- `--json` 键集/键序与其他 lint 子命令一致，`target='req'`。
- 抑制：行内标记、区间标记各一条用例。
- 零误报：`plan scheme` / `stage` / `flow review` / `openfeel config get` 均不报。
- 全量测试 / tsc / lint i18n / lint kb / dsh / build ×2 全绿；**不新增错误码**（复用 exit 1）。

**不做**

- 不扫描 `docs/**`、`flow-archive/**`、计划文档——它们天然引用历史/错误命令名，且不是需求契约。
- 不改 `req add` 行为（正文是机械铺骨架 + 人工编辑，问题不在写入时机，且改 `req add` 会动既有输出契约）。
- 不做近似纠错建议（只报「不存在」，避免误导到错误的命令）。
