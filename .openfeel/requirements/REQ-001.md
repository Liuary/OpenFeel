## 摘要

本需求单来源于 **OpenFeel-DSH 适配器**（OpenFeel 的 DSH 适配版本）在开发过程中逐条撞到的 CLI 缺口。适配器原则为「不重实现领域逻辑」，因此需求方向统一为：**让 CLI 输出机器可读、让决策权威留在 CLI**，而非把逻辑搬进适配器。

- 基线版本：**OpenFeel v1.2.1**
- 目标主题（三项）：
  1. **CLI 成为唯一决策权威**——「下一步该谁做」不再只存在于 `feel` agent 提示词与适配器镜像的 `PHASE_AGENT_MAP` 中，改由 CLI 单一权威输出。
  2. **读命令全面 `--json`**——消除对中文人类输出的文本解析，所有读命令采用 `{ "schemaVersion": 1, … }` 单文档契约。
  3. **机器可读错误**——拒绝原因以稳定 `code` + `kind`（`refusal` / `internal`）结构化给出，同时保留退出码语义。
- 需求规模：共 **11 项**，其中 **P0 × 3**（阻塞适配器质量）、**P1 × 4**（显著提升适配质量）、**P2 × 4**（体验与一致性）。

## 目标与验收

### P0 — 阻塞适配器质量

#### P0-1 新增 `openfeel flow next [--json]`

**目标**：由 CLI 单点输出「当前活跃阶段 + 相位 → 负责 Agent → 合法下一相位 → 建议命令」，消除适配器对 `PHASE_AGENT_MAP` / `mapPhaseToAgent` 的镜像依赖，避免 Agent 编制调整时的静默漂移。

**验收判据**：

- `openfeel flow next --json` 输出单文档，`schemaVersion: 1`，且包含字段：`stage`、`phase`、`phaseLabel`、`responsibleAgent`、`workflowMode`、`reviewTier`、`legalNextPhases`（数组）、`suggestedCommand`、`guards`（数组）、`blockingReviews`（数组）。
- `responsibleAgent` 取值与当前 Agent 编制一致；`legalNextPhases` 与 `flow advance` 实际接受的相位集合一致（非法相位不在其中）。
- `suggestedCommand` 为可直接执行的完整命令串，且在不修改状态的前提下与实际可推进相位匹配。
- 无参数可调用；人类输出模式下仍给出可读文本（非破坏性）。

#### P0-2 读命令补齐 `--json`

**目标**：以下 10 组读命令目前只能产出中文人类文本，需统一补齐 `{ "schemaVersion": 1, … }` 单文档输出，与既有 `--json` 出口契约保持一致。

| 命令 | 适配器用途 |
|---|---|
| `openfeel stage status [stageId]` | 读取阶段 `status.md` 字段（负责 Agent / 自动推进 / 工作流模式） |
| `openfeel flow recover` | 跨会话恢复（阻塞原因、待处理任务） |
| `openfeel flow checkpoint list [stage]` | 快照列表（可回退点枚举） |
| `openfeel knowledge search <q>` | 知识检索结果的结构化呈现/排序 |
| `openfeel knowledge list` / `index` / `dedup` | 知识库概览与去重结果 |
| `openfeel config get` / `effective` | 配置值与生效来源 |
| `openfeel view list` | REV 条目列表（含 blocking 筛选所需字段） |
| `openfeel plan scheme list [stage]` | 方案列表（op 枚举与填充度） |
| `openfeel flow log --last <n>` | 审计链（最近事件结构化） |
| `openfeel project overview` | 项目结构概览 |

**验收判据**：

- 上述每条命令加 `--json` 后均输出 `{ "schemaVersion": 1, … }` 单文档，stdout 无人类文本混入。
- 各命令的关键人类文本字段均有对应结构化字段（如 `stage status --json` 含负责 Agent / 自动推进 / 工作流模式字段；`view list --json` 含可判定 blocking 的字段）。
- 不加 `--json` 时人类输出保持现状（向后兼容）。

#### P0-3 机器可读的错误封装

**目标**：`--json` 模式下失败同样输出单文档，携带稳定 `error.code` 与 `error.kind`，使适配器不再依赖「有无堆栈」或文本特征（且不受 zh-CN / en 语言切换影响）。

**验收判据**：

- `--json` 模式下失败输出形如：

  ```json
  {
    "schemaVersion": 1,
    "error": {
      "code": "PHASE_TRANSITION_ILLEGAL",
      "kind": "refusal",
      "message": "…本地化文本…",
      "detail": { "from": "done", "to": "exec_running", "stage": "v1.2.1-stage-93" }
    }
  }
  ```

- `error.kind` 取值限定为 `refusal`（预期拒绝，如门禁/相位非法）或 `internal`（内部故障）。
- `error.code` 稳定且语言无关；同类拒绝在不同语言下 code 一致。
- **保留退出码语义**（0 成功 / 1 预期拒绝 / 2 内部错误或用法错误，按既有约定）作为冗余信号。
- 非 `--json` 模式的行为不变。

### P1 — 显著提升适配质量

#### P1-1 `flow status --json` 补齐每阶段调度属性

**目标**：`stages[]` 目前只有 `{id, phase, status, deps, ops}`，适配器需 N 次 `flow mode --json` 才能拼出多阶段调度视图；改为在一次调用中给出。

**验收判据**：

- `stages[]` 每个元素新增 `workflowMode`（解析后的生效值）、`requirementId`、`reviewTier`、`opsSummary`（`{ total, byState }`）。
- 已有字段不增删、不改变类型；新增字段在无值时按统一约定给出 `null`（或空对象 `{total:0,byState:{}}`）。
- 单次 `flow status --json` 即可为每个阶段计算「模式与合法下一相位」所需信息。

#### P1-2 全局 `--project <path>`

**目标**：除 `knowledge dedup` 外，其余命令支持全局 `--project <path>` 锚定项目根，使适配器可在单进程内服务多项目会话，无需切换 `cwd`。

**验收判据**：

- 全局 `--project <path>` 对所有命令生效，等效于以该路径为 `cwd` 解析项目根。
- 命令级 `--project`（如 `knowledge dedup`）与全局参数不冲突，语义一致。
- 路径不存在或非法时给出明确错误（`--json` 下走 P0-3 错误封装）。
- 不传 `--project` 时仍按 `process.cwd()` 解析（向后兼容）。

#### P1-3 `req list --json` 附带关联阶段

**目标**：消除适配器对每条需求再调 `req show --json` 的 N+1 问题。

**验收判据**：

- `requirements[]` 每个元素新增 `linkedStages: [{ id, phase }]` 与 `progress`（`done/total`，两者均为数值）。
- 已有需求字段保持不变。
- `linkedStages` 与 flow.json 中 `stages[*].requirement_id` 的关联关系一致。
- 无关联阶段时给出空数组与 `progress: "0/0"`（或约定的一致表示）。

#### P1-4 `flow archive` 显式暴露判据明细

**目标**：判据门失败时，适配器需在执行前提示「还差哪几个阶段 / 哪几个 REV」，而非解析人类文本。

**验收判据**：

- `flow archive <version> --dry-run --json` 输出 `{ eligible: false, unfinishedStages: [...], blockingReviews: [...] }`。
- `eligible` 为 `true` 时 `unfinishedStages` 与 `blockingReviews` 为空数组。
- `--dry-run` 保持既有「只校验不执行」语义，不产生任何写入。
- 判据口径与既有 `flow archive` 门禁一致（全阶段 done 且无 blocking open REV）。

### P2 — 体验与一致性

#### P2-1 `--json` 的稳定字段顺序与类型

**目标**：冻结 `--json` 文档的字段稳定性，供适配器做严格断言。

**验收判据**：

- 文档中明确规定：`schemaVersion` 恒为首键；数组元素字段不增删；可选字段用 `null` 而非省略键。
- 既有 18 个 `--json` 出口在需要处补齐 `null` 占位，保持契约一致。

#### P2-2 `flow phases --json` 的 `reviewTier` 语义说明

**目标**：区分「展示值」与「生效值」两个同名字段语义，避免适配器误用（`flow phases --json.reviewTier` 为按模式派生的展示值；`flow advance` 未显式传 `--review-tier` 时生效档位为 `full`，即零裁剪）。

**验收判据**：

- 采用显式区分命名（如 `displayReviewTier` / `effectiveReviewTier`），或在文档与 `--json` 输出中固定说明二者语义。
- 说明须可被适配器程序化区分，不依赖隐含约定。
- 改动遵守向后兼容策略（旧字段保留或按冻结规则声明变更）。

#### P2-3 `openfeel --version --json`

**目标**：适配器启动自检不再解析纯文本版本号。

**验收判据**：

- `openfeel --version --json` 输出 `{ "schemaVersion": 1, "version": "…", "node": "…" }` 单文档。
- `version` 与包版本一致；`node` 为当前 Node 运行时版本。
- 不带 `--json` 时保持原有纯文本输出（向后兼容）。

#### P2-4 `openfeel archive <stage>`（阶段摘要归档）`--json`

**目标**：与 `flow archive` 的 `--json` 对齐，供适配器结构化消费阶段归档结果。

**验收判据**：

- `openfeel archive <stage> --json` 输出单文档，包含生成的摘要路径与提取的知识条目。
- 字段命名与既有 `flow archive` 系 `--json` 出口风格一致。
- 人类输出模式不变（向后兼容）。

### 通用验收

- **向后兼容**：所有新增 `--json` 能力均以开关形式附加；不加 `--json` 时既有人类输出（含 zh-CN / en）保持现状。
- **无第三方依赖**：实现不引入新的运行时第三方依赖。
- **单文档契约**：所有 `--json` 输出均为 `{ "schemaVersion": 1, … }` 单文档（stdout 不混入额外文本/多文档）。
- **零破坏**：适配器已消费的 18 个 `--json` 出口（`flow status` / `flow current` / `flow overview` / `flow phases` / `flow mode` / `flow metrics` / `flow ops list` / `flow health` / `flow archive list` / `flow archive show` / `flow archive <version>` / `req list` / `req show` / `req board` / `req next` / `req split` / `instructions`）字段零破坏，仅允许按 P2-1 规则补齐 `null` 占位。
