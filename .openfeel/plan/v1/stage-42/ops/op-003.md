## 目标（含反馈条目）

修正 `advanceStagePhase` 中恒置 `pipeline.phase='active'` 的缺陷：改为「**所有 stage 均 done → `done`，否则 `active`**」（全量 done 判定）。**不做** `pipeline.current` 回退。

**对应反馈**：`docs/phase-5/06-openfeel-tooling-feedback.md` 问题 #6（中）「`flow status` 全局 phase 在阶段 done 后仍显示 active」（**经核实**：反馈中「current 不回退」不属实；真缺陷 = `pipeline.phase` 恒 active）。
**对应决策**：P3（全量 done 判定）+ P3a（**不实施** current 回退）。

> 参见 kb/troubleshooting.md #autoRepairInconsistency 干扰组合条件推进路径（修改 `advanceStagePhase` 须避免再次干扰组合条件推进）、kb/patterns.md #ValidationResult errors/warnings 分离。

## 关键设计决策

1. **判定式（写死，含空集守卫）**：
   ```ts
   const allDone = Object.keys(this.data.stages).length > 0
     && Object.values(this.data.stages).every((s) => s.phase === 'done');
   this.data.pipeline.phase = (allDone ? 'done' : 'active') as MetaPhase;
   ```
   - **空集守卫理由**：`[].every(...) === true`（vacuous truth），若无 stage 会误置 `done`。实际 `advanceStagePhase` 要求目标 stage 存在（否则抛出），故数据必有 ≥1 stage；守卫为防御性。
   - 判定时 `stage.phase` **已在 `:1052` 被赋为 `targetPhase`**，故「推进最后一个 stage 到 done」时该 stage 已计入 `done`，判定正确。
2. **不改 `current` 逻辑（P3a）**：`:1072-1075` 保持——`advanceStagePhase` 无条件将 `current` 设为被推进阶段（设计行为，非缺陷）。
3. **不改返回值语义**：`true`（归档标记）仅在 `targetPhase==='done' && prevStatus!=='done'` 时返回，与 `pipeline.phase` 无关。
4. **不迁移历史数据**（见「兼容策略」）。

## 兼容策略（是否需数据迁移 → **明确结论：不需要**）

1. **`pipeline.phase` 是派生宏观状态**：其真值可由 `stages[].phase` 重新推导；历史 `flow.json` 中「全 done 但 phase=active」的残留（本项目当前不存在——实测 46 阶段未全 done）仅是**显示层早一层**，不造成状态机错误（推进校验基于 `stage.phase`，与 `pipeline.phase` 无关）。
2. **自愈**：任一次 `advanceStagePhase` 即按新判定重算，无需一次性迁移。
3. **成本/风险**：迁移需改写 46 阶段 + 431+ 条日志所在的大文件（**以实施时实盘为准**），收益仅为瞬间显示一致，且会污染审计链（本版本另在 op-004 补审计日志，不宜再动历史）。计划已裁定「不迁移历史数据」。
4. **`current` 不悬空**：outs of scope（P3a）；current 悬空是 stage-41 op-003 `removeStage` 的兜底职责，与本 op 无关。
