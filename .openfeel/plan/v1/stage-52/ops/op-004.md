## 一、变更目标

## 二、B5 子项清单

### B5-1（中）`findPhasePath(stageName, to)`（core，BFS 唯一路径）

- **文件:行号**：`src/core/flow-manager.ts`（新增方法；参照既有 `getValidTargets():1555-1566`（实测单步）、`getPipelineTransitions()`（stage-50 起）与 `hasTransition` 语义）
- **现状**：`getValidTargets` 仅返回**单步**可达目标；`advance` 用 `hasTransition` **单步判定**（`src/commands/flow.ts:629-646`）→ 跨相推进需人工多次调用。
- **改后**：
  ```ts
  /** 路径查找结果 */
  export interface PhasePathResult {
    /** 唯一可达路径（含起点后的逐跳目标）；不存在/多义时为 [] */
    path: string[];
    /** 结果原因 */
    reason: 'ok' | 'already-at-target' | 'no-path' | 'ambiguous' | 'depth-exceeded';
  }

  /**
   * 在运行时 transitions 上求 stageName 当前 phase → to 的**唯一**可达路径（BFS，深度上限 8）。
   * @param stageName 阶段 ID
   * @param to 目标 phase
   * @returns 路径与原因（多义/无路径须可区分，供命令层报错）
   */
  findPhasePath(stageName: string, to: string): PhasePathResult
  ```
  实现要点：
  1. 起点 = 该阶段当前 `phase`；转移表用**运行时** `getPipelineTransitions()`（含自定义 pipeline.yaml）；
  2. BFS 深度上限 **8**（超出 → `depth-exceeded`，按「拒绝」处理）；
  3. **唯一路径判定**：若在最短深度上存在**多条**不同路径 → `ambiguous`（**拒绝**，不猜测）；
  4. `to` 非法（不在合法 phase 集合/无任何入边）→ `no-path`；已在 `to` → `already-at-target`（命令层按 no-op 成功处理）；
  5. **纯只读**（不写盘、不改内存）。

### B5-2（中）`advance --to` 自动逐步（命令层）

- **文件:行号**：`src/commands/flow.ts:561`（`.command('advance')`）、`:629-646`（单步 `hasTransition` 判定）、`:690-695`（`--dry-run`）
- **现状**：仅单步；非法跳转 `exit 1`；`--dry-run` 仅打印单步。
- **改后**：
  1. **保留拒绝语义**：`findPhasePath` 返回 `no-path`/`ambiguous`/`depth-exceeded` → **`exit 1`** + 列出**当前可达目标**（复用既有「可达目标」输出，`flow.ts:641-676` 附近）——与现状一致，反馈亦称「拒绝是正确的」；
  2. **唯一路径** → **逐步调用** `mgr.advanceStagePhase(stageName, next)`（每步保留既有校验/日志/checkpoint 语义），逐步 `save()`（或按既有 save 时机）；
  3. **`--dry-run`**：打印**完整路径** `A → B → C` 且**不写盘**（内存/文件均不变）；
  4. **未提供 `--to` 的既有调用行为不变**（单步路径）；
  5. **每步日志**：各写一条 `advance_stage_phase`（可读性优于合并；与既有单步日志同构）；
  6. **失败处理**：中途某步抛错 → **不回滚**已完成步（A3）→ 输出「已完成到 X，失败于 Y，剩余路径 Z」+ `exit 1`。

### B5-3（中，**REV-52-001**）`assertNoBlockingOpenRev` 抽取 + 多步循环复检

- **文件:行号**：`src/commands/flow.ts:658-680`（现有 REV 闭环检查，实测位于命令层且**仅 `--to done` 时**生效，过滤条件 `r.blocking !== false && r.status === 'open'`（`:664-666`））
- **现状**：REV 阻塞检查只在**入口**且仅 `--to done`；多步路径若中途产生 blocking → 一次跑到底不会复查。
- **改后**：
  1. **抽取**为本地函数：
     ```ts
     /**
      * 断言不存在阻塞中的 open REV（REV 闭环兜底）。
      * 命中 → 返回命中的 REV 列表（调用方决定退出码与文案）；无命中 → 空数组。
      * 单步 advance 与多步循环共用（禁止双实现）。
      */
     function assertNoBlockingOpenRev(mgr: FlowManager, stage: string | undefined, lang: string): ReviewItem[]
     ```
  2. **调用点**：
     - **单步路径**：保持既有「`--to done` 时检查」行为（**不变**）；
     - **多步路径**：**每步完成后调用**（至少**进入 `done` 前**一次）→ 命中即**停止推进并报告剩余路径**（`exit 1`）；
  3. **等价论证（写入代码注释）**：`addAutoFixReview`（`flow-manager.ts:2145`）在 `addReview` 前**强制 `item.status = 'resolved'`**（`:2172`）→ **恒不满足** `status === 'open'`，故不可能成为 blocking open；且 `addAutoFixReview` **仅由** `addReviewEntry`（`src/core/view/entry.ts:168`）调用，**`advance` 路径不创建任何 review**（实测）。**故本复检为防御性加固**（防未来语义漂移）。
  4. **测试局限（诚实声明）**：「中间步注入 blocking REV」在**当前实现下不可构造**（advance 不创建 review，autoFix 恒 resolved）→ 以「**存量 blocking 拦截**」+「**等价性单测**」组合覆盖，并在用例注释中说明该局限。
