## REV-001: stage-02 对 stage-01 的 hard 依赖不成立

- **状态**：pending
- **优先级**：high
- **阻塞**：true
- **提出人**：Reviewer
- **提出时间**：2026-07-09 16:00

### 问题描述

计划第 60-62 行声明 stage-02 对 stage-01 存在 hard 依赖，理由是「stage-02 修改的 feel/executor 模板文件由 stage-01 创建」。但这一依赖关系分析有误：

1. **stage-02 的三个任务中，只有 op-001 和 op-002 涉及模板文件修改**，且修改的是 `src/core/templates-data/agents/zh-CN/feel.md` 和 `executor.md`。但 stage-01 的 op-002 才创建这些文件——如果 stage-01 未完成，stage-02 确实无法修改尚不存在的文件。

2. **然而，op-003（REV-004 修复）修改的是 `src/commands/project.ts`，与模板文件化完全无关**。当前代码（project.ts 第 130-133 行）硬编码了 `CLI 入口: src/cli/index.ts` 等路径，不存在目录时直接输出错误路径。这个修复完全可以在现有代码基础上完成，不需要等待模板重构。

3. **更重要的是**：stage-02 对 feel.md/executor.md 的修改，本质上是对 **Agent prompt 内容** 的修改。在当前架构中，这些内容以 `AGENT_DEFINITIONS` 常量内联在 `update.ts` 中。stage-02 完全可以直接修改 `update.ts` 中的内联常量来强化日志纪律和自测报告要求——**不需要先完成模板文件化重构**。

4. **依赖链重组建议**：
   - stage-02 (op-003) 可独立执行，无任何依赖
   - stage-02 (op-001, op-002) 修改的是 Agent prompt 内容，在当前架构下修改 `update.ts` 内联常量即可，与模板文件化无关
   - 如果坚持 stage-02 在模板文件上修改，那依赖确实存在，但这是**人为制造的依赖**而非技术必然

5. **实际影响**：硬依赖导致三阶段严格串行，总周期拉长。如果 stage-02 能与 stage-01 并行或至少 op-003 独立先行，可以显著缩短整体交付时间。

### 建议

将 stage-02 拆分为两部分：
- **stage-02a**（可与 stage-01 并行）：REV-004 修复（project.ts）
- **stage-02b**（依赖 stage-01）：feel.md 和 executor.md 的纪律强化

或者，stage-02 的 feel.md/executor.md 修改直接在当前 `update.ts` 内联常量上完成，消除对 stage-01 的依赖，使 stage-01 和 stage-02 可并行。

## REV-002: 模板加载方式选型应在 plan 阶段确定方向

- **状态**：pending
- **优先级**：high
- **阻塞**：true
- **提出人**：Reviewer
- **提出时间**：2026-07-09 16:05

### 问题描述

计划第 127-131 行将「模板加载方式选型」（运行时 fs.readFileSync vs 构建时内联）标记为「由 Schemer 在方案阶段确认最终选型」。这是不恰当的：

1. **两种方案对项目架构影响截然不同**：
   - **运行时方案**：需要确保 `package.json` 的 `files` 字段包含 `src/core/templates-data/`；需要处理 ESM/CJS 环境下的路径解析差异（`import.meta.url` vs `__dirname`）；影响 npm 包分发体积和结构
   - **构建时方案**：需要额外的构建步骤；模板变更需重新编译；但打包后无运行时文件依赖

2. **当前 `package.json` 的 `files` 字段仅包含 `["dist", "bin", "schemas"]`**，不包含 `src/`。如果选择运行时方案，npm 包需要包含 `src/core/templates-data/`，这意味着要么修改 `files` 字段，要么构建脚本将模板文件复制到 `dist/` 目录。这是一个**架构决策**，不应推迟到方案阶段。

3. **风险矩阵（第 4.4 节）中前两项风险**（npm 包分发遗漏、路径解析失败）都直接由运行时方案引入。如果在 plan 阶段就选择构建时内联方案，这两项高风险可完全消除。

4. **推荐方案**：构建时内联。理由：
   - 当前架构已使用 `AUTO-GENERATED-BEGIN/END` 内联模式，构建时方案是现有模式的自然演进
   - 消除运行时文件读取的跨平台路径问题
   - npm 包分发无额外配置负担
   - 唯一劣势（模板修改后需重新编译）在实际开发中不是问题，因为每次修改模板后必然要 `npm run build`

### 建议

在计划阶段明确选择「构建时内联」方案，并更新：
1. stage-01 op-005 的实现方向
2. 风险矩阵移除前两项（已通过选型规避）
3. `package.json` 修改项从"可能"改为"不需要"

## REV-003: npm 包分发 .md 模板文件的风险评估不足

- **优先级**：medium

## REV-004: 英文术语表翻译建议存在不当

- **状态**：closed
- **优先级**：medium
- **阻塞**：false
- **提出人**：Reviewer
- **提出时间**：2026-07-09 16:15

### 问题描述

计划第 4.3 节英文术语表中，部分翻译建议值得商榷：

1. **「总统领」→ "Commander / Orchestrator"**：
   - "Commander" 在军事语境中有强等级色彩，与 OpenFeel 的协作式 Agent 体系调性不完全吻合
   - "Orchestrator" 更贴切——强调协调和编排，而非命令
   - 但注意：Agent 的 `id` 是 `feel`，术语表应与 Agent ID 保持对应关系

2. **「事务官」→ "Utility Agent"**：
   - "Utility" 暗示"工具性/辅助性"，不够具体
   - 当前代码中该 Agent 的 ID 是 `utility`，所以 "Utility Agent" 与 ID 一致，这是合理的
   - 但如果考虑语义准确性，"Operations Agent" 或 "Clerk" 可能更好

3. **术语表缺少 agent ID 与英文名的映射关系**：翻译时应确保英文术语与 Agent ID 不冲突或歧义。例如 Agent ID `feel-tester` 对应「测试官」，英文应为 "Tester" 而非 "Feel Tester"（避免与 Feel 混淆）。

4. **AGENTS.md 中的约束链翻译**：英文模板中「你应当以中文思维思考问题」需改为「You should think in English and output concise conclusions in English at the beginning of each session」——这不只是翻译，是行为逻辑的根本切换，计划中 B2 任务未充分考虑这种语义切换的复杂性。

### 建议

1. Feel → Orchestrator（推荐）或 Commander，在方案阶段由 Schemer 确认
2. 在术语表中增加 Agent ID 列，确保翻译与 ID 一致性
3. stage-03 op-002 任务说明中增加「英文 AGENTS.md 的行为准则需适配英文思维模式」的显式约束

- **状态**：pending
- **优先级**：medium
- **阻塞**：false
- **提出人**：Reviewer

风险矩阵第 4 项「向后兼容破坏」标记为概率低、影响中。但以下场景未被充分评估：
