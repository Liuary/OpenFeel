## 二、分维度不足分析

### 维度 1：源模板 vs 部署版的分歧（提示词腐化）

#### 发现

| 对比项 | 源模板 (zh-CN) | 部署版 (.opencode/agents/) | 差异行数 |
|--------|---------------|---------------------------|----------|
| `feel.md` | 有`核心定位：你是调度者`+`硬性纪律表`+`流程不可跳过`+`禁止手动编辑 flow.json`四个节 | **全部缺失** | diff +27 行 |
| `executor.md` | 有`## package.json 模板要求`节（含 4 个必填字段 + 必填说明表） | **缺失** | diff +25 行 |

#### 影响

Feel 部署版缺失的四个节是**调度纪律的核心约束**：

- **"核心定位"**（1 行）：缺失后 Feel 不知道自己是调度者而非执行者，导致越权倾向
- **"硬性纪律表"**（8 行规则表）：缺失后 Feel 无法判断何种场景必须委托、何者可亲为
- **"流程不可跳过"**（6 行反例清单）：缺失后 Feel 可能跳过 Planner/Schemer/Reviewer/Tester/Archiver 任何一环
- **"禁止手动编辑 flow.json"**（6 行反例 + 3 条原因）：缺失后 Feel 可能在 CLI 故障时直接 edit flow.json

Executor 部署版缺失的 `package.json 模板要求` 导致其在创建新项目时无最小字段约束，产出可能遗漏 `"type": "module"` 等关键字段。

**根因**：`build.js` 注入管线可能只在 `npm run build` 时同步，而部署版文件是手动维护的，两者不同步。

### 维度 4：冗余与矛盾

#### 4.1 Feel "兼任 Planner" 与 "必须委托" 的矛盾

- **AGENTS.md** 第 93 行："Feel 总统领统一调度下游 Agent"
- **feel.md（源模板）** 调用子 Agent 硬性纪律表中明确：制定计划 → Planner
- **feel.md（部署版）** 第 154 行："Planner 职责由 Feel 兼任，计划制定与整体调度高度耦合"
- **feel.md（部署版）** 小改阈值表：单文件 ≤ 30 行 → "Feel 自行处理（兼任 Planner）→ 直接编码"

**矛盾链**：
1. 硬性纪律说「制定计划 → Planner」是必须的
2. 小改阈值说 ≤ 30 行 Feel 可兼任 Planner
3. 模型选择段说"Planner 职责由 Feel 兼任"（暗示这是常态）

当 Feel 面临一个 25 行的需求时：是委托 Planner 还是自己上？硬性纪律和阈值表给出了冲突答案。

**建议**：统一表述——小规模默认由 Feel 兼任 Planner（阈值表为准），删除模型选择段中歧义性"Planner 职责由 Feel 兼任"表述，或改为"Feel 在小规模场景下可兼任 Planner 角色"。

#### 4.2 "委托 Executor" vs "可派事务官" 边界模糊

- feel.md 委托边界："文件增删复制移动、格式转换、编码检查" → 事务官
- feel.md 非编码小活："格式批量替换、配置项整理、文档结构调整" → Executor（type: utility）

这两个列表有高度重叠。Agent 无法判断一个"格式批量替换"任务该走事务官还是 Executor utility 路径。

#### 4.3 AGENTS.md 与 core.md 的功能域重叠

| 内容 | AGENTS.md | core.md |
|------|:--:|:--:|
| 9 Agent 体系总览表 | ✅ | ❌（间接引用） |
| 职责边界 | ✅ | ❌ |
| 路径自校验规则 | ❌ | ✅ |
| 知识库自动写入机制 | ❌ | ✅（详尽） |
| 审查/追踪生命周期 | ❌ | ✅（详尽） |

两文件分工总体清晰（AGENTS.md=行为约束，core.md=工作区操作），但 AGENTS.md 中的"跨 Agent 工具使用约束"和"Feel 调度约束"其实更接近操作规范（core.md 领域），而 core.md 中的"流水线推进"又涉及全局行为。存在模糊地带。

### 维度 6：与业界最佳实践的差距

#### 6.1 思维链引导（Chain-of-Thought）

- **现状**：AGENTS.md 第 12 行仅一句"以中文思维思考问题，将思考结论整理为简扼信息"，无结构化思维链引导
- **最佳实践**：系统 prompt 应引导模型在复杂决策前输出 `<thinking>` 块，包含"分析 → 方案 → 验证"三阶段
- **差距**：9 个 Agent prompt 均无 CoT 引导句式。仅 Reviewer 的"审查流程"有类似行为但不显式要求输出推理过程
- **影响**：Agent 在复杂决策（如 Feel 判断"该委托谁"、Planner 判断"是否需要独立 Planner"）时可能跳过推理直接行动

#### 6.2 Few-shot 示例

| Agent | 有 Few-shot | 示例内容 |
|-------|:--:|------|
| Feel | ⚠️(1 个反例) | "反例：Feel 直接给 Executor 一段长 prompt" |
| Executor | ⚠️(1 个正例) | 自测报告模板（可视为 example） |
| Reviewer | ⚠️(1 个表) | blocking 场景示例表 |
| Schemer | ⚠️(1 个模板) | 方案模板 |
| Planner | ❌ | — |
| Feel Tester | ❌ | — |
| Archiver | ❌ | — |

- **差距**：每个 Agent 的**最少应有一个正例和一个反例**，展示什么是正确的行为、什么是违规行为
- **最佳实践**：Anthropic 的系统 prompt 指南建议"每次给出一个约束时附带一个示例"
- **影响**：Agent 大概率理解约束字面意思但无法映射到实际行为

#### 6.3 输出格式约束

- **现状**：仅 Executor 和 Schemer 有输出模板（自测报告、方案文件），其他 Agent 仅文字描述
- **最佳实践**：关键输出（Planner 的计划、Reviewer 的 REV、Tester 的 BUG、Archiver 的归档摘要）应有结构化模板
- **差距**：Planner 的"产出格式"节仅列出文件路径，未给出计划文件的具体内部结构

#### 6.4 自我纠错 / 反思循环

- **现状**：仅 Executor 有"重试 3 次"机制，Reviewer 有"再审"循环
- **差距**：
  - 无 Agent 在产出后有"自我批判"步骤（自问"我是否遗漏了什么？是否有更好的方式？"）
  - Feel 推进后无"回看确认"步骤（是否所有日志都写了？是否状态都同步了？）
- **最佳实践**：OpenAI 的 meta-prompt 建议在复杂决策后加"review and revise"步骤

#### 6.5 Hallucination 预防

- **现状**：Schemer 的"可测试性检查"中有"CLI 命令引用须通过 `--help` 确认存在"——这是 anti-hallucination 机制
- **差距**：此项约束局限在 Schemer，未推广到其他 Agent
  - Planner 制定计划时引用的 CLI 命令是否都存在？
  - Archiver 归档时引用的文件路径是否都存在？
  - Feel 调度时使用的 Agent ID 是否都合法？

## 三、强化方向（按优先级排序）

### P0-致命：修复源模板与部署版的提示词腐化

| 项 | 内容 |

### P1-高：统一 Agent Prompt 结构标准

| 项 | 内容 |
|----|------|
| **问题** | 9 个 Agent prompt 结构参差不齐——Feel Tester 严重欠结构化（评分 4/10），Planner 和 Reviewer 有碎片化残留。新 Agent 加入时无标准模板可参照，全靠人工对齐。 |
| **建议修改** | 在 patterns.md 或 dev_core.md 中定义一个「Agent Prompt 最小结构标准」：① 核心职责（3-5 条）② 工作流程（步骤化）③ 输出模板（结构化示例）④ 异常处理（常见异常 + 响应方式）⑤ KB 检索（何时、如何检索）⑥ 注意事项（禁止事项列表）。所有 Agent 按此标准回填。 |
| **受益文件** | `.opencode/agents/{feel-tester,planner,reviewer,archiver}.md` |
| **收益** | 一致性提升，新 Agent 加入有章可循，减少 CR 中的结构性问题 |

### P2-高：系统化错误处理路径

| 项 | 内容 |
|----|------|
| **问题** | 仅 Executor 和 Archiver 有明确的异常处理路径，其余 Agent 的异常处理均为"暗示"（如 Feel 的"决定重试/重定方案/人工介入"无具体操作步骤）。全局异常升级链缺失。 |
| **建议修改** | 1. 在 dev_core.md 定义全局异常升级链（Agent 自身 → Feel → 用户）及超时阈值；2. 每个 Agent prompt 增加「异常处理」节：工具调用失败、输入不完整、环境不兼容的响应方式；3. Feel prompt 增加"子 Agent 超时/无响应"的处理流程 |
| **受益文件** | `.opencode/agents/feel.md`、`.openfeel/dev/dev_core.md`、其余 Agent prompt |
| **收益** | 减少"卡住无响应"场景，降低人工介入频率 |

## 四、总体评估

| 维度 | 评分 | 评语 |
|------|:--:|------|
| 体系完整性 | **8/10** | 6 层架构设计合理，分层清晰，约束→操作→Agent→知识 逐层细化 |
| 内容质量 | **7/10** | Feel/Executor 高质量，Feel Tester 明显欠结构，Reviewer 有编辑残留 |
| 一致性 | **5/10** | 源模板与部署版严重不一致，Feel 内部有兼任/委托矛盾，交叉引用缺乏校验 |
| 可维护性 | **6/10** | patterns.md 维护良好，但源/部署同步机制薄弱，静态引用无校验 |
| 实用性偏差 | **7/10** | 缺乏 CoT/Few-shot 等业界实践，错误处理覆盖不全面 |

**总评**：提示词体系框架设计良好，但存在**两个致命缺口**（Feel 和 Executor 部署版过期）和**两个系统性弱点**（结构不统一、错误处理不足）。建议按 P0 → P1 → P2 → P3 顺序依次修复，P4-P7 可在日常迭代中逐步处理。
