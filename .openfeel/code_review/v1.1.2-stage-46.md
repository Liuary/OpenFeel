## REV-011 裁定与移交（fail-fast 语义分叉）

**事实**（隔离实测双证）：受管文件路径（`writeManagedFile` / `init`）备份失败 → 跳过该文件 + `anomaly(backup_failed)` + 命令**继续**（exit 0）；全局 `opencode.jsonc` 三处直写（`setup.ts:64` / `update.ts:1529` / `migrate.ts:524`）备份失败 → `BackupError` **上抛中止整条命令**（exit 1）。与 B3「其余文件继续」字面不符。

**裁定**：**可接受（非阻塞 fail-fast）**——① 数据安全无损（abort 下「无备份不覆盖」以最强形式成立，jsonc 原样保留）；② 状态可自愈（三命令 `saveGlobalUpdateState` 均在尾部，中止即未落盘，重跑收敛；migrate 另有 `finally` 回填 + `rollbackMigration` 兜底）；③ 失败响亮（含路径 + 原因 + 非零退出）；④ 根因是**方案缺口而非执行偏差**（op-003 改动 3 伪代码本身无 try/catch，executor 如实实现并在偏差记录披露）。唯一实质偏差 = `setup`/`update` 中止于「部分部署」状态（非数据不一致、非数据丢失）。

**归属裁定：stage-47**（planner 已裁定：`setup`/`update` 补 try/catch 对齐 B3 口径；`migrate` 保留 fail-fast + 文档化）。归档官**不代改**，仅沉淀（见 `.openfeel/kb/troubleshooting.md`「备份失败绝不覆盖的失败路径语义分叉」）。

## 心得建议

1. **「方案伪代码」是执行保真度最高的契约，也最易带走控制流缺陷**：REV-008 的矛盾代码块（`writeDefaultConfig` 落在 `if` 之外）若按字面实现即重现数据丢失路径。审查必须逐块**追踪字面控制流**，而非只看「正文要求」与「实现提示」。
2. **备份类需求必须先写清「失败语义」再动代码**：本阶段受管路径与直写路径的处理不一致，根因是方案层没给 jsonc 直写路径定 try/catch。需求含「失败不 X」时，方案须**逐接入点**给出失败分支，而非在某一处给出范式后默认其余一致。
3. **「备份 + 状态文件提示」是三段链**：条目（机器可读）+ TTY 提示（当场可见）+ 会话启动检查规则（事后可发现）。缺任一段都会出现「备份了但没人知道」，故三者须同批落地并同批验收。
4. **状态文件新增类别时，读侧改造与写侧同等重要**：REV-003 实证「只改 `SECTION_TITLES` 不改读侧」会把新节条目误归前一节——这类「写侧显式、读侧硬编码」的双源，是最典型的静默错分类来源。
5. **语义有意的「失败分叉」应当显式裁定并留归属**：REV-011 未强行在本阶段消除，而是给出「可接受 + 归属下阶段 + 排查/对齐方向」，避免为表面一致性引入静默半完成。
6. **缓解 ≠ 修复**：Bug 归档须严格区分二者并在公共 Bug 文件显式标注（本阶段 `config/BUG-002` 保持 open），否则后续排期会被误导。
