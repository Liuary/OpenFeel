# 对 OpenFeel 的认知

> 基于 NumKit v1.0.0 全流水线端到端测试的实践认知
> 撰写：Feel（总统领 Agent），2026-06-27

---

## 一、OpenFeel 是什么

OpenFeel 是一套**基于多 Agent 协作的软件开发流水线自动化体系**。它不只是一个工具，而是一个完整的工作方法论——将软件开发过程拆解为 7 个独立 Agent，每个 Agent 负责一个明确环节，通过流水线状态机串联成完整的"计划→方案→编码→审查→测试→归档"闭环。

核心设计理念：
- **职责分离**：每个 Agent 只做一件事，不越界
- **交叉验证**：不同模型/不同视角的 Agent 互相审查，避免盲区
- **可回溯**：每个操作都有方案文档、审查记录、测试报告，全程可追溯
- **知识沉淀**：通过 Archiver 将经验提取到知识库，项目越做越"聪明"

## 二、架构全景

### 2.1 三层体系

```
┌─────────────────────────────────────────┐
│              分期大纲 (Roadmap)            │  ← Feel + Planner
│          "这个版本要做什么"                │
├─────────────────────────────────────────┤
│              工作阶段 (Stage)              │  ← Planner
│    "这个阶段要交付什么、质量指标是什么"     │
├─────────────────────────────────────────┤
│              操作方案 (Op)                 │  ← Schemer
│     "具体怎么做、步骤1/2/3、自测清单"      │
└─────────────────────────────────────────┘
```

### 2.2 七 Agent 体系

| Agent | 模型策略 | 核心职责 | 输入 | 产出 |
|-------|----------|----------|------|------|
| **Feel** | 主力推理模型 | 总调度、意图理解、决策 | 用户指令 | 调度指令 |
| **Planner** | 推理模型 | 分期大纲、阶段划分、依赖声明 | 需求 | Roadmap + Stages |
| **Schemer** | 推理模型 | 极细粒度操作步骤 + 自测清单 | 阶段目标 | op-xxx.md |
| **Executor** | 快速模型 | 按方案编码 + 自测（速度优先） | 操作方案 | 代码 + 测试 |
| **Reviewer** | **异种推理模型** | 5 维交叉审查 | 方案 + 代码 | REV 条目 |
| **Tester** | 推理模型 | 独立验收 + Bug 管理 | 方案 + 代码 | BUG 条目 |
| **Archiver** | 推理模型 | 产出归档 + 知识提取 | 阶段产出 | 知识库条目 |

### 2.3 流水线状态机

```
plan_pending → plan_passed → scheme_pending → scheme_passed
                                                  ↓
                                            exec_running
                                                  ↓
test_passed ← test_pending ← review_passed ← review_pending
    │                            ↑                │
    └── test_failed ──→ (Bug修复)            review_failed ──→ (REV修复)
                                                  ↓
                                            archiving → done
```

### 2.4 配置级联优先级

```
用户直接指令  >  status.md（阶段级覆盖）  >  config.yaml（全局默认）
   (最高)              (中等)                    (基础)
```

## 三、关键设计洞察

### 3.1 模型异构是核心价值

经过实际测试，**Reviewer 使用异种模型是 OpenFeel 最有价值的设计决策**。

实证：在 stage-01 中，Planner(Schemer)→Executor 的全链路（均为 DeepSeek 系列）均未发现 TypeScript 版本 `5.8.0` 在 npm 不存在的问题。而 Reviewer（异种模型）在审查时立即捕获了这一不一致。

这验证了一个关键假设：**同模型系列的 Agent 存在集体盲区，异种模型的交叉审查能有效弥补。**

### 3.2 自测与正式测试的职责分离

Executor 的"自测"和 Tester 的"正式测试"不是冗余，而是互补：

| | Executor 自测 | Tester 正式测试 |
|------|:--:|:--:|
| 视角 | 实现者视角（确认"我做对了"） | 验收者视角（确认"需求对了"） |
| 深度 | 按自测清单逐项检查 | 独立设计边界/异常用例 |
| 盲区 | 容易忽略非功能性边界 | 不熟悉实现细节 |

实证：Executor 自测通过了全部用例（52/52），但 Tester 用独立验收测试发现了 `toFixed(1.005, 2)` 的 IEEE 754 精度 Bug——这是 Executor 自测清单未覆盖的边界。

### 3.3 方案驱动 vs 意图驱动

OpenFeel 采用**方案驱动**模式（Schemer 出 op → Executor 执行），而非"意图驱动"（直接告诉 Executor 做什么）。

优势：
- 可复现：每个 op 是精确的操作记录
- 可审查：Reviewer 可对照 op 审查代码
- 可修正：出问题时 Schemer 出修正 op，而非临时 patch

代价：
- 额外开销：多一层 Schemer 调用
- 粒度敏感：op 太粗则 Executor 需自主决策，太细则效率低

### 3.4 知识库的"滚雪球"效应

Archiver 不只是"归档"，而是**知识提取引擎**。每次流水线完成，经验被提取到 kb/，后续 Agent 可查询。

实测中，stage-01 提取了 7 条知识（npm 版本验证、tsc 空目录报错等），stage-02 新增 4 条（IEEE 754 修复策略等）。如果同一个项目持续开发，知识库会形成"滚雪球"效应——后面的 Agent 越来越"懂"这个项目。

### 3.5 公共域 vs 私域的设计

`.openfeel/` 分为公共域（纳入版本管理）和私域（用户隔离），这是一个精细的设计：

- **公共域**：计划、知识库、审查结论 → 团队共享，纳入 git
- **私域**：个人操作日志、笔记、临时文件 → 用户隔离，gitignore

这解决了"哪些该共享、哪些该隔离"的边界问题。

## 四、工作区设计理解

### 4.1 目录结构语义

```
.openfeel/
├── config.yaml        ← 全局配置（执行模式、自动推进、测试开关）
├── flow.json          ← 流水线状态机（当前阶段、操作、审查/Bug 记录）
├── roadmap/           ← 分期大纲（版本级目标）
├── plan/              ← 大计划 + 依赖声明 + 计划日志
├── stages/            ← 工作阶段（子计划目录 + status.md + ops/）
├── kb/                ← 知识库（架构/模式/排查/环境）
├── code_review/       ← 公共审查摘要
├── bugs/              ← 公共 Bug 摘要
├── log/               ← 公共日志（团队级重要事件）
├── dev/               ← 核心规则 + 当前进度
├── tmp/               ← 项目级临时文件
└── users/{name}/      ← 私域（个人日志、笔记、审查、Bug）
```

### 4.2 状态管理机制

每个 stage 有独立的 `status.md`，记录：
- 执行模式（manual/auto）
- 自动推进（enabled/disabled）
- 当前状态（planned/ready_for_code/coding/ready_for_review/.../done/paused）
- 当前责任 Agent
- 阻塞原因
- 完整状态变更历史

这使得**跨会话恢复**成为可能——下次会话启动时读取 status.md 即可知道"上次做到哪了、谁应该接着做"。

### 4.3 自动推进的安全性

自动推进有明确的安全边界：
- 遇到计划外架构变更 → paused
- 连续两次验收失败 → paused
- 权限不明确 → paused
- 测试环境缺失 → paused

这避免了"Agent 不受控地自动推进导致灾难"的风险。

## 五、OpenFeel 的定位

经过完整测试，我对 OpenFeel 的理解是：

> **OpenFeel 是一个"软件工程的工业化流水线"**——它将软件开发的模糊过程标准化为 7 个 Agent 的协作流水线，每个环节有明确的输入/输出、质量标准、审查机制。它不是替代开发者，而是给开发者一套"工程纪律"——让你知道每个阶段该做什么、谁来做、做到什么程度算完成、出问题怎么回溯。

与传统开发模式的关键区别：

| 维度 | 传统模式 | OpenFeel 模式 |
|------|----------|---------------|
| 计划 | 口头/issue 描述 | 结构化 Roadmap + Stage + Op |
| 执行 | 开发者自主决策 | Executor 严格按 op 执行 |
| 审查 | 同事 PR review | 异种模型交叉审查 + REV 条目 |
| 测试 | QA 手动/自动化 | Tester 独立验收 + BUG 条目 |
| 知识 | 散落各处 | Archiver 提取 → kb/ 结构化存储 |
| 回溯 | git log + PR 讨论 | 完整 op + REV + BUG + 状态记录链 |

## 六、适用场景判断

**适合 OpenFeel 的场景**：
- 中大型项目的规范化开发
- 需要多人/多 Agent 协作的复杂任务
- 对质量和可追溯性要求高的项目
- 需要知识持续沉淀的长期项目

**不太适合的场景**：
- 快速原型/一次性脚本
- 单人小项目（流水线开销 > 收益）
- 需要大量创造性探索的任务（op 粒度难以预设）
