# op-002：实现 REV 闭环：blocking REV 阻塞 done 推进
- **阶段**：v4.4-stage-02
- **前置**：op-001（hard，共享 flow-manager.ts + flow.ts 文件）
- **负责 Agent**：Executor
- **最多重试**：3
- **参考**：kb/patterns.md #REV blocking 标记模式（blocking 字段语义、数据结构硬化）、kb/patterns.md #CLI 原子管理模式、kb/patterns.md #autoFixReview 前置条件校验模式（双路兜底）

## 目标

在流水线核心 (`flow-manager.ts`) 和 CLI 命令层 (`flow.ts`) 实现双路兜底：当目标 phase 为 `done` 时，若存在 `blocking !== false` 且 `status === 'open'` 的 REV 条目，无条件拒绝推进。`--force` 仅降级警告但不跳过安全检查。

## 设计决策

> **REV 闭环不设例外**（参见 plan.md 关键设计决策）：blocking REV > 0 时 `advance to done` 无条件拒绝。`--force` 仅降级日志级别（error → warn），仍拒绝推进。理由：流水线安全不应存在后门——若确有 low 优先级 REV 故意不修，应先通过 `flow review resolve` 或修改 REV 的 `blocking` 标记。

- [ ] A2. 在方法开头（参数校验通过后、stage 存在性检查之后），新增 REV 阻塞检查逻辑。插入位置：`const fromPhase = stage.phase;` 之前
- [ ] A3. 实现检查逻辑（参考 `addAutoFixReview` 的前置条件校验模式）：

  ```typescript
  // REV 闭环：blocking REV > 0 时拒绝推进到 done（--force 仅降级警告）
  if (targetPhase === 'done') {
    const stageReviews = this.data!.reviews.filter(
      (r) => r.op.startsWith(stageName) || r.op === `${stageName}.op-001`.replace(/\.op-001$/, '') // 按阶段前缀匹配
    );
    // 更精确的匹配：按 stageName 前缀匹配（如 stageName=v4.4-stage-01，匹配 op 以 v4.4-stage-01 开头的）
    const blockingOpen = stageReviews.filter(
      (r) => r.blocking !== false && r.status === 'open',
    );
    if (blockingOpen.length > 0) {
      const revList = blockingOpen
        .map((r) => `  ${r.id}: ${r.title} (priority=${r.priority})`)
        .join('\n');
      throw new Error(
        `无法推进到 done：存在 ${blockingOpen.length} 个未解决的阻塞 REV：\n${revList}`,
      );
    }
  }
  ```

- [ ] A4. **重要**：`--force` 处理不在 flow-manager.ts 层实现——flow-manager.ts 的 `advanceStagePhase` 方法不接收 `force` 参数。由命令层（flow.ts）在捕获到错误时根据 `--force` 决定是降级警告还是向上抛出。因此 A3 中直接 `throw new Error`

  ```typescript
  // REV 闭环（命令层兜底）：推进到 done 时检查 blocking REV
  if (options.to === 'done' && options.stage) {
    const allReviews = mgr.getReviewItems();
    const stageReviews = allReviews.filter(
      (r) => r.op.startsWith(options.stage!) || r.op === options.stage,
    );
    const blockingOpen = stageReviews.filter(
      (r) => r.blocking !== false && r.status === 'open',
    );
    if (blockingOpen.length > 0) {
      console.warn(`[!] 检测到 ${blockingOpen.length} 个未解决的阻塞 REV：`);
      for (const rev of blockingOpen) {
        console.warn(`    ${rev.id}: ${rev.title} (priority=${rev.priority})`);
      }
      if (options.force) {
        console.warn('[!] --force 已指定，但 REV 安全检查不可绕过。拒绝推进。');
      }
      console.error('错误：blocking REV 未解决前禁止推进到 done。');
      console.error('请先解决上述 REV 或通过 flow review resolve 标记为非阻塞。');
      process.exit(1);
    }
  }
  ```

## 困难点

1. **REV 按 stageName 精确匹配**：`ReviewItem.op` 字段格式为 `stage-xx.op-xxx`（如 `v4.4-stage-02.op-001`），需用 `startsWith(stageName)` 匹配。当 `stageName` 本身不含 `.op-xxx` 后缀时，前缀匹配足够精确。若存在边界情况（如 `v4.4-stage-02` 和 `v4.4-stage-02-extra` 前缀重叠），需升级为 `r.op.startsWith(stageName + '.')` —— 当前阶段命名规范不含特殊后缀，前缀匹配可用。

2. **双路兜底顺序**：命令层（flow.ts）先校验 → flow-manager.ts 层再校验。命令层的优势是可以提供更丰富的 CLI 错误输出（含 `--force` 提示），flow-manager.ts 作为最后防线。两层校验逻辑应保持同步。
