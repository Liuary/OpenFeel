## 心得建议

1. **「文档即载体」可零代码新增**：CLI 用法 skill 化不需要任何新逻辑——只需在既有唯一权威源目录里放一个 `SKILL.md`，build 的双注入与自举会自动纳入。真正的设计点在**防发散**：`description` 触发词（保证被加载）+ **快照声明**（把实时真相的权威指回 `--help`/自描述命令）+ 与执行型 skill（wizard）的边界互引。
2. **新增 skill 的隐藏成本是「计数断言」**：`16 → 17` 会连带 14 处写死断言，其中 `expectedSkills` 是**白名单数组而非计数**（不追加则新 skill 完全不被断言覆盖）。方案首版漏此点由审查官补出——「新增载体必须全仓扫描写死数字与白名单」应作为标准动作。
3. **版本号收口的敌人是「生成段 + 手工副本 + 历史注释」三者的相似性**：`agents-md/*` 权威源与仓库根 `AGENTS.md` 是**手工双份**（只改一处不触发任何失败）；生成段禁手改；D 类历史注释必须靠**内容特征**而非行号判定。清单化（A/B/C/D/E）+ 独立 op 复核是唯一可靠解。
4. **`package-lock.json` 的漂移要用「手改两行」而非「重装」**：`npm install` 重生成会连带依赖树 diff，把版本收口变成不可审的变更；手工同步 root `version` 使 diff 可逐行核对（本案零依赖树变动）。
5. **门禁可信度优先于门禁数字**：`lint i18n` 的 502/531 之争根因是**PATH 上存在全局旧版 CLI**，两个数字都「真实」，但只有一个属于本仓。凡结论依赖某信号，必须能复现「命令 + 版本 + 环境」三要素。
6. **审查官被推翻的判断必须留档并显式更正**：本阶段审查方主动改写 REV-006 结论、撤销 stage-47 的连带「微瑕」判定、并落「后续门禁一律 `node bin/openfeel.js`」的流程改进——违反直觉（审查方认错），但这正是审计链可信的来源。
7. **最后阶段必须做「归属收口」**：`REV-44` 三项 pending 若不在最后阶段显式落地或声明归属，将随版本结束**永久丢失**（REV-004 的 blocking 正源于此）。版本收官前应例行扫描**所有前置阶段遗留的 pending/归属未落地条目**。
