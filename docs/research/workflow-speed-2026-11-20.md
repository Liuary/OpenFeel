# 工作流运转速度研究（基于本地历史会话）

> 研究日期：2026-11-20 ｜ 阶段：`v1.5.25-stage-13` ｜ 需求：REQ-052
> 数据来源：`%USERPROFILE%\.dsh\sessions\<project>\<session>\session.v4.jsonl.zstd`（DSH 会话原始事件流）
> **数据快照时刻**：2026-11-20 02:0x（OpenFeel 桶在本会话中仍在增长，复跑会有个位差异）
> 方法：文件是**多帧 zstd 追加**（Node 单帧解压只能读到类型为 `session` 的元数据行），按 RFC 8878 帧头解析切帧后逐帧解压，再统计 `turn/start`、`turn/end`、`tool/call`、`tool/result`。

## 一、口径与已知偏差

- **turn**：`turn/start` → `turn/end` 的墙钟区间（含模型推理与工具执行）。
- **call**：一次 `tool/call`。
- **工具耗时**：`tool/call.time` → 对应 `tool/result.time` 的差值。**它包含模型推理/排队等待，不等于工具纯执行时间**；因此本文只用**中位数**做量级判断，不用均值。
- **重复调用**：工具名 + 参数 JSON 完全相同（sha1 前 8 位）；只统计 ≥3 次。
- **连续同名段**：同一会话内连续 ≥3 次同名工具调用；按文件（会话）重置计数。
- 首次统计脚本存在两个口径错误（跨项目混算收益、用均值折算时间、连续段跨文件累加），已修正；本文数字为修正后结果。

## 三、结论（与上一版相反的部分）

1. **砍流程对"总墙钟"几乎没有影响**：`feel_*` 在 CulaHub 只占 3.9%、在 OpenFeel 只占 0.6%。
   想要"小时级提速"靠削减流程是不现实的；把 562 次 feel_req 全砍掉也只省 57 分钟/1449 分钟。
2. **真正的墙钟大头是执行与等待**：
   - CulaHub：`job_output` 421 分钟（29%）——后台任务结果等待；`pwsh` 676 分钟（47%）——构建/测试/脚本。
   - OpenFeel：`pwsh` 4655 分钟（72%）——主要是全量 `vitest`（60–80s/次）、`build`、长命令。
3. **流程的代价主要在"调用次数与上下文"**：CulaHub 每轮 24 次调用（p90 43），feel_req 占 19% 的调用次数。
   减少调用对**模型轮转、上下文膨胀、以及人等待反馈的粒度**有实感，但省下的是分钟，不是小时。
4. **每轮时长本身不是问题**（中位 172–177s），问题是长尾（p90 825–970s）：一轮里塞了太多步骤。

## 四、建议（按证据强度排序，收益按实测口径）

### P1（推荐，S）：需求生命周期再合两步

- **做法**：`req add --claim --stage --start`（一条命令到 `in_progress`）+ 已有 `req complete`。
- **实测收益**：CulaHub 7.9 → 约 2.5 次/需求，**省约 380 次调用、约 19 分钟**；调用次数降 13%。
- **风险**：低（都是既有原子操作的组合，审计不变）。

### P2（推荐，S）：把"等待后台任务"从轮询改成事件

- **做法**：`feel_next` 明确"用完成通知 / `wait_agent`，不要 `job_output` 轮询"；任务完成时由适配器注入结果，下一次 `feel_next` 直接带摘要。
- **实测收益**：CulaHub `job_output` 335 次、合计 421 分钟（p50 25s/次）——这是最大单项可优化项；即便只省一半等待也有小时级。
- **风险**：低（不改数据，只改调度建议）。

### P3（推荐，S–M）：批量化瞄准 pwsh / edit / read

- **做法**：提示词与工具用法上鼓励"一条 shell 做多件事、一次 edit 改多处"；`feel_stage task` 支持数组批量勾选（本仓实测 96 次单条调用）。
- **实测收益**：OpenFeel 连续段 pwsh 608 / edit 414 / read 320；减少段数意味着更少的往返与上下文。
- **风险**：低；注意 shell 命令变长后门禁判定更易落第 4 类（warn）。

### P4（不建议，M）：写工具自带状态快照、去掉显式 preflight 读

- **原提案**：写工具返回 snapshot，省掉"先读状态"。
- **实测反驳**：OpenFeel 同参 `feel_status` 121 次 × p50 0.58s ≈ **1.2 分钟**；CulaHub 只有 4 次。
- **风险**：preflight 现在是"本会话内真实读过状态"的账本；改成进程内快照后，**跨会话恢复 / 子 agent 派发**可能从未真实读状态就写入受保护文件。收益 1 分钟，风险是流程污染。
- **结论**：不做。若将来要改，应先补"恢复态/子 agent 态"的等价性设计，而不是当提速项。

### 不动的部分

- **审查门 / done 门**：CulaHub 上 `review`+`verify` 142 次、约 7 分钟；它们是"完成可核对"的唯一机制，收益远大于成本。
- **写入门禁**：48 个错误里只有 3 次是受保护文件；拦错的代价高于放行。

## 五、把话说清楚

- 本报告能证明的：**需求记账是调用次数的主要噪声（19%），但不是墙钟的主要噪声（3.9%）**；
  后台任务等待与构建/测试才是墙钟大头。
- 本报告不能证明的：单次 feel 调用 2–3s 里"多少是 spawn 开销、多少是 flow.json 读写"——
  需要一次空 CLI spawn 基准测试才能拆开（未做，标为未验证）。
- 因此"提高工作流运转速度"的正确靶子是：**并行化等待、减少每轮调用数、把测试/构建粒度变细**；
  "削减无用流程"能做的只有 P1（需求生命周期）这一件事，其余流程（审查/门禁）应保留。

## 六、建议落地

1. `v1.5.26`：P1（`add --start`）→ P2（等待改事件）
2. 观测项：P3 作为使用习惯改进，写进提示词即可，不单独立项
3. 明确不做：P4
