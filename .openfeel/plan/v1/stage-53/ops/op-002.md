### 三.4 并发协议（**A9 用户裁定**：加锁 + 合并双保险）

**锁 API 与路径（实测坐标）**：

| 项 | 真实 API / 路径 | 文件:行号 |
|----|------|------|
| 同步临界区封装 | `withFileLock<T>(lockPath: string, fn: () => T, options?: FileLockOptions): T` | `src/core/fs/file-lock.ts:122` |
| 项目级锁路径 | `projectLockPath(projectPath, name)` → `{projectPath}/.openfeel/tmp/locks/{name}.lock` | `src/core/fs/file-lock.ts:59-61` |
| 全局锁路径（**本场景不用**） | `globalLockPath(name)` → `~/.openfeel/locks/{name}.lock` | `src/core/fs/file-lock.ts:64-67` |
| 超时 / 陈旧阈值 | `LOCK_TIMEOUT_MS_DEFAULT = 5000` / `LOCK_STALE_MS_DEFAULT = 3000`（`FileLockOptions` 可覆写） | `src/core/fs/file-lock.ts:31/33/40-49` |
| 原子写 | `atomicWriteFileSync(path, content)` | `src/core/fs/atomic-write.ts` |
| 既有同类用法（范式参照） | `withFileLock(projectLockPath(projectPath,'update-state'), …)` / `withFileLock(lockPath, …)`（`flow-manager` / `public-logger` / `stage.ts`） | `src/core/update-state.ts:120`；`src/core/flow-manager.ts:486/613/2834/3140`；`src/core/public-logger.ts:147`；`src/commands/stage.ts:214/271` |

**锁粒度裁定**：**每用户一把锁**（`name = 'dev-last-' + username`），**索引与全部主题文件共用同一把锁**。理由：
1. 索引摘要与主题文件内容**同属一次写入事务**（摘要必须反映主题文件的最新条目）→ 分锁会出现「索引与主题不一致」的中间态；
2. 锁名含 `username` → **不同用户互不阻塞**（并行度足够；写发生在会话末尾，冲突概率极低）；
3. 锁文件落在 `.openfeel/tmp/locks/`（**已 gitignore**）→ 不污染版本库，也不侵入 `users/{username}/` 私域目录。

**临界区形态（写死）**：**一次进出、短临界区**——`读索引 + 读主题文件` **也在锁内**（否则 read-modify-write 竞态），随后合并 → `atomicWriteFileSync` 写回。

**为何仍然保留合并语义（锁之外的第二道保险）**：
1. **锁边界有限**：`withFileLock` 只覆盖**同一项目内**的进程；跨项目/跨机（共享目录）或陈旧锁（`staleMs=3000`）被抢占的窗口内，仍可能交叉写；
2. **跨会话读取滞后**：Feel 可能在**会话开始**读过索引、**会话末尾**才写回 → 写前必须在锁内**重读**并按「合并」策略合并，否则会丢失他人在此期间的写入；
3. **绕过锁的写入**：手工编辑、第三方工具、或 `dist` 不可用时的降级路径不经锁；
4. **合并承担取舍语义**：**同主题冲突 → 两侧条目均保留 + 追加冲突标记**——这是锁**无法**表达的（锁只保证互斥，不决定如何合并）。

**降级路径（`dist` 不可用等）**：无法调用 `withFileLock` 时 → 至少执行「**读-合并-写**」（`atomicWriteFileSync`）并在报告中标注「未加锁」；**不得**退回「整文件覆盖写」。
