# 给 AI 编程套上缰绳：从 Vibe Coding 到结构化协作

> 我们不是在驯服 AI，而是在驯服开发流程的熵。

---

## Vibe Coding 很美，但很美不够

2025 年最火的词之一是 Vibe Coding —— 你跟 AI 聊天，它写代码，你看着它跑，爽不爽？爽。

但用过的都知道那个时刻：聊了 30 轮，上下文炸了，AI 忘了你十分钟前说过什么。你让它改一个函数，它顺手重构了三个文件。你觉得不对，但它信心满满地告诉你"这是最佳实践"。

Vibe Coding 的问题不是 AI 不够聪明，而是**没有结构**。一个人的脑子记不住 30 轮对话的上下文，一个模型也不行。你的项目状态在哪？当前在干什么？谁在做？做到哪了？——这些信息全在对话气泡里飘着，一刷新就没了。

## Harness，不是限制，是指引

骑马需要缰绳（harness），不是要勒死马，而是让马知道方向。

AI 编程需要同样的东西：一套轻量但明确的约束体系，让 Agent 知道"现在该做什么、不该做什么、谁来做"。

OpenFeel 做的就是这个。核心就三样：

**1. 特化 Agent，不搞全能选手**

```
总统领 (Feel)     → 理解意图，调度全局
计划官 (Planner)   → 定方向，分阶段
方案官 (Schemer)   → 拆成 Executor 能直接执行的清单
执行官 (Executor)  → 按清单写代码，不自行发挥
审查官 (Reviewer)  → 交叉审查，换模型去盲区
测试官 (Tester)    → 正式验收，不是 Executor 自测就算
归档官 (Archiver)  → 沉淀知识，下次少犯错
事务官 (Utility)   → 文件操作、构建校验，不浪费推理模型
```

每个 Agent 只做自己最擅长的事。不是"让一个 AI 做完所有事"，而是**让多个特化 AI 在流水线中接力**。

**2. 状态外化，不靠记忆**

```
flow.json   → 流水线走到哪了
status.md   → 当前阶段进度、谁在干活、阻塞在哪
kb/         → 踩过的坑、验证过的模式
```

Agent 不需要"记住"上下文——状态在文件里，重启会话也能从断点继续。

**3. 反馈循环，不是线性执行**

```
计划 → 方案 → 编码 → 审查（不通过？回退方案）→ 测试（发现 Bug？回退修复）→ 归档
```

每一步都可能回到上一步。不是流水线，是**带反馈的循环（loop）**。失败不阻塞——方案级问题标记为非阻塞，继续推进；阻塞性问题才停下等待干预。

## 三个实战教训

**教训一：不要提前优化**

我们担心频繁调用子 Agent 会破坏模型缓存，讨论做"返回精简"优化。拉了一个月实际数据：cache 命中率 95.5%。系统提示词占总输入的 95%，每次请求都命中缓存。子 Agent 返回的增量聊天气泡占比极小。凭直觉的"优化"对着空气挥拳。

**经验**：技术决策优先看数据，别靠猜。

**教训二：减法优先于加法**

v3.0 有 15 个 Agent。v4.0 砍到 7 个。砍掉的全是职责重叠的中间层。每多一个 Agent，多一层调度开销和一个可能出错的地方。

**经验**：不是越多越好。清晰的边界比数量重要。

**教训三：约束要说清楚能做什么，不能含糊**

"Feel 不直接修改源码"——这条约束导致 Feel 连 git rm 一个文件都要纠结是不是越界。后来明确了 Feel 可以直接操作的范围（文件增删、格式转换、构建校验），把"修改源码内容"留给 Executor。

**经验**：模糊的约束比没有约束更糟。

## 这套东西难不难用？

v4.0 我们用这套框架开发了它自己——39 项任务，4 个阶段，11 条审查条目，0 个阻塞 Bug 残留。测试 225/227 通过。全过程靠 `openfeel flow overview` 一个命令看清所有状态。

用起来就是一句 prompt："开发一个支持 Markdown 解析的静态网站生成器"。然后观察框架一步步推动。

## 不是替代你，是放大你

Vibe Coding 让你沉浸在"和 AI 一起写代码"的体验里。Harnessed Coding 让你站在流水线上方，看多个 Agent 各司其职。

你不是在和 AI 对话，你是在调度一个开发团队。
