### 步骤 2：flow-manager.ts — `save()` 改造（275-332 行）

> ⚠️ **（REV-103 修订）本步骤代码已替换为最终版（含乐观并发 revision 校验），与 R2.3 为同一代码。R2.3 保留设计说明与「改造前 → 改造后」对照，若两处不一致以本步骤为准。**

**改造前**：写 `.tmp` → 读回校验 → `renameSync` → 末尾 `writeFileSync(.bak, content)`（新内容覆盖 `.bak`，缺陷）；且无 revision 概念。

**改造后**（整体替换方法体）：

```ts
  /** 保存 flow.json（自动更新 meta.updated；锁内做乐观并发校验、备份旧版本并原子写） */
  save(): void {
    if (!this.data) {
      return;
    }
    this.data.meta.updated = new Date().toISOString();

    // 创建清理后的副本：去除 op 中的 id 字段（id 由 stages.{stageId}.ops 的键名决定）
    const serializable = JSON.parse(JSON.stringify(this.data)) as FlowData;
    for (const stage of Object.values(serializable.stages)) {
      for (const op of Object.values(stage.ops)) {
        delete (op as unknown as Record<string, unknown>).id;
      }
    }

    const lockPath = projectLockPath(this.projectPath, 'flow');
    try {
      withFileLock(lockPath, () => {
        // 乐观并发校验：锁内读磁盘 revision，与加载时比对；不一致说明有并发写，拒绝覆盖
        const diskRevision = this.readDiskRevision();
        if (diskRevision !== this.loadedRevision) {
          throw new FlowConcurrentModificationError(this.loadedRevision, diskRevision);
        }
        const nextRevision = this.loadedRevision + 1;
        serializable.meta.revision = nextRevision;

        // S5：写前复制旧文件为 .bak；写成功后不覆盖 .bak，使其始终保留上一版本
        const content = JSON.stringify(serializable, null, 2) + '\n';
        atomicWriteFileSync(this.filePath, content, { backup: true });

        // 同步内存与加载基线，避免同实例连续 save 误判冲突
        this.data!.meta.revision = nextRevision;
        this.loadedRevision = nextRevision;
      });
    } catch (err) {
      console.error(`[ERROR] flow.json 保存失败: ${err instanceof Error ? err.message : err}`);
      throw err;
    }
  }

  /** 读取磁盘当前 revision（不存在/损坏/缺失 → 0，兼容存量文件） */
  private readDiskRevision(): number {
    try {
      const raw = readFileSync(this.filePath, 'utf-8');
      const parsed = JSON.parse(raw) as { meta?: { revision?: unknown } };
      const rev = parsed?.meta?.revision;
      return typeof rev === 'number' && Number.isInteger(rev) ? rev : 0;
    } catch {
      // 文件不存在或损坏：视为 0（首次写入 / 由 repair 兜底）
      return 0;
    }
  }
```

**关键点**：
- 删除原 291-327 行全部 tmp/rename/`.bak` 手工逻辑；`backup: true` 由 op-001 实现「写前复制」。
- 删除原 307-321 行「写 tmp 后 JSON 读回校验」——`atomicWriteFileSync` 的 temp+rename 已保证不落半写文件；如需 JSON 合法性前置校验，可在序列化后本地 `JSON.parse(content)`（`JSON.stringify` 输出必然合法，故省略，避免冗余）。
- **锁粒度 = 乐观校验 + 序列化 + 备份 + 原子写**（**REV-103 修订**：序列化由锁外移入锁内——revision 必须随内容一起原子落盘，无法在锁外确定；`readDiskRevision` 读取在锁内，见 R5.5 性能说明）。
- 新增 `loadedRevision` 实例字段（R2.2）与 `readDiskRevision()` 私有方法；`FlowConcurrentModificationError` 定义见 R2.1。

> ✅ **（乐观并发修订）**：原「已知限制」——`save()` 的锁只互斥「文件写入」，不解决跨进程 load-modify-save 丢失更新——已由本修订的**乐观并发校验**覆盖（见「乐观并发校验」小节 R1-R5）：锁内比对 `meta.revision`，并发 OpenFeel 写入者冲突时报 `FlowConcurrentModificationError`（退出码 2）而非静默覆盖。**能力边界**：不维护 revision 的外部手工改写仍不在检测范围（详见 R1.3）。`save()` 对 flow.json 的保证为：**无半写/损坏、`.bak` 始终为上一有效版本、并发写不产生交错内容、并发写入者冲突报错不覆盖**。

```ts
  restoreCheckpoint(filename: string): boolean {
    // 安全校验：拒绝含路径分隔符或 '..' 的文件名，防止路径穿越
    if (!filename || filename.includes('/') || filename.includes('\\') || filename.includes('..')) {
      return false;
    }
    try {
      const dir = resolve(this.projectPath, '.openfeel', 'checkpoints');
      const filePath = resolve(dir, filename);
      if (!existsSync(filePath)) {
        return false;
      }
      const content = readFileSync(filePath, 'utf-8');
      // 校验快照 JSON 合法性，非法内容拒绝恢复
      JSON.parse(content);

      const lockPath = projectLockPath(this.projectPath, 'flow');
      let conflict = false;
      withFileLock(lockPath, () => {
        // 乐观并发校验：磁盘被并发修改时拒绝恢复，防止覆盖他人写入
        const diskRevision = this.readDiskRevision();
        if (diskRevision !== this.loadedRevision) {
          conflict = true;
          return;
        }
        // 快照 revision 重定基为 diskRevision+1，保证单调递增
        const restored = JSON.parse(content) as FlowData;
        restored.meta.revision = diskRevision + 1;
        const restoredContent = JSON.stringify(restored, null, 2) + '\n';
        // REV-002：与 save() 同锁、同 S5 语义（写前复制旧文件为 .bak，写后不覆盖）
        atomicWriteFileSync(this.filePath, restoredContent, { backup: true });
      });
      if (conflict) {
        console.warn('[WARN] flow.json 已被其它进程修改，拒绝从快照恢复（请重新加载后重试）');
        return false;
      }

      this.load();
      return true;
    } catch {
      return false;
    }
  }
```

export function createScheme(projectPath: string, stageName: string, title: string): string {
  // 解析 stageId（短名/完整）得到 series + stageDir + 完整 ID
  const parsed = parseStageId(stageName);
  if (!parsed) {
    throw new Error(`非法阶段名: ${stageName}（应为 stage-NN 或 vX.Y.Z.W-stage-NN）`);

  const safeTitle = title.replace(/\s+/g, '_');

  const opId = withFileLock(lockPath, () => {
    const reserved = reserveSequence({
      dir: opsDir,
      candidate: (seq) => `${opIdOf(seq)}_${safeTitle}.md`,
      parse: (fileName) => {
        const m = fileName.match(/^op-(\d+)/);
        return m ? parseInt(m[1], 10) : null;
      },

    atomicWriteFileSync(reserved.path, content);
    return opIdOf(reserved.seq);

  projectPath: string,
  category: string,
  title: string,
  content: string,

  // 校验分类有效性
  if (!CATEGORIES.includes(category as (typeof CATEGORIES)[number])) {
    throw new Error(`无效分类 "${category}"，有效值：${CATEGORIES.join(', ')}`);
  }

    initKnowledgeBase(projectPath);
  }

  const today = new Date().toISOString().slice(0, 10); // YYYY-MM-DD
  const catPath = resolve(kbDir, `${category}.md`);

  const entryText = `\n## [+] ${title} (${today})\n\n${content}\n`;

  const lockPath = projectLockPath(projectPath, 'kb');

    // 分类文件：读 → 拼接 → 原子写（替代 appendFileSync，避免半写）

  });

## 乐观并发校验（乐观并发修订）

> 背景：本 op 原步骤 2 已声明 `save()` 的写锁只互斥「文件写入」，不解决跨进程 load-modify-save 丢失更新。经用户拍板，本修订在 `flow.json` 引入 **乐观并发校验**，将「静默覆盖」转为「冲突报错」。本节新增内容均标注「（乐观并发修订）」。

### R1. revision 标识设计

**字段选择：`meta.revision`（整数，单调递增）**

| 候选 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| `meta.revision` 整数 | O(1) 比较；可读可调试（cat flow.json 直接可见）；错误信息可给出期望/实际版本号；天然贴合已有 `meta` 对象（version/project/updated） | 需存量兼容（缺失→0）；仅能发现「遵循 revision 约定」的写入者 | ✅ 采用 |
| `meta.rev` 短名 | 同上 | 命名不一致（`meta` 下既有字段均为完整单词 version/project/updated） | 否 |
| 内容哈希（raw 的 sha256） | 无需 schema 变更；能发现任意外部改写 | 每次 load/save 需读全文并哈希；外部工具重排 JSON/换行即假冲突；错误信息无法给出版本号；无法表达「递增」语义 | 否（列为备选，见 R1.3） |

**R1.1 字段位置与类型**
- `FlowData.meta` 增加可选字段 `revision?: number`（可选 = 兼容存量）。
- 精确位置：`src/core/flow-manager.ts:101`，改为：
  `meta: { version: string; project: string; updated: string; revision?: number };`

**R1.2 存量兼容（无 revision 的旧 flow.json）**
- 读侧：`extractRevision(data)` 对非整数/缺失一律返回 `0`（降级为 0）。
- 写侧：首次 `save()` 时 `next = loadedRevision + 1` → 存量文件首次保存后写为 `revision: 1`（即「首次 save 时补写」策略，**无需一次性迁移**）。
- `repair()`：补全缺失 `meta.revision` 为 0（计入 changes），并在实际写盘时 +1（见 R2.5）。
- `initFlow()`：新文件直接写 `revision: 0`（见 R2.6）。
- 结论：存量文件在下一次由 FlowManager 写入时自动获得 revision。

**R1.3 已声明的能力边界（诚实标注）**
- revision 校验只能发现「同样通过 `FlowManager.save()` 写入并维护 revision」的并发写者（这正是多 Agent / 多 CLI 进程的主场景）。
- 若有人**手工 edit flow.json 且不递增 revision**，旧快照写入者仍可能覆盖——此类外部改写无法被 revision 发现（哈希方案可发现但代价见上表）。因此约定：**flow.json 的一切写入必须经 FlowManager**（与既有审计表一致）。
- 内容哈希作为后续增强项，若需检测外部改写可在 stage-36+ 叠加（保留 `revision` 不变）。

**R1.4 是否需要改 schema 定义**
- `src/core/pipeline-schema.ts` 只定义 `pipeline.yaml` 的 `PipelineConfigSchema`（第 63-69 行），**不涉及 flow.json**，故本修订**不改 pipeline-schema.ts**。

/** flow.json 乐观并发冲突：磁盘 revision 与本次加载时不一致（存在并发写入） */
export class FlowConcurrentModificationError extends Error {
  /** 本次实例加载时的 revision */
  readonly expectedRevision: number;
  /** 锁内读到的磁盘当前 revision */
  readonly actualRevision: number;

  constructor(expected: number, actual: number) {
    super(`flow.json 并发冲突：期望 revision=${expected}，磁盘为 ${actual}（已被其它进程修改）`);
    this.name = 'FlowConcurrentModificationError';
    this.expectedRevision = expected;
    this.actualRevision = actual;
  }
}

export function isFlowConcurrentError(err: unknown): err is FlowConcurrentModificationError {
  return err instanceof FlowConcurrentModificationError
    || (typeof err === 'object' && err !== null && (err as { name?: string }).name === 'FlowConcurrentModificationError');

**R2.3 `save()` 改造（275-332 行）——改造前 → 改造后**

> **（REV-103 修订）最终代码已内联在「步骤 2」；本节保留设计说明与对照。若本节与步骤 2 不一致，以步骤 2 为准。**

- 改造前：序列化在锁外，`withFileLock` 内仅 `atomicWriteFileSync`（无 revision 概念）。
- 改造后（整体替换步骤 2 的方法体）：

```ts
  /** 保存 flow.json（自动更新 meta.updated；锁内做乐观并发校验、备份旧版本并原子写） */
  save(): void {
    if (!this.data) {
      return;
    }
    this.data.meta.updated = new Date().toISOString();

    // 创建清理后的副本：去除 op 中的 id 字段（id 由 stages.{stageId}.ops 的键名决定）
    const serializable = JSON.parse(JSON.stringify(this.data)) as FlowData;
    for (const stage of Object.values(serializable.stages)) {
      for (const op of Object.values(stage.ops)) {
        delete (op as unknown as Record<string, unknown>).id;
      }
    }

    const lockPath = projectLockPath(this.projectPath, 'flow');
    try {
      withFileLock(lockPath, () => {
        // 乐观并发校验：锁内读磁盘 revision，与加载时比对；不一致说明有并发写，拒绝覆盖
        const diskRevision = this.readDiskRevision();
        if (diskRevision !== this.loadedRevision) {
          throw new FlowConcurrentModificationError(this.loadedRevision, diskRevision);
        }
        const nextRevision = this.loadedRevision + 1;
        serializable.meta.revision = nextRevision;

        // S5：写前复制旧文件为 .bak；写成功后不覆盖 .bak，使其始终保留上一版本
        const content = JSON.stringify(serializable, null, 2) + '\n';
        atomicWriteFileSync(this.filePath, content, { backup: true });

        // 同步内存与加载基线，避免同实例连续 save 误判冲突
        this.data!.meta.revision = nextRevision;
        this.loadedRevision = nextRevision;
      });
    } catch (err) {
      console.error(`[ERROR] flow.json 保存失败: ${err instanceof Error ? err.message : err}`);
      throw err;
    }
  }

  /** 读取磁盘当前 revision（不存在/损坏/缺失 → 0，兼容存量文件） */
  private readDiskRevision(): number {
    try {
      const raw = readFileSync(this.filePath, 'utf-8');
      const parsed = JSON.parse(raw) as { meta?: { revision?: unknown } };
      const rev = parsed?.meta?.revision;
      return typeof rev === 'number' && Number.isInteger(rev) ? rev : 0;
    } catch {
      // 文件不存在或损坏：视为 0（首次写入 / 由 repair 兜底）
      return 0;
    }
  }
```

**关键点**：
- 锁内新增一次 `readFileSync + JSON.parse`（文件小，开销可忽略）；**序列化（`JSON.stringify`）从锁外移入锁内**——因为 revision 必须随内容一起原子落盘，无法在锁外确定。这是本修订对步骤 2「序列化在锁外」的**有意调整**（见 R5.5 性能说明）。
- 冲突时**不写盘、不备份**，直接抛错，`loadedRevision` 保持不变，调用方可重新 load 后重试。
- 成功写入后同步 `this.data.meta.revision` 与 `this.loadedRevision`，支持同一实例连续 `save()`。

## 困难点说明

1. **flow.json 的「丢失更新」边界（已由乐观并发修订解决）**：原 `save()` 的锁只互斥「文件写入」，不防止跨进程 `load → modify → save` 覆盖。本修订在锁内引入 `meta.revision` 乐观校验：磁盘 revision 与加载基线不一致时抛 `FlowConcurrentModificationError`，将「静默覆盖」转为「冲突报错」，并给出退出码 `2` 供自动化重试。**能力边界**：仅覆盖遵循 revision 约定的 OpenFeel 写入者；不维护 revision 的外部手工改写仍可能被覆盖（R1.3）。**性能**：`save()` 锁内新增一次 `readFileSync + JSON.parse`，且序列化移入锁内；flow.json 体积小（约数十 KB），实测影响可忽略。
2. **全局配置读-改-写的丢失更新**：`recordProjectLang` 的「读全局配置 → 改 → 写」跨进程仍可能丢失（低概率）。本阶段仅对写入加锁 + 原子写，不重构读改写；记录为遗留风险。
3. **`commands/stage.ts` 的锁粒度**：按 `stage-{NN}` 派生 `status-{stageDir}.lock`，不同阶段并发写互不阻塞；同阶段串行。
4. **锁不嵌套**：`scheme`/`stage`/`merge` 的 flow 同步均只调用 `FlowManager.save()`（其内部取一次 `flow.lock`），调用点不额外取 flow 锁，避免同进程自锁超时。

## 遗留风险（回填计划「遗留风险」）

1. **flow.json 丢失更新**：并发 OpenFeel 写入者已由 `meta.revision` 乐观校验拦截（冲突报错、退出码 2）。遗留：不维护 revision 的外部手工改写无法检测（约定所有写入走 FlowManager）；如需覆盖可 stage-36+ 叠加内容哈希。
2. **全局配置读-改-写丢失更新**（见困难点 2）——低概率，后续可加「锁内读改写」辅助函数。
3. **性能**：每次 `save()` 增加一次 `fsync + rename + 加解锁`（实测原子写 P99 ≈ 5.22ms、加解锁开销 < 1ms）；乐观并发修订额外增加一次锁内读盘 + `JSON.parse`（文件小）；只读命令（`flow status`）不受影响。
