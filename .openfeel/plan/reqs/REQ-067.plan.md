> 依据：`.openfeel/plan/v1/stage-133/plan.md` §一（正文原编号 **A67.1–A67.4**）与 §二 R7（步 D12）。本文件只做需求级拆解，**不改判据、不新增需求外任务**。
> **2026-11-24 修订（REV-P08 / REV-P05）**：判据按正文原编号重排——A67.1＝wrapper 内容命中 → class 1/2 拒绝**并审计**、A67.2＝普通 wrapper 不受影响（回归）、A67.3＝**不可读脚本 → class 4 warn + 审计含 `wrapper` 与目标路径（`scriptPath`）**、A67.4＝**≥6 条用例**（含编码混淆 UTF-16/GBK）。原稿把「内联 payload 回归」当 A67.3、「审计」当 A67.4 的编号作废；A67.3 的审计字段（`wrapper`/`scriptPath`）本轮补为硬断言。

## 目标

- **目标**：封掉 guard 的 wrapper 绕过面——`pwsh -File`、`cmd /c`、`bash -c`、`node -e` 等包装执行时，静态读取脚本内容并按其内容分类（openfeel 写动词 / 受保护路径），不可判定也留审计。
- **现状证据**：现网只覆盖**内联** payload：`matchInlineInterpreter`（`dsh/lib/guard.js:1506`，`node -e`/`python -c`）与 `extractWrapperPayload`（`:1538`，`bash -c`/`pwsh -Command`），配 `payloadIsUnresolvable`（`:1562`）与 `WRAPPER_MAX_DEPTH=4`（`:1250`）；`-File`/`/c x.cmd` 这类**读文件执行**的形态全仓无处理 → 落到第 4 类 `undecidable`，而第 4 类缺省是 `warn` 放行（`SHELL_GATE_UNDECIDABLE='warn'`，`:91`）。这就是 v1.6.0 用 `.ps1` 包装脚本调 CLI 能绕过 shell gate 的原因（REQ-067 摘要）。
- **边界**：只加「读脚本内容」这一层；`SHELL_GATE_DECIDABLE='deny'`/`SHELL_GATE_UNDECIDABLE='warn'` 档位语义与 `resolveShellGate`（`:108`）不改；`strict` 档下 `undecidable` 仍拒；**零外部依赖**（`dsh/package.json` 现无 `dependencies`）。

## 验收判据

判据沿用**需求正文原编号**（只增不改），本需求对应 **A67.1 / A67.2 / A67.3 / A67.4**。必跑命令：

```bash
cd dsh && node test/guard.js             # A67.1—A67.4 四组新用例（≥6 条）+ 既有用例全绿
cd dsh && node test/guard-isolation.js   # 回归：隔离层未被污染
node bin/openfeel.js lint i18n
```

- **A67.1**：`pwsh -File write-openfeel.ps1`（内含 `openfeel req body`）→ `deny`（class 1）；`pwsh -File set-content-src.cmd` / `cmd /c set-content-src.cmd`（含 `openfeel dev clean` 或写 `src/**` / `.openfeel/flow.json`）→ `deny`（class 1/2）；内联 `bash -c "openfeel archive create …"`、`node -e "require('fs').writeFileSync('src/x.ts','')"` 命中同样 `deny`；**拒绝时** `.openfeel/log/guard-audit.jsonl` 增行含 `event:'guard_deny'` 与 `kind:'class1'|'class2'`。
- **A67.2**：普通 wrapper 不受影响——`pwsh -File readonly.ps1`、`pwsh -File build.ps1`（无 openfeel 写、无受保护路径）→ `allow` 且**不写 deny 审计**；`node -e "console.log(1)"` → `allow`（不误杀，既有 `:1220` 口径）；既有非 wrapper 用例零改动仍绿。
- **A67.3**：脚本不可读 / 超 `MAX_SCRIPT_BYTES` / 编码不明（`bin.dat`、`gbk-write.cmd`）→ 决策 `warn`（第 4 类，`SHELL_GATE_UNDECIDABLE`）**且必须写审计**：`event` 为审计事件、`kind:'undecidable'`、**`detail.wrapper`**（如 `'pwsh -File'`/`'cmd /c'`，缺失即失败）、**`detail.scriptPath`**（解析后的绝对路径，缺失即失败）、`detail.reason` 非空；`strict` 档下同例仍 `deny`。
- **A67.4**：新增 **≥6 条**独立 guard 用例，且用例数有断言（不靠人工数）：`.ps1` 命中 deny / `.cmd` 命中 deny / `bash -c` 命中 deny / `node -e` 命中 deny / **编码混淆**（UTF-16LE+BOM 的 `.ps1` 解码后命中 → deny；GBK 的 `.cmd` → undecidable + 审计）/ 普通脚本 → allow；fixture 全在 `dsh/test/fixtures/wrapper/`。

## 风险

- **误杀正常脚本**：把 `readonly.ps1`、`build.ps1`、`npm run build` 包装判成写操作，agent 日常操作被 deny → 用户被迫关档位（等于门禁失效）。规避——分类只认三类（openfeel 写动词 / 可解析写目标 / 受保护路径），复用既有判定函数，**不新增启发式关键字**；`A67.2` 保留只读反例。
- **递归放大**：脚本套脚本（`bash -c 'bash -c …'`）会放大扫描成本。规避——沿用 `WRAPPER_MAX_DEPTH=4`（`:1250`）与 `MAX_SCRIPT_BYTES`；触顶即 `undecidable`，不抛错。
- **脚本文件本身已是 class 2**：`SOURCE_EXTENSIONS` 含 `.ps1`（`:264`），所以「写脚本」已被拦；本任务补的是「**执行脚本**」的读取面。两者不得混为一谈（否则会误以为已覆盖）。
- **不可判定被静默**（本轮重点，REV-P08）：第 4 类若只 `warn` 不审计，等于把 v1.6.0 的绕过面换个形式保留。规避——`undecidable` 必须写审计行且 **`wrapper`/`scriptPath` 为非空断言**（不是「含某字符串」），`verify` 用 `guard-audit.jsonl` 取证。
- **编码混淆用例被跳过**：Node 的 `TextDecoder('gbk')` 在 ICU 裁剪环境可能不可用。规避——GBK fixture 的**期望结果就是 `undecidable`**（warn + 审计），不依赖 GBK 能否解码；UTF-16 走 BOM 分支（无 ICU 依赖），因此两条编码用例在任何 Node 构建下都可判定。
- **同文件冲突**：与 REQ-062 改同一文件，若并行会互相覆盖。规避——严格按阶段计划 §三顺序（B3/B4 在前，D12 在后），派单时写明「只改 wrapper 段 `:1498-1620`，不动 `:2929-2943` 与 `:279`/`:348`/`:445`」。
