## 心得建议

1. **审查纪律须上溯为前置规则，而非事后补救**：事后「可信度声明」方向正确但已晚；把四条纪律写进 reviewer agent 模板（随会话自动加载）+ Feel 首轮健康探测，把「坏会话产出结论」的窗口前移闭合。这是 stage-48 事件 A 的核心范式。
2. **「修复有效」须有因果证据**：隔离缺口在本机不触发时，「测试全绿」零信息量。**干净机器模拟**（移出真实文件）证明「CI 上不写」，**对照实验**（移除 mock 块）证明「是 mock 让它不写」——两步合起来才排除假通过。
3. **守卫的设计目标是「不漏检 + 不误报」**：ABSENT→ABSENT 通过（干净 runner 不误报）、只比 sha256 不比 mtime（touch 不误报）、三态可捕获；快照点必须紧贴被测命令（窗口外 step 的写入会漏检）。
4. **一次性数据清理 = 可逆性工程**：末段匹配（避免字面前缀 0 命中假性通过）+ 计数断言（避免空跑通过）+ 隔离副本先行 + 时间戳备份 + 复核可还原性；「删干净」不如「删对了且能还原」。
5. **`profile.yaml` 非法态：不覆盖才是保护**：解析失败属用户可修复态，用默认值整体覆写是不可逆伤害 → `parseError` 标记 + 跳过写回 + 响亮告警；且不因此引入跨模块依赖边（`console.warn` 而非全局状态写入）。
6. **REV 状态行滞后要用「实测快照 + 缩减提请」处理**：op-004 的提请表基于撰写时快照，3/5 已失效；schemer 以 `rg` 实测缩减为 2 条有效并留痕失效项，避免对已 closed 状态行提请同步的自相矛盾审计记录。
