# 对 OpenFeel 的理解

> 基于 DateKit 全流水线实战经验
> 日期：2026-06-28

---

## 一、OpenFeel 是什么

OpenFeel 是一个**多 Agent 协作的软件开发流水线体系**。它通过一个总统领 Agent（Feel）调度多个专业化下游 Agent，按照「计划→方案→编码→审查→测试→归档」的标准流水线完成软件开发任务。

核心思路是将软件工程的最佳实践（分阶段、交叉审查、测试门禁、知识归档）固化为 Agent 协作流程，让多模型协同完成从需求到交付的完整闭环。

## 二、架构模型

### 2.1 角色体系

```
                        Feel（总统领）
                       /    |     |    \
                      /     |     |     \
                Planner  Schemer  Executor  Reviewer  Tester  Archiver
                (推理)   (推理)   (快速)    (异种推理) (推理)    (推理)
```

| Agent | 模型类型 | 核心职责 |
|-------|:------:|----------|
| **Feel** | 主力推理模型 | 全局调度、理解用户意图、推进流水线、决策流程分支 |
| **Planner** | 推理模型 | 制定分期大纲和工作阶段划分，产出 plan.md |
| **Schemer** | 推理模型 | 将工作阶段拆解为极细粒度操作方案，Executor 无需决策即可执行 |
| **Executor** | 快速模型 | 严格按操作方案编码实现 + 自测，追求速度 |
| **Reviewer** | 异种推理模型 | 交叉审查计划/方案/代码，避免同模型盲区 |
| **Tester** | 推理模型 | 正式测试验收，与 Executor 自测分离，提交和管理 Bug |
| **Archiver** | 推理模型 | 归档阶段产出，提取可复用知识写入知识库 |

### 2.2 模型分层策略

OpenFeel 的模型选择策略有明确的分层逻辑：

1. **Feel 用主力推理模型**：全局调度需要深度理解和决策能力
2. **Planner / Schemer / Reviewer / Tester / Archiver 用推理模型**：计划、方案、审查、测试、归档都需要深度思考
3. **Executor 用快速模型**：编码实现追求速度，严格遵循方案而不需要架构决策
4. **Reviewer 用异种推理模型**：与主力模型不同系列，避免「自己审自己」的盲区

### 2.3 三层计划体系

```
分期大纲 (roadmap/v1.0.md)        ← 宏观：版本级目标与里程碑
  └── 工作阶段 (stages/stage-01/)  ← 中观：阶段任务分解与状态管理
        └── 操作方案 (ops/op-xxx.md) ← 微观：Executor 可直接执行的步骤
```

每一层都是上一层的细化，确保从高层目标到底层执行的无损传递。

## 三、流水线状态机

### 3.1 核心状态

```
plan_pending → plan_done → ready_for_code → coding → ready_for_review
                                                   ↓
                                            review_failed ←→ review_passed
                                                   ↓              ↓
                                            bug_fixing    ready_for_test
                                                   ↓              ↓
                                            review_passed   testing
                                                   ↓              ↓
                                                   └────→ done ←─┘
                                                           ↓
                                                     archive_done
```

### 3.2 状态驱动机制

流水线推进不是基于时间或人工指令，而是**基于状态驱动**：

1. 每个阶段的状态记录在 `flow.json` 和 `status.md` 中
2. Feel 读取状态，判断当前阶段和下一步该做什么
3. 调度对应的 Agent 执行任务
4. Agent 完成任务后更新状态，Feel 继续读取并推进

### 3.3 自动 vs 人工模式

| 模式 | execution_mode | auto_advance | 行为 |
|------|:--:|:--:|------|
| 全人工 | manual | disabled | 每个阶段需人工确认后才推进 |
| 半自动 | auto | disabled | Agent 接管但需人工推进 |
| 全自动 | auto | enabled | Agent 按状态机自动推进全链路 |

级联优先级：`用户指令 > status.md 局部覆盖 > config.yaml defaults`

## 四、工作区设计

### 4.1 公共域 vs 私域

```
.openfeel/
├── 公共域（纳入版本管理）
│   ├── dev/            # 核心规则 + 进度状态
│   ├── log/            # 团队级重要事件日志
│   ├── code_review/    # 公共审查摘要
│   ├── bugs/           # 公共 Bug 摘要
│   ├── plan/           # 计划体系（三层）
│   ├── kb/             # 知识库
│   └── tmp/            # 临时文件
│
└── 私域（.gitignore）
    └── users/{username}/
        ├── dev_last.md     # 跨会话状态恢复
        ├── log/            # 个人操作日志
        ├── note/           # 个人笔记
        ├── code_review/    # 详细审查记录
        ├── bugs/           # 详细 Bug 报告
        └── tmp/            # 个人临时文件
```

**设计原则**：
- 公共域存结论摘要，私域存过程细节
- 公共域纳入版本管理供团队查阅，私域不纳入避免冲突
- 知识从私域提炼后归入公共域

### 4.2 级联配置覆盖

```
用户直接指令（最高优先级）
    ↓ 覆盖
status.md 局部配置
    ↓ 覆盖
config.yaml defaults（全局默认）
```

这确保了全局一致性（所有阶段有统一默认值），同时允许阶段级灵活性（特殊阶段可覆盖）和用户最终控制权。

## 五、经验暂存与知识库自动归档

### 5.1 经验暂存

每次会话结束时，Agent 将本会话的**关键经验**暂存到 `dev_last.md` 的「经验暂存」区域：

```markdown
## 经验暂存
- [ ] `troubleshooting`：diffDays 类型校验缺失的教训
- [ ] `patterns`：错误处理一致性模式
```

### 5.2 知识归档

下次会话启动时，Agent 读取 `dev_last.md`，提醒用户确认未归档的经验，然后写入对应的知识库分类文件：
- `architecture.md` — 架构决策
- `patterns.md` — 代码模式
- `troubleshooting.md` — 排查经验
- `setup.md` — 环境配置

这确保了 Agent 的经验不会随会话丢失，知识库随项目持续增长。

## 六、从 DateKit 实战看 OpenFeel 的价值

### 6.1 自动化但不失控

DateKit 项目全程在 auto 模式下运行，Feel 自动推进了 6 个阶段，调度了 8 次 Agent 调用。**唯一一次"中断"是审查不通过**——这是设计之中的质量门禁，而非系统故障。自动推进不会跳过质量检查。

### 6.2 交叉审查的真实价值

Reviewer（异种推理模型）发现了 Executor 自测未能发现的 HIGH 问题——diffDays 的类型校验缺失。这说明：

1. **Executor 自测 ≠ Review**：Executor 追求执行速度，自测是"按清单检查"，而 Reviewer 是"从多个维度交叉审视"
2. **异种模型确实有价值**：不同的模型系列有不同的"视角"，能够发现同一模型系列可能忽略的问题

### 6.3 知识沉淀的即时性

DateKit 一个简单工具库的开发，最终产出了 12 条知识条目，覆盖架构决策（ESM + UTC 策略）、代码模式（错误处理一致性）、排查经验（类型校验缺失教训、coverage-v8 兼容性）、环境配置（vitest 配置要点）。这些知识如果不被系统性地捕获，很可能在下一次开发中重蹈覆辙。

### 6.4 方案先行减少执行偏差

Schemer 制定的操作方案包含了**完整的代码模板**和精确到文件级别的步骤，Executor 几乎是在"抄写"代码而非"编写"代码。这带来两个好处：
1. 执行速度快（不需要思考和决策）
2. 结果可预测（严格遵循方案，偏差极小）
