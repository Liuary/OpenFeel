# DateKit 开发中的问题与建议

> 基于 OpenFeel 全流水线 DateKit 开发实战
> 日期：2026-06-28

---

## 一、流程中发现的问题

### 问题 1：审查阶段发现的 HIGH 级别 Bug（REV-002）

**现象**：`diffDays` 函数使用了简化的参数处理逻辑 `d instanceof Date ? d : new Date(d)`，导致 `null`、`123`、`undefined` 等非预期类型被静默接受，而 `format` 和 `addDays` 使用了正确的三段校验（`instanceof → typeof string → throw TypeError`）。

**根因分析**：
- Executor 在实现 diffDays 时未参考同项目中已有的参数校验模式
- 测试覆盖存在盲区——未测试非 Date/string 类型的输入
- 方案（op-002）中对 diffDays 的参数处理描述可能不够明确

**修复**：通过 op-004 修复方案，统一了四个函数的参数校验模式。

**教训**：
1. 同一项目内接受相同签名的函数必须使用**完全一致**的校验逻辑
2. 测试必须覆盖参数类型校验的所有分支，而不仅是正常路径
3. 审查时应将「模式一致性」作为独立的审查维度

---

### 问题 2：vitest 主包与 coverage provider 版本兼容性

**现象**：安装 `@vitest/coverage-v8@latest`（4.x）与 `vitest@3.0.0` 不兼容，导致 `vitest run --coverage` 执行失败。Executor 在 op-003 执行时自行安装该包时发现了此问题，锁定了 `3.0.0` 版本。

**根因分析**：
- 方案 op-001 的依赖声明中遗漏了 `@vitest/coverage-v8` 包（REV-001）
- vitest 的 coverage provider 包与主包存在主版本号强绑定关系

**建议**：
1. 方案制定时应明确写出所有隐式依赖（如 vitest.config.ts 中 `provider: 'v8'` 会触发对 `@vitest/coverage-v8` 的依赖）
2. 依赖版本应锁定精确版本，且与主包版本号对齐

---

### 问题 3：方案与实际执行之间的偏差

**现象**：op-001 中声明了 3 个依赖（typescript / vitest / @types/node），但实际执行时 Executor 额外安装了 `@vitest/coverage-v8`（因为 vitest.config.ts 中配置了 coverage provider）。方案与实际状态不一致。

**建议**：可以考虑在方案执行后增加一个「方案一致性回写」步骤——如果 Executor 在执行中发现方案遗漏，自动更新方案文件补齐声明。

---

### 问题 4：NodeNext 模块解析的 .js 扩展名要求

**现象**：TypeScript `moduleResolution: "NodeNext"` 模式下，ESM 导入路径必须带 `.js` 扩展名（如 `import { format } from './format.js'`），否则 `tsc --noEmit` 报错。

**影响**：这不是一个 Bug，但很容易被开发者忘记。DateKit 项目中方案已经明确了这一点，所以没有出错，但如果方案不明确，很容易导致编译失败。

**建议**：在知识库 `setup.md` 中记录这一要求，并在新项目初始化时自动检查导入路径是否带 `.js` 扩展名。

---

### 问题 5：流水线时间戳不连续

**现象**：在 `flow.json` 的 log 和 reviews 记录中，时间戳存在不连续情况。例如 Plannner 的 `plan_done` 时间是 `12:30`，但 Reviewer 的 `review_failed` 时间也是 `13:00`，而中间还有 `12:46` 的 `review_passed` 记录。这是由于多个 Agent 在各自上下文中独立记录时间戳造成的。

**影响**：轻微。不影响功能，但让日志阅读者困惑。

**建议**：可以考虑让 Feel 在收到 Agent 结果后统一记录时间戳，而不是由各 Agent 自行记录。

---

### 问题 6：REV-001（方案级问题）无法在代码修复流程中关闭

**现象**：REV-001 是关于方案 op-001 缺少依赖声明的问题。因为它是方案级（而非代码级）问题，修复它需要修改 `.openfeel/plan/stage-01/ops/op-001.md`，但 op-004 修复方案只覆盖了代码文件。所以 REV-001 保持 pending 状态，留待后续关闭。

**建议**：建立方案级 REV 的修复流程。可以新增一类操作方案（如 `op-fix-scheme-xxx.md`），专门用于修复方案文件中的问题。

## 二、对 OpenFeel 体系的建议

### 建议 1：增加「模式一致性」作为审查的独立维度

当前审查维度：正确性、规范性、安全性、完整性、一致性。但 REV-002 的经验表明，「一致性」不仅指与外部架构一致，还应包括**项目内部模式一致性**——即同一项目中相似功能的代码是否遵循相同的实现模式。

**具体建议**：将「一致性」拆分为两个子维度：
- **外部一致性**：与项目架构、技术栈的一致性
- **内部模式一致性**：同一项目中相似函数的实现模式是否统一（如参数校验逻辑、错误处理风格、UTC 使用方式等）

这可以帮助 Reviewer 更系统地发现类似 REV-002 的问题。

---

### 建议 2：增加方案执行后的「方案一致性回写」

当前流程：方案（Scheme）→ 执行（Code）。如果执行中发现了方案遗漏，需要单独走审查→修复方案→执行流程（如 REV-001 → op-004）。

**具体建议**：在 Executor 完成方案执行后，增加一个自动检查步骤——对比方案声明与实际产出，发现差异则自动更新方案文件。这可以：
1. 保持方案与实际代码的一致性
2. 减少审查中发现「方案与实际不一致」类问题的概率
3. 让后续开发者能信任方案文件的准确性

---

### 建议 3：审查阶段应可以标注「非阻塞性问题」

DateKit 审查中的 REV-004（版本号前缀）是一个 low 优先级问题，不阻塞流水线推进，但当前流程中一旦存在任何 REV pending，就需要先修复才能继续。

**具体建议**：增加 REV 条目的「阻塞」标记：
- `blocking: true` → 必须修复才能通过审查
- `blocking: false` → 不阻塞流程，可在后续阶段修复

这样可以让 low 优先级的非阻塞问题不打断流水线自动推进。

---

### 建议 4：支持知识库检索增强 Agent 决策

当前各 Agent 执行任务时，不会自动查阅知识库中的排查经验。例如，如果有一个新项目也需要配置 vitest + coverage-v8，Executor 可能会再次踩相同的版本兼容坑。

**具体建议**：在 Agent 启动时，自动加载与当前任务相关的知识库条目（如通过关键词匹配），将排查经验和代码模式注入 Agent 的上下文。这可以让知识库真正成为「可执行的记忆」，而不仅是「被动的文档」。

---

### 建议 5：完善 Worktree 并行模式的支持

当前 config.yaml 中 `merge_mode: manual`，worktree 并行模式未启用。对于单阶段项目（如 DateKit）这不成问题，但对于多阶段项目，能够并行执行无依赖的阶段可以显著缩短总时间。

**具体建议**：
1. 在 config.yaml 中增加 worktree 并行模式的开箱即用配置
2. deps.yaml 中增加 `parallel_group` 标记，声明可并行的阶段组
3. Feel 能自动识别可并行的阶段并同时启动多个 Worktree Session

---

### 建议 6：增加流水线可视化

当前流水线状态分布在 `flow.json`、`status.md`、多个 REV 和 Bug 文件中，难以一眼看清全局状态。

**具体建议**：
1. 提供一个 `/opfx:status` 命令，汇总输出当前流水线的完整状态
2. 考虑在 `flow.json` 中增加一个 `summary` 字段，包含当前阶段、待处理 REV 数、测试覆盖率等关键指标的摘要

---

## 三、DateKit 项目本身的后续建议

1. **补充类型导出测试**：当前 `src/index.ts` 使用 `export type { DateFormatPattern }`，但没有验证该类型能否被外部正确导入。建议增加一个简单的类型测试。

2. **增加 ESM 构建验证**：当前只有 `tsc --noEmit` 验证，建议增加 `npm run build`（实际编译到 dist/）并验证产物可被 Node.js 正确导入。

3. **发布准备**：`package.json` 已配置了 `files: ["dist"]` 和 `exports`，如果计划发布到 npm，需要补充 `.npmignore`、`README.md`、CHANGELOG.md 等发布相关文件。

4. **REV-001 关闭**：方案 op-001 中补充 `@vitest/coverage-v8` 的依赖声明。这是唯一的待处理审查问题。

5. **format 函数可扩展性**：当前 `DateFormatPattern` 硬编码为三种模式的联合类型。如果未来需要支持更多模式（如 `YYYY/MM/DD`、`DD.MM.YYYY`），可以考虑使用模板字符串类型或策略模式重构。
