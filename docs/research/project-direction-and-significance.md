# AI_Prompt 项目方向与意义

> 面向 Kilo Agent 的 AI 协作方式模板：把提示词、角色、流程、记忆和验收机制沉淀为可部署、可复用、可审查的工程资产。

## 一、项目定位

AI_Prompt 不是业务代码库，也不是单一提示词合集，而是一套围绕 Kilo Agent 构建的 AI 协作模板项目。它试图解决的问题不是“让 AI 写更多代码”，而是“让 AI 在清晰边界内稳定参与软件工程”。

从仓库内容看，项目由四类核心资产组成：

| 类型 | 代表文件 | 作用 |
|------|----------|------|
| 行为约束 | `AGENTS.md` | 规定 AI Agent 的通用行为边界、编码规范、确认规则和文档规则 |
| 流程规范 | `Kilo/Instructions/kilo_instructions_core.md` | 规定 `.openfeel/` 工作区、计划、日志、知识库、Bug 和审查的运行方式 |
| 角色模板 | `Kilo/agents/*.md` | 将 Architect、Code、AutoRunner、Tester、Debug 等职责拆开 |
| 能力模板 | `Kilo/skills/*/SKILL.md` | 用 Skill 标准化知识库查阅、Bug 获取、阶段状态更新等重复操作 |

因此，本项目的本质是一个“AI 软件工程操作系统”的模板雏形。它把过去散落在个人习惯、临时 prompt 和聊天上下文里的协作方式，整理成可以复制到其他项目的结构化规则与流程。

## 二、项目要解决的核心问题

### 2.1 AI 协作缺少稳定边界

普通 AI 编码会话容易出现几个反复问题：改动范围扩大、过度设计、忘记测试、跨会话丢失上下文、把调试经验混进行为约束。AI_Prompt 用 `AGENTS.md` 和 Kilo Instructions 建立分层约束，让 AI 先知道什么能做、什么不能做、什么时候必须停下来问人。

这种边界设计的价值在于：把“相信 AI”转为“约束 AI 后再使用 AI”。它不是削弱 AI 的能力，而是减少不可控的发挥空间，让 Agent 更像工程团队成员，而不是一次性代码生成器。

### 2.2 项目记忆缺少可追溯载体

AI 编码的另一类问题是记忆不可靠。很多关键经验只存在于某次对话中，一旦上下文压缩或会话结束，约定、排障经验和设计理由就会消失。

本项目通过 `.openfeel/` 工作区把记忆分为公共域和私域：公共域沉淀计划、知识库、团队日志、审查摘要和 Bug 结论；私域保存个人操作状态、详细审查、Bug 追踪和临时笔记。这个设计将 AI 记忆从“模型上下文”迁移到“项目文件系统”，使经验可以被人查看、被 Git 追踪、被下次会话重新加载。

### 2.3 多 Agent 协作缺少职责分离

如果一个 Agent 同时负责计划、编码、审查、测试和验收，就容易产生角色冲突。实现者审查自己的实现，测试者修自己的测试，都会降低问题暴露概率。

AI_Prompt 将人工流程和自动流程拆开：人工流程使用 `architect`、`code`、`ask` 等主 Agent；自动闭环由 `auto-runner` 调度 `code-worker`、`review-worker`、`test-writer`、`tester` 等 Worker Agent。尤其是 AutoRunner 的“一个子计划一个 worktree”设计，避免了自动化流程把同一任务拆散到多个分支，保留了可检查、可合并、可暂停的工程控制点。

## 三、项目方向

### 3.1 从提示词集合走向流程模板

项目当前已经超出“保存好用 prompt”的阶段。它的方向是把 AI 协作抽象成一套流程模板：启动时读取规则，执行中维护计划，编码后进入审查，测试发现问题后进入 Bug 流转，经验沉淀进知识库。

这意味着项目后续不应只追求更多 Agent 或更多 Skill，而应优先提升流程的一致性、可验证性和部署体验。新增能力只有在能减少协作摩擦、提升可追溯性或降低人为操作成本时才值得加入。

### 3.2 从个人经验走向可迁移工程资产

`deploy.py` 和 `DEPLOY.md` 表明项目希望被复制到其他项目中使用。它不是只服务当前仓库，而是作为模板项目为不同业务仓库提供统一 AI 协作底座。

这个方向下，AI_Prompt 的核心竞争力不在某个单点规则，而在迁移后的完整性：目标项目拿到 AGENTS、Instructions、Agent、Skill、`.openfeel/` 工作区和 `.gitignore` 规则后，可以立即形成一套可运行的协作秩序。

### 3.3 从人工辅助走向受控自动闭环

项目没有把“全自动”作为默认目标，而是把人工流程设为默认，把自动闭环设为显式开启能力。只有当子计划状态同时满足 `auto` 与 `enabled` 时，AutoRunner 才能接管后续流程。

这体现了一个清晰方向：自动化要服务于可控交付，而不是替代人的最终判断。Agent 可以实现、审查、测试和修复，但不会自动合并主分支，也不会自动清理 worktree。最终控制权仍保留给开发者。

### 3.4 从一次性产出走向长期知识积累

`.openfeel/kb/` 的定位说明项目重视“经验的结构化复用”。调试流程、架构决策、代码模式和环境搭建经验不再散落在聊天记录里，也不混入 AGENTS 这种行为约束文件，而是进入知识库。

未来方向上，项目可以继续强化知识库索引、阶段复盘和 Bug 根因归档，让每一次 AI 协作都留下可复用的信息增量。

## 四、项目意义

### 4.1 为 Vibe Coding 补上工程纪律

Vibe Coding 强调用自然语言推动软件构建，但它天然存在风险：开发者容易过度信任生成结果，忽略 diff、测试和架构边界。AI_Prompt 的意义在于给这种高速度开发方式加上工程纪律：计划、边界、审查、测试、日志和知识沉淀。

它不是反对 Vibe Coding，而是让 Vibe Coding 更适合真实项目。

### 4.2 降低 AI 协作的隐性成本

AI 工具带来的效率提升，经常被隐性成本抵消：重复解释项目规范、重复告诉 AI 不要越界、重复粘贴调试经验、重复整理 Bug 状态。AI_Prompt 通过模板化文件和 Skill，把这些重复沟通转化为默认流程。

对个人开发者来说，这能减少“每次都要重新训练 AI”的疲惫感。对团队来说，这能让不同成员在同一个项目中使用相近的 AI 协作方式，减少风格漂移和流程分裂。

### 4.3 把 AI 行为纳入版本管理

传统项目会把源码、配置和文档放进 Git，但 AI 的行为规则经常停留在工具设置或个人习惯里。本项目把 Agent 行为、流程规则、知识库和部署方式都文件化，使 AI 协作本身也成为项目资产。

这件事的长期意义很大：团队不仅可以审查代码，也可以审查“AI 是如何参与写代码的”。当一次自动化流程出错时，可以追溯规则、计划、日志和状态，而不是只面对一段不可解释的对话历史。

### 4.4 为多 Agent 工程化提供实验样板

多 Agent 协作容易流于概念：角色很多，但边界不清；流程很自动，但结果难以合并。AI_Prompt 提供了一个更务实的样板：主 Agent 面向人工协作，Worker Agent 面向自动闭环，AutoRunner 只调度不写源码，审查和测试保持独立角色。

这种分工让多 Agent 不只是“多个聊天窗口”，而是接近软件工程中的职责分离、状态机流转和工作区隔离。

## 五、建议保持的建设重点

1. 继续强化部署后的可用性：让目标项目首次部署后能快速完成 `.openfeel/` 初始化、身份识别、知识库索引和状态检查。
2. 继续控制模板复杂度：新增 Agent 或 Skill 前，先判断是否能复用现有角色，避免模板本身变成维护负担。
3. 继续完善文档索引：README 面向快速理解，DEPLOY 面向部署执行，`docs/research/` 面向方向分析和长期思考。
4. 继续沉淀真实使用反馈：把自动闭环失败、Bug 验收反复、知识库遗漏等案例转化为规则或知识库条目。
5. 继续保留人工控制点：自动流程可以推进子计划，但最终合并、清理、架构取舍仍应由人确认。

## 六、结论

AI_Prompt 的项目方向可以概括为：构建一套可部署、可审查、可迭代的 AI Agent 协作模板，让 AI 编码从临时对话走向工程化流程。

它的意义不在于提供某个万能提示词，而在于把 AI 协作中的规则、角色、状态、记忆和验收机制组织起来。对于个人开发者，它提供稳定的个人工作流；对于团队，它提供可共享的 AI 协作规范；对于更长期的软件工程实践，它提供了一个把 AI 行为纳入版本管理和工程治理的实验样板。
