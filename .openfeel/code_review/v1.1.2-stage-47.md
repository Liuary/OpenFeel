## 心得建议

1. **「不覆盖」与「备份后覆盖」是同族命令内的两种正当策略，判据是资产归属**：用户可编辑的项目配置 → 拒绝覆盖（保留用户意图）；框架为唯一权威源的部署物 → 备份后覆盖。混淆两者会在两个方向出错：给用户配置加备份即产生「备份了但没覆盖」的误导性审计条目；给框架资产生效「不覆盖」则模板演进永久失效。
2. **备份接入点必须与覆盖事实同生共死**：「备份是覆盖的前置」——当策略从「覆盖」改为「不覆盖」时，备份接入点连同其 `backed` 条目必须**同批删除**，否则审计链路自相矛盾（REV-002 的 blocking 正源于此）。这是「语义变更须全链路核对」的具体形态。
3. **可编程消费 > 文字免责**：自描述命令与实际接受集合不同源时，把差异既写进人类输出、又导出为 `--json` 字段（`advanceAccepted`），使脚本可预校验；这比「文档里写一句限制」强得多，也避免了强行收敛引发的类型系统连锁改动。
4. **事务顺序是「中间态」的唯一解**：不可逆副作用一律后置到状态落盘成功之后，且由**调用方**执行（core 只返回目标）；审计日志记意图（`purgeTarget`）而非已发生事实（`purged`）。判据可用一句话自检：「若下一步失败，磁盘与状态会否自相矛盾」。
5. **测试的「保存/恢复」是伪隔离**：它以「测试全绿」为掩护长期改写真实用户目录（`config/BUG-004`）。审计要点是 **mtime + hash 双比对**——只比 hash 会漏检。隔离的唯一正解是 `vi.mock('node:os')`（依赖全仓 `homedir` 收敛到 `global-paths.ts`）。
6. **审查官被推翻的判断也要留档**：REV-003③ 的「en 值空串须补全」经 planner 代码级反驳不成立，审查官如实记录「原判断被推翻」——这保持了 REV 链条的可信度，也给后续同类判断留下校准样本。
