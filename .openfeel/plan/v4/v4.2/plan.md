# OpenFeel v0.4.2 — 项目快速架构索引

> 创建于 2026-07-08 | 用户确认：**实施 A+B**

## 一、需求理解

### 1.1 问题陈述

当前 AI Agent 在会话启动时需要多次 glob / grep / read 来理解项目结构，消耗大量 tokens。需要创建一个轻量级的 `.openfeel/architecture-index.md`，让 Feel 用最少 tokens 快速理解项目全貌。

### 1.2 索引内容设计

| # | 字段 | 说明 |
|:--:|------|------|
| 1 | 项目定位 | 一句话描述 OpenFeel 是什么 |
| 2 | 目录结构树 | 关键目录+文件，≤30 行 |
| 3 | 核心模块职责表 | 模块名 → 职责 → 入口文件 |
| 4 | 关键类型/接口速查 | ≤10 个 |
| 5 | 依赖关系拓扑 | 内部模块间依赖 |
| 6 | 技术栈摘要 | 语言/框架/关键依赖 |
| 7 | 最近更新时间 | ISO 日期 |

### 1.3 更新机制设计

1. **归档官归档时自动更新**：Archiver 在每次阶段归档时同步更新索引。
2. **Feel 不一致检测**：Feel 发现索引与项目实际不一致时（如 glob 发现新文件但索引未收录），通知 Archiver 更新。

## 二、可行性分析

### 2.1 项目规模基线

| 指标 | 数值 |
|------|:--:|
| Source 文件（`src/**/*.ts`） | 38 |
| Agent prompt 文件（`.opencode/agents/*.md`） | 8 |
| CLI 命令模块（`src/commands/`） | 10 |
| 核心模块（`src/core/`） | 15 |
| 知识库条目（kb/ 四分类） | 34 |
| 已存在索引/概览文件 | 3 个（kb/index.md、plan/plan_index.md、README.md） |

### 2.2 代价分析

#### 2.2.1 Archiver 新增工作量

当前 Archiver 每次归档已承担以下任务：

```
阶段归档流程（现有）：
  1. 汇总阶段 ops 产出 → 归档摘要
  2. 汇总审查条目 → 归档摘要
  3. 从 closed REVIEW 提取知识条目
  4. kb-dedup 去重 → 写入 kb/ 分类文件
  5. 更新 kb/index.md 最近更新表
  6. 追加 flow.json 日志
  7. 通过 Feel 推进阶段到 done
```

新增「更新 architecture-index.md」需要 Archiver 额外做到：
- **理解代码级模块变更**：当前 Archiver 只处理审查条目和 ops 产出（文本级），不理解代码模块的职责变化。更新"核心模块职责表"需要阅读实际 TS 源码并做语义理解。
- **更新依赖关系拓扑**：模块间的 import 关系变更不会被 ops 或 REVIEW 条目捕获，需要 Archiver 额外扫描 `src/` 目录。
- **维护一致性与时效性**：如果一次归档涉及 5 个 ops 跨越 3 天，索引需要在归档点一次性更新——此时 Archiver 可能已经丢失了变更的上下文。

**预估新增成本：5-10 分钟 / 阶段**。v4.1 共 3 阶段，总计 15-30 分钟额外 Archiver 时间。

#### 2.2.2 索引格式维护

索引中的主观内容（"核心模块职责"、"关键类型速查"）无法自动生成。每次模块重构、文件移动、职责变化都需要人工判断如何更新，这是持续性的认知负担。

#### 2.2.3 文件数量变迁的影响

| 项目阶段 | TS 文件数 | 索引维护难度 |
|----------|:--:|:--|
| 当前（38） | 低 | 但收益也低 |
| 如果增长到 100+ | 高 | 维护成本急剧上升 |
| 如果增长到 200+ | 极高 | 需要自动化生成 |

#### 2.2.4 引入"不一致检测"的隐藏成本

需求中"Feel 发现索引不一致时通知 Archiver"是最大的未解决问题：

- **检测机制是什么？** 如果 Feel 通过 glob 获取实际文件列表、对比索引的目录树——那 Feel **还是做了 glob**，token 节省效果归零。
- **检测的精度？** 文件新增/删除容易检测，但"模块职责变更"、"依赖关系变化"几乎无法自动检测。索引会以"表面一致、实质过时"的状态欺骗 Agent。
- **谁来驱动修复？** 通知 Archiver 更新 → Archiver 需要被 Feel 唤起 → 走完整流水线或 ad-hoc 修复 → 这是一个独立的修复流程，成本不菲。

### 2.3 收益分析

#### 2.3.1 Token 节省估算

**当前典型会话启动（无索引）**：

| 操作 | 调用次数 | 预估 tokens |
|------|:--:|:--:|
| `read /`（项目根目录） | 1 | ~50 |
| `read src/`（源码目录） | 1 | ~30 |
| `glob src/**/*.ts`（文件列表） | 1 | ~100 |
| `read .openfeel/kb/index.md`（知识库入口） | 1 | ~200 |
| `read flow.json`（流水线状态） | 1 | ~80 |
| `read config.yaml`（配置） | 1 | ~150 |
| 按需 grep/read 关键文件 | 2-3 | ~200 |
| **合计** | | **~800** |

**有架构索引后（理想情况）**：

| 操作 | 调用次数 | 预估 tokens |
|------|:--:|:--:|
| `read architecture-index.md` | 1 | ~500 |
| `read flow.json` | 1 | ~80 |
| **合计** | | **~580** |

**净节约：~220 tokens / 会话**

#### 2.3.2 Agent 决策质量提升（理论）

- 减少"遗漏关键文件"导致的错误假设
- 统一的项目认知基线
- 新 Agent（如 Feel 初始调度时）更快进入上下文

#### 2.3.3 收益量化总结

| 指标 | 估值 |
|------|:--|
| 每会话 token 节省 | ~220 tokens |
| 每会话调用减少 | ~5-7 次 glob/grep/read |
| 跨会话上下文恢复加速 | 中等（仍需读 flow.json + status.md） |
| 年化假设（500 次会话）| 节省 ~110,000 tokens |

### 2.4 风险分析

| 风险 | 概率 | 影响 | 缓解难度 |
|------|:--:|:--:|:--:|
| **索引过时** | 高 | 高 — Agent 基于错误信息做决策 | 需可靠的自动检测机制 |
| **过时检测不可靠** | 高 | 中 — 实质过时但表面一致，检测不到 | 无有效缓解（见下文） |
| **与 kb/index.md 冗余** | 确定 | 中 — 两个入口文件，哪个是权威？ | 选一个作为唯一入口 |
| **Archiver 负担过重** | 中 | 中 — 归档质量下降 | 自动化生成代替手动维护 |
| **维护不可持续** | 中 | 高 — 项目增长 3 倍后索引维护成为瓶颈 | 项目达到 100+ 文件时必须自动化 |

#### 核心风险：表面一致但实质过时

假设一个阶段重构了 `FlowManager`，从原来的单 phase 改为多阶段独立状态机（v4.1-stage-03）。索引中"核心模块职责表"对 `FlowManager` 的描述仍是旧的——"管理全局流水线 phase"。但文件路径没变、文件名没变、glob 结果一致。Feel 的"不一致检测"（基于文件列表对比）完全无法发现这个问题。

Agent 读了索引 → 基于旧职责理解调度逻辑 → 做出错误路由决策。这种"静默错误"比没有索引时的多几次 glob/grep 危险得多。

## 三、核心判断：不建议实施

### 3.1 决策逻辑

```
当前项目规模（38 TS 文件）
    ↓
索引维护成本（5-10 min/stage 手动更新 + 不可靠的检测机制）
    vs
Token 收益（~220 tokens/会话）
    ↓
结论：净收益为负（维护成本 > 实际收益）
```

**三个决定性因素**：

1. **规模不匹配**：architecture-index 解决的是"大规模项目首次认知"问题，OpenFeel 当前 38 个源文件远未达到需要索引的规模阈值。`read /` + `read src/` + `glob src/**/*.ts` 只需 3 次调用 ~180 tokens，比读索引文件本身（~500 tokens）还少。

2. **自动检测悖论**："Feel 发现索引不一致"需要 Feel 先做 glob 获取实际文件列表。但如果 Feel 已经 glob 了，为什么还需要索引？检测机制本身消解了索引的价值。

3. **知识库已覆盖**：`kb/index.md` 已是 Agent 的"项目认知入口"（通过 `check-kb` skill 加载），`kb/architecture.md` 已包含架构决策和设计理由。新增 architecture-index 会与现有知识体系冲突，造成"多个真相来源"问题。

### 3.2 适用场景对比

| 场景 | architecture-index 的价值 |
|------|:--|
| 大型单体项目（500+ 文件，深度嵌套） | **高** — 无索引无法快速理解 |
| 中型项目（100-300 文件） | 中 — 有帮助但非必需 |
| 小型项目（< 50 文件） | **低** — glob+grep 已足够 |
| OpenFeel 当前（38 文件） | **极低** — 维护成本超过收益 |

## 四、替代方案

### 方案 A（推荐）：增强 kb/index.md 的"项目概览"能力

> **零新增文件，复用现有 Archiver 工作流**

在现有 `kb/index.md` 顶部增加一个「项目快速概览」节：

```markdown
# 知识库索引

## 项目快速概览

| 维度 | 内容 |
|------|------|
| 定位 | AI Agent 开发流程治理 CLI 工具 |
| 语言 | TypeScript (Node.js ≥20) |
| 核心依赖 | Commander, Zod, YAML, fast-glob |
| 源文件 | 38 个 .ts 文件（src/） |
| Agent 数 | 8 个（feel/planner/schemer/executor/reviewer/tester/archiver/utility） |
| 模块入口 | src/index.ts → cli/index.ts |
| 关键目录 | src/core/（流水线核心）、src/commands/（CLI 命令）、.opencode/agents/（Agent 定义） |
| 最近更新 | 2026-07-08（v4.1 进行中） |

## 分类概览
...
```

**优势**：
- kb/index.md 已是 Archiver 每次归档必须更新的文件，加一个简短表格几乎无额外成本
- 通过 `check-kb` skill 加载，与现有 Agent 启动流程无缝对接
- 单点真相：Agent 只看一个入口文件即可获得完整上下文

**劣势**：
- 不能完全替代目录树扫描（但 38 文件的项目不需要）
- 仍然依赖 Archiver 手动更新部分主观内容

**实施成本**：极低（1 个任务，5 分钟工作量）

---

### 方案 B：CLI 自动生成项目快照

> **零维护成本，100% 准确**

新增 `openfeel project overview` 命令，自动扫描项目并输出结构化的项目概览：

```
src/core/flow-manager.ts       — 流水线状态机核心
src/core/pipeline-schema.ts    — Zod Schema 定义
src/commands/flow.ts           — flow CLI 命令
...
```

Agent 启动时调用 `openfeel project overview` 即可获得实时、准确的项目结构。可通过 Feel 的 bash 工具一键执行。

**优势**：
- 零维护成本（代码驱动，每次运行实时扫描）
- 100% 准确（不会过时）
- 可扩展（后续可加入 git log 最近变更、测试覆盖率等）

**劣势**：
- 需要新增 CLI 命令（~100 行 TS 代码）
- 无法捕获主观信息（"模块职责描述"需要 AI 理解，纯扫描做不到）

**实施成本**：中等（新增一个命令，~100 行代码）

---

### 方案 C：等待项目增长后再评估

不做任何改动。当项目达到以下任一阈值时重新评估：

- TS 源文件 ≥ 80
- `.opencode/agents/` 下 Agent ≥ 15
- 单次会话 glob/grep/read 探索调用 ≥ 15 次
- 有实际案例证明"因缺乏项目概览导致 Agent 做出错误架构决策"

**优势**：零成本，不在过早阶段引入过度工程

**劣势**：如果项目突然快速增长，可能需要紧急补救

---

### 方案 D：方案 A + B 组合 — ✅ 选中

先实施方案 A（增强 kb/index.md，立即见效），再补充方案 B（CLI 自动快照）。

这是最务实的渐进式路径。

## 五、条件性实施计划

> ⚠️ 以下计划仅在用户明确选择忽略上述"不建议实施"建议时启用。

如果用户决定尝试 architecture-index 作为实验，建议按以下单阶段最小可行方案推进：

### v4.2-stage-01：实验性 architecture-index 落地与评估

**目标**：创建 architecture-index.md，接入 Archiver 工作流，运行 2 个阶段后评估 ROI。

| # | 任务 | 说明 |
|:--:|------|------|
| 1 | **定义索引格式 Schema** | 确定 architecture-index.md 的标准格式（标题/节、表格列、Markdown 结构），确保可程序化解析。建议采用 YAML frontmatter + Markdown 正文的混合格式。 |
| 2 | **创建初始索引** | 手工编写第一版 `.openfeel/architecture-index.md`，覆盖需求中的 7 个字段。基于当前 38 个源文件的项目状态。 |
| 3 | **Archiver 更新钩子** | 在 Archiver prompt 中增加"归档完成后检查是否需要更新 architecture-index.md"的步骤。明确触发条件（新增/删除文件 ≥1、模块职责变更）。 |
| 4 | **Feel 不一致检测** | 在 Feel 启动流程中增加：读取索引 → 对比 `glob src/**/*.ts` 的结果 → 文件列表不一致时在 `dev_last.md` 中标记，下次唤醒 Archiver 时附带修复任务。 |
| 5 | **量化追踪** | 在 2 个阶段的实验期内记录：(a) 索引更新次数及耗时 (b) 不一致检测触发次数 (c) 因索引导致的错误决策次数 (d) 实际 token 节省量。 |
| 6 | **实验评估** | 2 阶段结束后根据数据决定：正式纳入 / 降级为方案 A / 放弃并删除索引。 |

#### 修改文件范围

- **新增**：`.openfeel/architecture-index.md`
- **修改**：`.opencode/agents/archiver.md`（增加更新索引步骤）
- **修改**：`.opencode/agents/feel.md`（增加不一致检测逻辑）
- **可能修改**：`.openfeel/kb/index.md`（添加对 architecture-index 的引用）

#### 成功标准（实验期）

| 指标 | 阈值 | 判定 |
|------|:--|------|
| 每阶段索引更新耗时 | < 3 分钟 | 可接受 |
| 索引过时（表面一致）导致错误 | 0 次 | 必须 |
| 不一致检测触发率 | 与实际变更率匹配 | 检测有效 |
| 每会话 token 节省 | > 0 | 基线 |

#### 放弃条件

满足任一即放弃实验，回退到替代方案：
- 索引维护导致 Archiver 遗漏知识库更新（回归）
- 索引过时但检测未触发 ≥ 1 次
- 2 阶段内 net token 节省为负（维护消耗 > 使用节省）
