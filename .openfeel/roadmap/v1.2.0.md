## 目标

### 主题二：flow.json 归档拆分（先行执行）

`flow.json` 单文件 **406280 B / revision 914 / 78 阶段全留 / `log[]` 1313 条**，随版本无限累积；每次 `flow status` / `overview` / Agent 读状态都吞下整文件（污染大模型上下文窗口）；`save()` 每次重写全文件（写放大）。用户诉求原话：「flow 只在一个文件中，应该也要对 flow json 文件进行归档拆分。flow 文件只保留近期事务和未归档事务，已归档的历史信息按版本号归档到归档 flow json 文件中。这个流程也是 CLI 控制的，避免读取污染大模型上下文窗口。」

1. **归档粒度 = 版本**：stageId 前缀 `vX.Y[.Z]`（`parseStageId` 既有解析）；该版本全部阶段 `done`（版本收官）后，把该版本 `stages` 段 + 对应 `reviews` + `log` 段移入独立归档文件。
2. **归档落点**：`.openfeel/flow-archive/{version}.json`（新建；与既有 `openfeel archive`（**阶段**归档，输出 `.openfeel/log/archive-{stage}.md`）职责分离）。
3. **命令面（CLI 控制）**：`flow archive <version>`（执行归档，含 `--dry-run`）/ `flow archive list` / `flow archive show <version> [--json]`（按需读取，**不进常规路径**）。
4. **机制一致**：归档写盘复用 `withFileLock` + 原子写 + 审计；flow.json 变更走既有 `save()`（revision 乐观锁 + `.bak`）。
5. **跨版本依赖**：`flow.json.meta.archived_versions` 轻量索引——新 stage 依赖已归档版本时，`plan stage add --deps` 校验将其视为**已满足**（展示层不读归档）。
6. **不自动归档**（不挂 advance 钩子）：触发 = 显式命令，可预览、可审计、可回滚。

### 主题一：需求流转系统

现状为线性计划范式：一个版本 = 一串阶段跑完，版本内若干需求**无独立身份 / 生命周期 / 排期 / 认领**。引入四层模型：`版本 roadmap → 需求 REQ-NNN → 计划 stage(15-phase) → 方案 op`。**需求 = 排期与调度层**（可指定预估版本号）；**计划 = 对某项明确需求的具体实现**。

1. **双层状态模型**：需求层粗粒度状态 `draft → scheduled → in_progress → done`（+ `blocked` / `cancelled` / `rejected`）；`in_progress` 内部进度**由关联阶段的 15-phase 聚合**（工序单一事实源仍在 `phase`，对齐 ADR-003）。
2. **需求 done = 全部关联阶段 done**：聚合判定并**同事务回写**（复用 `save()` 锁与事务）。
3. **存储**：`flow.json` 顶层新增 `requirements` 字段（类比 `reviews`）；正文落 `.openfeel/requirements/REQ-NNN.md`（人读副本，机读权威恒为 flow.json）。
4. **需求↔计划 1:N**：`stage.requirement_id` 单值、可空（存量 = null 向后兼容）。
5. **轻量原子认领**：`owner` + `claimed_at`，`req claim` 占用校验防并发覆盖，**无 TTL / 心跳**。
6. **命令面**：新增顶层命令组 `openfeel req`（`add` / `list` / `show` / `claim` / `release` / `set` / `link` / `advance` / `board` / `next`）。

## 关键裁定

| 议题 | 裁定 |
|------|------|
| **执行顺序** | **归档拆分先行**（主题二先于主题一；78→79→80→81→82→83→84→85 严格串行）——先收缩 flow.json 体积，为需求层腾空间（详见大计划 §四） |

| 存量迁移 | 本仓 78 阶段（v1.0.0 ~ v1.1.7 九组）一次性归档（stage-80 自举项）；程序 = 全量备份 + 逐版本判据门 + 回滚路径成文 |
| 需求模型 | 四层：`版本 → 需求 → 计划 → 方案`；需求层负责「排期与调度」，不负责「工序」 |
| 需求状态 | **双层**：显式粗粒度状态 + 关联阶段 15-phase **聚合投影**（单一事实源 = `phase`） |
| 需求存储 | `flow.json` 顶层 `requirements`（load 缺失补齐）；正文 `.openfeel/requirements/REQ-NNN.md`（人读副本） |

| 认领 | 轻量原子（`owner` + `claimed_at` + 占用校验）；**无 TTL / 心跳 / 抢占** |
| phase 枚举 | **零新增**（两主题共用）——需求层复用 15 phase 聚合，归档不改转移表 |

| 本仓自举 | v1.2.0 八阶段以 **full** 运行（架构级变更需完整审计链）；本仓 `workflow_mode: full` 在位 |
| 不做 | 需求间运行时 DAG 调度 / TTL 心跳抢占 / artifact-graph 集成 / 自动归档 / log 保留窗口 / 需求随版本归档（留后续版本） |

## 发布

- **不代 push / 不 `npm publish`**：推送与发布由 Feel/用户执行（与 v1.1.2~v1.1.7 口径一致）。
- v1.2.0 为**功能版（Y 级，新开发周期）**，命令面**增量**（新增 `flow archive` 子命令组 + 顶层命令组 `openfeel req`），需同步 `openfeel-cli-usage` skill 与 docs。
- **不新增第三方依赖**；CI 无改动；**无默认行为变更**（既有命令接受集不变、不报错；`requirements` 字段缺失 / 归档文件缺失时全命令零报错；归档执行后阶段枚举视图随活跃集收缩属设计预期，见下行兼容承诺）。
- 向后兼容承诺：既有命令**不读** `.openfeel/flow-archive/**` 文件内容（例外：`flow health` 归档一致性对账读目录清单级信息）、**不报错**；`requirement_id` 缺省 = 遗留无需求；**阶段枚举视图随活跃集收缩（文档明示，非回归）**——完整消费点清单与视图口径见大计划 §三 裁定 P 附注。
