# REQ-057：主会话只调度：子 Agent 分角色执行并记录派发

> 本文件为需求正文（人读副本，由 openfeel req 机械铺骨架）。**机读权威恒为 `.openfeel/flow.json` 的 `requirements` 条目**；两者不一致时以 flow.json 为准。下方状态为创建时快照，不追写实时状态。

## 状态

in_progress（创建时快照；以 flow.json 为准）

## 摘要

主会话（Feel/lead）把所有活都自己干：读代码、改文件、跑测试，上下文迅速拉满；需要子 Agent 时也不派发。提示词只是「建议」，没有任何后果。结果是一致性差、上下文爆、跨轮次失忆。

## 目标与验收

**目标**：把「主会话只调度、子 Agent 分工」从口号变成有记录、可观测、被提示词与工具面同时约束的动作。

- A7 `feel_dispatch action=record` 写入 `.openfeel/dev/dispatch.jsonl`（schema 见 plan §5.4），去重 5 分钟、保留 24h/200 行；`feel_status.dispatch` 暴露 `total/sincePhase/missingRoles/records`。
- A7b `feel_dispatch` 的 goal 不含 `<...>` 占位；`files` 与 `returnFormat` 落盘。
- A10 feel_mode 提示 ≤1200 字符、≤25 行、3 条「条件→动作→拒绝形态」检查点；5 处副本同哈希（parity 测试）。
- A10b 每步提醒走可用档位并在 `spike.md` 留证；`feel_status.nextAction` 为动作型（dispatch/command/idle）。
- 不做 guard 硬拦截（用户裁定 ②），只做记录 + 强提示 + 每步提醒。

## 问题

1. feel_mode 提示约 5000 字符、13 节、51 处加粗，混排政策与参考，关键禁令埋在中段，且自身文本里还有「一次 edit 改多处」这类反向鼓励。
2. 13 个 `feel_*` 工具里没有任何「派发」动作，工具返回的 `next` 恒指向另一个读工具 —— 模型永远收不到「你该派发了」。
3. 没有派发记录：谁派给谁、目标是什么、边界是什么，事后不可追溯，无法审计「主会话是否包办」。
4. 主会话与子 Agent 没有可观测的身份区分（guard 审计不含 origin）。

## 初步规划

1. `dsh/lib/adapters/dispatch-ledger.js` + `feel_dispatch` 工具 + guard 保护台账文件。
2. 提示词重写（`dsh/lib/surface/prompt.js`）并镜像到 template-loader 与 4 份 feel.md。
3. 每步提醒：post-execute spike（不可用则 systemPrompt.context 降级）+ 动作型 next。
4. 指标定义：`main_write_ratio`、`subagent_per_req`、`first_status_step`、`violation_rate`。
