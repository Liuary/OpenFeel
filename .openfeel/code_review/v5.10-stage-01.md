## REV-001 详情

- **标题**：`ensureProfileDefaults` 写盘失败未降级
- **优先级**：high（blocking）
- **文件**：`src/core/config.ts`
- **问题**：`writeProfile(profile)` 调用未包裹 try/catch，文件系统不可写时（权限不足、磁盘满、只读挂载）会抛出异常阻断 Feel 启动。
- **修复**：在 `ensureProfileDefaults` 中对 `writeProfile(profile)` 包裹 try/catch + `console.warn`，仅在外层降级。`writeProfile` 公共 API 内部未改动，保留其抛异常语义。
- **自测**：模拟写盘失败（EISDIR）时不抛异常，输出 `[profile] 自动填充写盘失败，已跳过` warn。

## REV-002 详情

- **标题**：`readProfile` 丢弃顶层 passthrough 字段
- **优先级**：medium（non-blocking）
- **文件**：`src/core/config.ts`
- **问题**：`readProfile` 返回时仅合并 `user`/`preferences`/`history` 三块，用户手动写入的顶层扩展字段（如 `custom_top_level`）被静默丢弃。后续 `writeProfile` 全量写回时会抹除这些字段。
- **修复**：`return { ...parsed, user, preferences, history }` — 先展开所有 parsed 字段，再覆盖三块深度合并值，保留扩展字段。
- **自测**：在 profile.yaml 中添加 `custom_top_level: 42`，读取后此字段保留，写回后仍存在。

## REV-003 详情

- **标题**：`projectPath` 未规范化导致 `recent_projects` 重复
- **优先级**：medium（non-blocking）
- **文件**：`src/core/config.ts`
- **问题**：`ensureProfileDefaults` 未对 `projectPath` 做规范化，不同表示形式（`C:\foo`、`C:/foo`、`C:\foo\`、`C:\foo\bar\..`）会被视为不同路径，导致 `recent_projects` 去重失效。
- **修复**：在函数开头 `const normalizedPath = resolve(projectPath)`，所有比较与存储均使用规范化路径。
- **已知限制**：`resolve()` 不统一 Windows 盘符大小写（`c:` vs `C:`），属边缘场景，记录为已知限制。
- **自测**：多种路径形式传入，`recent_projects` 仅保留一个规范化条目。

## 心得建议

1. **外层降级优于内部吞异常**：REV-001 的修复点在调用方而非公共函数内部，保持了 `writeProfile` 的异常透明性，使其他调用方可以自行决定是否处理异常。这比在公共函数内部静默吞掉所有异常要好。
2. **全量写回必须配 passthrough 保留**：配置文件读取时如果用选择性合并而非全量展开，后续全量写回就会丢失扩展字段。`readProfile` 中的 `...parsed` 展开是必须的配对操作。
3. **路径存储前规范化**：任何涉及路径比较或去重的场景，都应在入口处用 `resolve()` 规范化——成本极低，但能避免跨平台路径形式的细微差异导致的数据一致性问题。
